# Тема 5.7: HTTP и HTTPS. Полное руководство

Изучение фундаментальных протоколов прикладного уровня HTTP и HTTPS, их архитектуры "клиент-сервер", структуры сообщений (запрос/ответ), методов запросов, кодов состояния, заголовков, механизмов безопасности (TLS, HSTS, CORS, Cookies), эволюции от HTTP/1.1 к HTTP/2 и HTTP/3, а также практического анализа трафика в Wireshark.

---

## 1. Архитектура HTTP

### 1.1. Основные понятия и компоненты

- **Уровень OSI:** Прикладной уровень (L7).
- **Сущность данных (PDU):** Сообщение (запрос/ответ).
- **Транспортный протокол:** TCP (порт `80` для HTTP, порт `443` для HTTPS).
- **Принцип работы:** HTTP (Hypertext Transfer Protocol) — это протокол прикладного уровня для распределённых, совместных, гипермедийных информационных систем. Он работает по схеме **«клиент-сервер»**: клиент (например, браузер, поисковый робот, мобильное приложение) инициирует соединение и отправляет запрос, а сервер (например, веб-сервер `Apache`, `nginx`) ожидает соединения, обрабатывает запрос и возвращает ответ.

HTTP является **протоколом без состояния (stateless)**. Это означает, что каждый запрос обрабатывается изолированно, и протокол не "помнит" о предыдущих взаимодействиях. Для поддержания состояния используются дополнительные механизмы, такие как **Cookies** и **сессии**.

> **Важно:** HTTP не является безопасным протоколом. Все данные, включая заголовки и тело запроса, передаются в открытом виде, что делает их уязвимыми для перехвата и модификации. Для решения этой проблемы используется **HTTPS**.

### 1.2. Посредники (Intermediaries)

HTTP позволяет использовать посредников (прокси, шлюзы, туннели) для удовлетворения запросов через цепочку соединений. Важно различать их роли:

| **Тип посредника**                              | **Описание**                                                                                          | **Примеры использования**                                                                                       |
| :---------------------------------------------- | :---------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| **Прокси (Proxy)**                              | Посредник, выбираемый клиентом (обычно через локальную конфигурацию) для отправки запросов.           | Группировка трафика организации для безопасности или кэширования; обход ограничений на корпоративных фаерволах. |
| **Шлюз (Gateway / Reverse Proxy)**              | Посредник, выступающий в роли сервера для клиента, но перенаправляющий запросы на внутренние серверы. | Балансировка нагрузки, кэширование (ускорение), инкапсуляция устаревших или ненадёжных сервисов.                |
| **Туннель (Tunnel)**                            | Слепой ретранслятор между двумя соединениями, который не изменяет сообщения.                          | Организация зашифрованного туннеля (TLS) через прокси с помощью метода `CONNECT`.                               |
| **Перехватывающий прокси (Interception Proxy)** | Прокси, который перехватывает и фильтрует трафик (например, TCP-порт 80) без согласия клиента.        | Контроль политик доступа в корпоративных сетях ("каптивные порталы"), блокировка нежелательного контента.       |

> **Простыми словами:**
> - **Прокси** — это посредник, который ты выбираешь сам (например, в настройках браузера). Он может кэшировать данные или скрывать твой IP.
> - **Шлюз (Reverse Proxy)** — это посредник, который стоит перед сервером. Клиент думает, что общается с сервером, но на самом деле шлюз перенаправляет запрос на внутренний сервер. Это используется для балансировки нагрузки.
> - **Туннель** — это просто «труба», которая пропускает данные без изменений. Например, чтобы пробросить TLS через прокси, который не понимает TLS.
> - **Перехватывающий прокси** — это прокси, который встаёт между тобой и сервером без твоего ведома (например, в отеле или офисе). Его ещё называют «прозрачный прокси».

> **Важный нюанс:** Посредник, не являющийся туннелем, **обязан** реализовывать заголовок `Connection` и исключать из пересылки заголовки, предназначенные только для данного соединения ("hop-by-hop").

### 1.3. Кэширование (Caching)

Кэш — это локальное хранилище предыдущих ответных сообщений. Он позволяет сократить время ответа и уменьшить потребление сетевого трафика, обслуживая повторяющиеся запросы из локальной копии.

- Ответ является **кэшируемым**, если кэш может сохранить его копию для использования в ответ на будущие запросы.
- Правила кэширования определяются заголовками, такими как `Cache-Control` (например, `max-age`, `no-cache`).
- Кэш может быть реализован как на стороне клиента (браузер), так и на стороне посредников (прокси-серверы).

> **Пояснение:** `max-age` говорит браузеру, сколько секунд можно хранить копию. `no-cache` — не использовать кэш без проверки на сервере.

## 2. Структура HTTP-сообщения и синтаксис

Каждое HTTP/1.1 сообщение состоит из стартовой строки, одного или нескольких заголовков, пустой строки, обозначающей конец заголовков, и необязательного тела сообщения.

```abnf
HTTP-message   = start-line
                 *( header-field CRLF )
                 CRLF
                 [ message-body ]
```

### 2.1. Стартовая строка

- **Запрос (Request-line):** `Метод SP ПУТЬ_ЗАПРОСА SP HTTP-ВЕРСИЯ CRLF`.
    - *Пример:* `GET /wiki/HTTP HTTP/1.1`.
- **Ответ (Status-line):** `HTTP-ВЕРСИЯ SP КОД_СТАТУСА SP ПОЯСНЕНИЕ CRLF`.
    - *Пример:* `HTTP/1.1 200 OK`.

> **Важно для ИБ:** Рекомендуется, чтобы все отправители и получатели HTTP поддерживали длину стартовой строки не менее **8000 октетов** ([RFC 7230](https://www.ietf.org/rfc/rfc7230.html), раздел 3.1.1). Сервер, получивший запрос с URI длиннее, чем он готов обработать, должен ответить кодом `414 URI Too Long`.

> **Пояснение:** 8000 октетов — это рекомендованный минимум. На практике современные серверы и браузеры поддерживают гораздо большие длины, но этот лимит важен для совместимости со старым оборудованием.

### 2.2. Заголовки (Header Fields)

Заголовки содержат пары "имя-значение" и передают дополнительную информацию о сообщении, клиенте или сервере.

- **Синтаксис:** `header-field = field-name ":" OWS field-value OWS`.
- **Имена заголовков:** Не чувствительны к регистру (case-insensitive).
- **Расширяемость:** Заголовки полностью расширяемы. Новые поля могут быть введены без изменения версии протокола, если их семантика позволяет безопасно игнорировать их получателями, которые их не распознают.
- **Порядок заголовков:** Порядок получения заголовков с **разными** именами не имеет значения. Однако, заголовки с **одинаковыми** именами, чьи значения определены как разделённые запятыми списки (например, `Accept`), могут быть объединены в одно поле. **Исключение:** `Set-Cookie`, который часто встречается несколько раз в одном ответе и не должен объединяться.

> **Пояснение (про расширяемость):** Это значит, что разработчики могут добавлять свои собственные заголовки (например, `X-Custom-Header`), не дожидаясь выхода новой версии HTTP. Главное — чтобы старые клиенты игнорировали их, а не падали с ошибкой.

> **Простыми словами:** Заголовки — это как «конверт» для твоего запроса. В них лежит дополнительная информация: какой сайт ты хочешь открыть (`Host`), какой браузер у тебя (`User-Agent`), какой формат данных ты принимаешь (`Accept`). Без заголовков сервер не знал бы, что ему делать с твоим запросом.

### 2.3. Тело сообщения (Message Body)

Тело сообщения используется для передачи полезной нагрузки (payload body) запроса или ответа.

- **Наличие тела:** Для запросов наличие тела сигнализируется заголовками `Content-Length` или `Transfer-Encoding`. Для ответов наличие тела зависит от метода запроса и кода состояния.
- **Ответы БЕЗ тела:** Ответы на `HEAD`, все ответы с кодами `1xx`, `204 No Content`, `304 Not Modified` **не содержат** тела сообщения.
- **Определение длины тела:** Длина тела определяется в следующем порядке приоритета ([RFC 7230](https://www.ietf.org/rfc/rfc7230.html), раздел 3.3.3):
    1.  **HEAD / 1xx / 204 / 304:** Длина равна нулю (тела нет), независимо от заголовков.
    2.  **CONNECT (2xx):** Соединение переходит в режим туннеля, любые заголовки `Content-Length` или `Transfer-Encoding` игнорируются.
    3.  **Transfer-Encoding:** Если присутствует `Transfer-Encoding: chunked` как последнее кодирование, длина определяется чтением и декодированием фрагментированных данных.
    4.  **Несколько Content-Length:** Если получено несколько заголовков `Content-Length` с разными значениями, сообщение считается некорректным, и получатель должен обработать это как ошибку (например, ответить `400 Bad Request`).
    5.  **Один Content-Length:** Длина тела определяется его десятичным значением.
    6.  **Нет декларации (запрос):** Длина тела равна нулю.
    7.  **Нет декларации (ответ):** Длина тела определяется количеством октетов, полученных до закрытия соединения сервером.

> **Простыми словами:** Тело сообщения — это сами данные, которые передаются в запросе или ответе. Например, если ты открываешь веб-страницу, её HTML-код лежит именно в теле ответа. Если ты отправляешь форму, то данные формы лежат в теле запроса. Ответы с кодами 1xx, 204 и 304 не содержат тела, потому что они только информируют клиента, а не передают данные.

> **Простыми словами:** Сервер определяет, где заканчивается тело сообщения, в следующем порядке:
> 1. Если это ответ на `HEAD` или код `1xx`/`204`/`304` — тело отсутствует.
> 2. Если есть `Transfer-Encoding: chunked` — тело читается по частям (чанкам).
> 3. Если есть заголовок `Content-Length` — тело заканчивается ровно после указанного числа байт.
> 4. Если ничего нет — тело считается пустым.
> Если сервер получает несколько противоречивых заголовков длины, он считает запрос некорректным и отвечает `400 Bad Request`.

## 3. Технический алгоритм: Инкапсуляция и транзит пакетов в HTTP

При передаче HTTP-сообщения (например, GET-запроса) по сети, оно проходит через несколько уровней стека протоколов:

1.  **Прикладной уровень (HTTP):** Формируется HTTP-сообщение с заголовками и телом.
2.  **Транспортный уровень (TCP):** HTTP-сообщение инкапсулируется в TCP-сегменты. Устанавливается TCP-соединение (3-way handshake).
3.  **Сетевой уровень (IP):** TCP-сегменты инкапсулируются в IP-пакеты. Для HTTPS (TLS) применяется дополнительный уровень шифрования между прикладным и транспортным уровнями.
4.  **Канальный уровень (Ethernet, Wi-Fi):** IP-пакеты инкапсулируются в кадры с MAC-адресами.

**Критически важно для L3/L2 динамики:** При транзите пакетов через маршрутизаторы, физические **MAC-адреса** полностью меняются на каждом участке пути (хопе). Структура и заголовки **IP-пакета** остаются неизменными (за исключением поля `TTL`), независимо от смены среды передачи (Ethernet, Wi-Fi, LTE). Внутри IP-пакета находится TCP-сегмент, который, в свою очередь, содержит HTTP-сообщение.

## 4. Методы HTTP-запросов

Метод указывает на основную операцию, которую клиент хочет выполнить над ресурсом. Метод чувствителен к регистру.

| **Метод**   | **Назначение**                                                                                                          | **Идемпотентность** | **Безопасность** |
| :---------- | :---------------------------------------------------------------------------------------------------------------------- | :------------------ | :--------------- |
| **GET**     | Запрос представления ресурса.                                                                                           | Да                  | Да               |
| **HEAD**    | Аналогичен GET, но в ответе отсутствует тело сообщения. Используется для проверки наличия и метаданных ресурса.         | Да                  | Да               |
| **POST**    | Отправка данных на сервер для обработки (например, HTML-форма).                                                         | Нет                 | Нет              |
| **PUT**     | Замена всех текущих представлений ресурса данными запроса. Если ресурс не существует, он создается (201 Created).       | Да                  | Нет              |
| **DELETE**  | Удаление указанного ресурса.                                                                                            | Да                  | Нет              |
| **CONNECT** | Установка туннеля к серверу (например, для организации TLS через нешифрованный прокси).                                 | Нет                 | Нет              |
| **OPTIONS** | Описание параметров соединения с ресурсом или возможностей всего сервера.                                               | Да                  | Да               |
| **TRACE**   | Эхо-тест, возвращает полученный запрос клиенту. Используется для диагностики путей через прокси. Устарел и небезопасен. | Да                  | Да               |
| **PATCH**   | Частичное изменение ресурса.                                                                                            | Нет                 | Нет              |
*Таб. 1. Методы HTTP.*

> **Простыми словами:**
> - **GET** — «дай мне страницу». Ничего не меняет на сервере.
> - **POST** — «вот тебе данные, обработай их». Например, форма входа или отправка комментария.
> - **PUT** — «замени этот ресурс на то, что я тебе отправляю». Если ресурса нет — создай его.
> - **DELETE** — «удали этот ресурс».
> - **OPTIONS** — «расскажи, что ты умеешь».
> - **TRACE** — «отправь мне мой запрос обратно». Используется для отладки, но небезопасен.

> **Важно для ИБ:** Идемпотентность (свойство операций, при котором повторное выполнение приводит к тому же результату) критически важна для безопасности и надежности. Если соединение разрывается, клиент может безопасно повторить идемпотентный запрос (GET, PUT, DELETE) без риска нежелательных побочных эффектов. Метод `TRACE` часто отключается на серверах, так как может быть использован для кражи Cookies через XSS (атака, известная как Cross-Site Tracing).

## 5. Коды состояния HTTP

Код состояния указывает на результат выполнения запроса. Первая цифра кода определяет класс ответа.

| **Класс**                          | **Диапазон** | **Назначение**                                                                                                |
| :--------------------------------- | :----------- | :------------------------------------------------------------------------------------------------------------ |
| **Информационные (Informational)** | 1xx          | Запрос получен, обработка продолжается. Клиент должен быть готов принять такие сообщения.                     |
| **Успех (Success)**                | 2xx          | Запрос успешно принят и обработан.                                                                            |
| **Перенаправление (Redirection)**  | 3xx          | Клиенту необходимо выполнить другой запрос для завершения операции. Адрес указывается в заголовке `Location`. |
| **Ошибка клиента (Client Error)**  | 4xx          | Запрос содержит ошибку (неверный синтаксис, формат, маршрутизация или права доступа).                         |
| **Ошибка сервера (Server Error)**  | 5xx          | Операция не выполнена по вине сервера.                                                                        |

*Таб. 2. Классы кодов состояния.*

### 5.1. Детальный разбор наиболее важных кодов состояния

| **Код** | **Пояснение**              | **Описание**                                                                                                                    |
| :------ | :------------------------- | :------------------------------------------------------------------------------------------------------------------------------ |
| **200** | OK                         | Запрос успешно выполнен. Значение "успеха" зависит от метода.                                                                   |
| **201** | Created                    | Запрос выполнен, и в результате создан новый ресурс.                                                                            |
| **301** | Moved Permanently          | Ресурс **навсегда** перемещен на новый URI, указанный в `Location`. Будущие запросы должны использовать новый URI.              |
| **302** | Found                      | Ресурс **временно** перемещен. В будущем могут быть изменения, поэтому старый URI должен использоваться в будущих запросах.     |
| **303** | See Other                  | Редирект на другой URI, но **обязательно методом GET**, независимо от исходного метода.                                         |
| **307** | Temporary Redirect         | Клиенту необходимо получить ресурс по другому URI **тем же методом**, что и исходный запрос. Метод **не должен** изменяться.    |
| **308** | Permanent Redirect         | Ресурс навсегда перемещен. Клиенту необходимо использовать новый URI **тем же методом**.                                        |
| **400** | Bad Request                | Сервер не может обработать запрос из-за ошибки клиента (синтаксис, формат, маршрутизация).                                      |
| **401** | Unauthorized               | Требуется **аутентификация** клиента.                                                                                           |
| **403** | Forbidden                  | Сервер отказывает в доступе, даже если клиент аутентифицирован.                                                                 |
| **404** | Not Found                  | Запрашиваемый ресурс не найден. Часто используется вместо `403`, чтобы скрыть существование ресурса.                            |
| **405** | Method Not Allowed         | Метод запроса не поддерживается для данного ресурса. Сервер должен вернуть заголовок `Allow` со списком поддерживаемых методов. |
| **500** | Internal Server Error      | Внутренняя ошибка сервера.                                                                                                      |
| **502** | Bad Gateway                | Прокси или шлюз получил недопустимый ответ от вышестоящего сервера.                                                             |
| **503** | Service Unavailable        | Сервер временно не может обработать запрос (перегрузка, обслуживание). Рекомендуется отправлять заголовок `Retry-After`.        |
| **505** | HTTP Version Not Supported | Версия HTTP, используемая в запросе, не поддерживается сервером.                                                                |
*Таб. 3. Часто встречающиеся коды состояния HTTP.*

> **Пояснение:** Коды из класса 4xx говорят, что проблема на стороне клиента (например, неверный URL или недостаточно прав). Коды 5xx — что проблема на стороне сервера (например, он перегружен или в нём ошибка). Это помогает быстро понять, кто виноват в сбое.

## 6. Разбор сложных инженерных ситуаций и аномалий

### 6.1. Обработка некорректного пробела в запросе

**Вопрос:** *Что делать, если в запросе между именем заголовка и двоеточием есть пробел (например, `Host : example.com`)?*
**Технический ответ:** Согласно [RFC 7230](https://www.ietf.org/rfc/rfc7230.html), раздел 3.2.4, между именем заголовка и двоеточием **не должно быть** пробелов. Различия в обработке такого пробела в прошлом приводили к уязвимостям безопасности, таким как **request smuggling**. Сервер **обязан** отклонить такой запрос с кодом `400 Bad Request`. Прокси, в свою очередь, **обязан** удалить такой пробел из ответа перед пересылкой его клиенту.

### 6.2. Фрагментированные и разделенные на несколько строк заголовки

**Вопрос:** *Как обрабатывать заголовки, которые разделены на несколько строк (line folding)?*
**Технический ответ:** Исторически HTTP допускал разделение заголовков на несколько строк с помощью пробела или табуляции в начале каждой последующей строки (`obs-fold`). Эта практика **устарела** ([RFC 7230](https://www.ietf.org/rfc/rfc7230.html), раздел 3.2.4).
- **Отправитель:** **НЕ ДОЛЖЕН** генерировать сообщения с разделенными на строки заголовками, если только сообщение не предназначено для упаковки внутри типа `message/http`.
- **Получатель (сервер):** При получении такого заголовка в запросе должен либо отклонить его (`400 Bad Request`), либо заменить каждую разделительную строку на один или несколько пробелов перед интерпретацией.
- **Получатель (прокси/шлюз):** При получении такого заголовка в ответе должен либо отбросить ответ и заменить его на `502 Bad Gateway`, либо заменить каждую разделительную строку на один или несколько пробелов.

### 6.3. Выбор метода для отправки данных: POST vs PUT

**Вопрос:** *В чем фундаментальное различие между методами POST и PUT?*
**Технический ответ:** Это различие заключается в понимании предназначения URI ресурса.
- **Метод POST:** Предполагает, что по указанному URI будет производиться **обработка** передаваемого клиентом содержимого. Это как "отправить данные для обработки в этот офис".
- **Метод PUT:** Предполагает, что загружаемое клиентом содержимое соответствует находящемуся по данному URI ресурсу. Это как "заменить содержимое этого файла на то, что я вам отправляю". Если ресурс по URI не существует, `PUT` должен его создать, а `POST` — нет.

## 7. HTTPS и TLS. Глубокий технический разбор

**HTTPS** (Hypertext Transfer Protocol Secure) — это расширение протокола HTTP, работающее поверх криптографических протоколов **TLS** (Transport Layer Security) или устаревшего SSL. HTTPS обеспечивает:
- **Конфиденциальность:** Шифрование данных.
- **Целостность:** Проверка того, что данные не были изменены при передаче.
- **Аутентификацию:** Подтверждение подлинности сервера (и, опционально, клиента).

### 7.1. Архитектура TLS ([RFC 5246](https://www.ietf.org/rfc/rfc5246.txt), [RFC 8446](https://www.ietf.org/rfc/rfc8446.txt))

TLS — это протокол транспортного уровня, который работает поверх надежного транспортного протокола (например, TCP). Он состоит из двух основных компонентов:
- **TLS Record Protocol:** Отвечает за фрагментацию, сжатие, защиту (шифрование и MAC) и передачу данных.
- **TLS Handshake Protocol:** Отвечает за аутентификацию, согласование алгоритмов и выработку общих ключей.

**TLS Record Protocol (Детали):**
- **Фрагментация:** Данные от приложения фрагментируются на блоки размером не более `2^14` байт.
- **Сжатие:** Опционально, данные могут сжиматься (но в TLS 1.3 сжатие запрещено из-за атак CRIME/BREACH).
- **Защита:** К каждому фрагменту применяется MAC (код аутентификации сообщения), и затем все шифруется.
- **Типы записей:** `change_cipher_spec` (20), `alert` (21), `handshake` (22), `application_data` (23).

### 7.2. TLS Handshake (Алгоритм по шагам)

Рассмотрим классический полный TLS Handshake ([RFC 5246](https://www.ietf.org/rfc/rfc5246.txt), TLS 1.2):

| **Шаг** | **Что происходит** |
| :--- | :--- |
| **1. ClientHello** | Клиент отправляет серверу: <br> - Версию протокола (например, `TLS 1.2`). <br> - Случайное число (`ClientHello.random`). <br> - Список поддерживаемых алгоритмов шифрования (`Cipher Suites`). <br> - Список поддерживаемых методов сжатия. |
| **2. ServerHello** | Сервер выбирает и отправляет: <br> - Версию протокола. <br> - Случайное число (`ServerHello.random`). <br> - Выбранный набор шифров. <br> - Выбранный метод сжатия. |
| **3. Certificate** | Сервер отправляет свой цифровой сертификат (X.509). Он содержит открытый ключ сервера и информацию о центре сертификации (CA). |
| **4. ServerKeyExchange (опционально)** | Отправляется, если в сертификате недостаточно данных для выработки ключа (например, при использовании Diffie-Hellman). |
| **5. CertificateRequest (опционально)** | Сервер запрашивает сертификат у клиента для взаимной аутентификации. |
| **6. ServerHelloDone** | Сервер сообщает, что закончил фазу приветствия. |
| **7. Client Certificate (опционально)** | Клиент отправляет свой сертификат, если его запросил сервер. |
| **8. ClientKeyExchange** | Клиент отправляет информацию для выработки общего секрета (`PreMasterSecret`). В случае RSA это `PreMasterSecret`, зашифрованный открытым ключом сервера. В случае (EC)DHE — публичные параметры клиента. |
| **9. CertificateVerify (опционально)** | Клиент отправляет цифровую подпись, чтобы подтвердить владение закрытым ключом от своего сертификата. |
| **10. ChangeCipherSpec** | Клиент и сервер отправляют это сообщение, чтобы уведомить, что все последующие записи будут зашифрованы с использованием согласованных ключей. |
| **11. Finished** | Клиент и сервер отправляют сообщение `Finished`, которое содержит хеш всех предыдущих сообщений рукопожатия. Это подтверждает, что все стороны согласовали одни и те же параметры и никто не вмешивался в процесс. |
| **12. Application Data** | Начинается защищенный обмен данными. |
*Таб. 4. Процесс TLS Handshake.*

> **Важное инженерное дополнение (TLS 1.3):** В TLS 1.3 процесс Handshake был значительно оптимизирован. Он теперь требует всего **1-RTT** (один круговой обход) для установления соединения, а в случае возобновления сессии (PSK) может быть **0-RTT**. Это достигается за счет того, что сервер может отправить свой `ServerHello` и ключевые параметры сразу, а клиент — начать отправку зашифрованных данных в первом же пакете (если у него есть соответствующий ключ).

## 8. Эволюция HTTP: от 1.1 к 2 и 3

### 8.1. HTTP/1.1 ([RFC 7230](https://www.ietf.org/rfc/rfc7230.html))
- **Синтаксис:** Текстовый, разделенный пробелами и CRLF.
- **Соединения:** Поддерживает постоянные соединения (persistent connections), позволяя отправлять несколько запросов по одному TCP-соединению. Это улучшает производительность по сравнению с HTTP/1.0.
- **Пайплайнинг (Pipelining):** Позволяет отправлять несколько запросов без ожидания ответа на предыдущий. Однако эта функция страдает от **проблемы головной блокировки (Head-of-Line Blocking)**, когда один медленный запрос блокирует все последующие.
- **Заголовки:** Объемные и повторяющиеся. Включают `Host`, `Connection`, `Transfer-Encoding` и другие.

### 8.2. HTTP/2 ([RFC 7540](https://www.ietf.org/rfc/rfc7540))
- **Синтаксис:** **Бинарный** протокол, а не текстовый. Это упрощает парсинг и уменьшает количество ошибок.
- **Мультиплексирование:** Позволяет отправлять множество запросов и ответов по одному соединению **одновременно**. Это решает проблему головной блокировки HTTP/1.1.
- **Приоритизация:** Клиент может указать серверу приоритет для каждого потока. Сервер выделяет ресурсы в соответствии с этой приоритизацией.
- **Сжатие заголовков (HPACK):** Использует HPACK для сжатия заголовков, что значительно уменьшает размер сообщений.
- **Server Push:** Сервер может "проактивно" отправлять клиенту ресурсы, которые, по его мнению, клиент запросит в ближайшее время. Это может сократить задержки.
- **Поддержка TLS:** HTTP/2 не требует TLS, но в реальности (в «h2» режиме) используется только поверх TLS. Режим без TLS («h2c») практически не используется.
- **Идентификация:** Для TLS используется ALPN (Application-Layer Protocol Negotiation) с протоколом `h2`. Для незашифрованного соединения — механизм `Upgrade` (используется редко).

### 8.3. HTTP/3 ([RFC 9114](https://www.ietf.org/rfc/rfc9114.html))
- **Транспортный протокол:** **QUIC** (UDP-основанный мультиплексированный и безопасный транспорт), а не TCP. QUIC реализован на базе UDP и является преемником TCP + TLS.
- **Основан на QUIC:** QUIC предоставляет встроенную мультиплексируемость, контроль перегрузки и безопасность (TLS 1.3) на транспортном уровне. Это делает HTTP/3 еще более быстрым и эффективным.
- **Решение проблем TCP:** QUIC решает проблему головной блокировки на уровне соединения, которая возникает в TCP (потеря пакета блокирует все потоки). В QUIC потеря пакета влияет только на поток, к которому он относится.
- **Сжатие заголовков:** Использует **QPACK**, модификацию HPACK, адаптированную для QUIC (учитывает возможность прихода пакетов не по порядку).
- **Идентификация:** ALPN протокол `h3`. Поддержка TLS 1.3 обязательно.
- **0-RTT:** Поддерживает 0-RTT (как и TLS 1.3) для ускоренного установления соединения.

## 9. Углубленный ИБ-контекст: Cookies, CORS и политики безопасности

### 9.1. Cookies ([RFC 6265](https://www.ietf.org/rfc/rfc6265.txt))

Cookies — это механизм управления состоянием в HTTP, позволяющий серверу хранить небольшие объемы данных на клиенте. Они являются **фундаментальным инструментом для поддержания сессий, но также и источником многих уязвимостей.**

- **Установка Cookies:** Сервер отправляет заголовок `Set-Cookie` в ответе.
- **Передача Cookies:** Клиент включает соответствующие Cookies в заголовок `Cookie` при каждом запросе.

**Атрибуты Cookies ([RFC 6265](https://www.ietf.org/rfc/rfc6265.txt), раздел 4.1.2):**

| **Атрибут** | **Описание** | **Значение для ИБ** |
| :--- | :--- | :--- |
| **`Expires`** | Дата истечения срока действия. | Определяет время жизни. |
| **`Max-Age`** | Максимальное время жизни в секундах. | Более приоритетен, чем `Expires`. |
| **`Domain`** | Определяет, для каких доменов передавать Cookie. | **Критично для безопасности:** Указывает scope Cookie. Злоумышленник может попытаться установить Cookie с `Domain` для более широкого домена (например, `.com`), что приведет к отправке Cookie на все поддомены. Многие браузеры блокируют "публичные суффиксы". |
| **`Path`** | Определяет, для каких путей передавать Cookie. | Не обеспечивает надежной изоляции, так как пути не изолируют в браузере. |
| **`Secure`** | Cookie будет передаваться **только по HTTPS**. | **Критично для безопасности!** Защищает от перехвата в открытом канале. |
| **`HttpOnly`** | Cookie **недоступен** для сценариев (JavaScript). | **Критично для безопасности!** Защищает от кражи Cookies через XSS. |
| **`SameSite`** | Предотвращает отправку Cookie в запросах с других сайтов. | **Критично для безопасности!** Защищает от CSRF-атак. Возможные значения: `Strict`, `Lax`, `None`. |

*Таб. 6. Атрибуты Cookies и их влияние на безопасность.*

### 9.2. Cross-Origin Resource Sharing (CORS)

**CORS** — это механизм, позволяющий серверу разрешать доступ к своим ресурсам с других источников (домен, схема, порт). Он основан на HTTP-заголовках и является ключевым инструментом для обхода политики одного источника (Same-Origin Policy).

- **Механизм:** Браузер добавляет заголовок `Origin` к запросу. Сервер в ответе указывает `Access-Control-Allow-Origin`.
- **Пример:**
    - **Запрос:** `GET /api/data`
        `Origin: https://example.com`
    - **Ответ:**
        `Access-Control-Allow-Origin: https://example.com`
        `Access-Control-Allow-Methods: GET, POST`
- **Preflight Request:** Для запросов, которые могут повлиять на данные сервера (например, `PUT`, `DELETE`, или если используются нестандартные заголовки), браузер отправляет предварительный запрос `OPTIONS`. Сервер должен на него ответить, чтобы подтвердить разрешение.

### 9.3. HTTP Strict Transport Security (HSTS)

**HSTS** — это политика безопасности, реализуемая с помощью HTTP-заголовка `Strict-Transport-Security`. Когда клиент получает этот заголовок от сервера, он обязуется в течение указанного времени (`max-age`) взаимодействовать с этим сервером **исключительно по HTTPS**. Это предотвращает атаки, при которых злоумышленник пытается "понизить" протокол до HTTP и перехватить трафик (атака SSL Stripping).

## 10. Расширенный ИБ-контекст и инженерный FAQ

### 1. Векторы атак и уязвимости

1.  **Ответвление ответов (Response Splitting, CRLF Injection):**
    - *Описание:* Злоумышленник внедряет символы CR и LF (например, `%0D%0A`) в параметры запроса, которые затем отражаются в заголовках ответа. Это может привести к разделению одного HTTP-ответа на два, что позволяет злоумышленнику внедрить вредоносный контент и обмануть кэш или пользователя.
    - *Защита:* Фильтрация любых входящих данных на наличие CR/LF перед их использованием в заголовках ответа.

2.  **Контрабанда запросов (Request Smuggling):**
    - *Описание:* Техника, использующая различия в интерпретации длины тела сообщения между разными посредниками (прокси, фаерволы, серверы). Злоумышленник может отправить запрос, который один посредник воспримет как один запрос, а другой — как два, что позволяет обойти политики безопасности, обмануть кэш или отравить его.
    - *Защита:* Строгое соблюдение правил определения длины тела сообщения и обработки несоответствий.

3.  **Атаки на сессионные Cookies:**
    - *CSRF (Cross-Site Request Forgery):* Злоумышленник заставляет браузер жертвы выполнить нежелательное действие на сайте, где жертва уже аутентифицирована. Это возможно, потому что Cookies автоматически прикрепляются к запросам.
    - *Session Fixation:* Злоумышленник устанавливает идентификатор сессии для жертвы до того, как она войдет в систему, а затем, после входа жертвы, использует этот же идентификатор для получения доступа.
    - *Защита:* Использование флагов `Secure` (передача только по HTTPS), `HttpOnly` (недоступность для JavaScript), `SameSite` (защита от CSRF), а также регулярная ротация идентификаторов сессий.

4.  **Атаки на TLS:**
    - *POODLE (Padding Oracle On Downgraded Legacy Encryption):* Атака на устаревший протокол SSLv3.
    - *CRIME / BREACH:* Атаки, использующие сжатие данных для восстановления содержимого Cookies. Из-за этого в TLS 1.3 сжатие было запрещено.
    - *Защита:* Использование последних версий TLS (1.2 и 1.3), отключение устаревших версий и алгоритмов.

5.  **Ненадёжные алгоритмы подписи сертификатов:**
    - *Описание:* Использование хеш-функций, таких как MD5 и SHA-1, для подписи сертификатов считается небезопасным.
    - *Защита:* Все сертификаты должны использовать алгоритмы подписи с достаточной криптостойкостью (например, SHA-256 или выше). Серверы и клиенты должны отклонять сертификаты, подписанные с помощью MD5 или SHA-1.

### 2. Инженерный FAQ (На основе разбора дискуссий)

- **Вопрос:** *Что такое HSTS и как он работает?*
- **Технический ответ:** **HTTP Strict Transport Security** — это политика безопасности, реализуемая с помощью HTTP-заголовка `Strict-Transport-Security`. Когда клиент получает этот заголовок от сервера, он обязуется в течение указанного времени (`max-age`) взаимодействовать с этим сервером **исключительно по HTTPS**. Это предотвращает атаки, при которых злоумышленник пытается "понизить" протокол до HTTP и перехватить трафик (атака SSL Stripping).

- **Вопрос:** *В чем разница между 301, 302, 307 и 308 редиректами?*
- **Технический ответ:**
    - **301:** Постоянное перенаправление. Метод может быть изменен (GET) для последующих запросов.
    - **302:** Временное перенаправление. Метод может быть изменен (GET) для последующих запросов.
    - **307:** Временное перенаправление. Метод **НЕ МОЖЕТ** быть изменен для последующих запросов (сохраняет `POST`, `PUT` и т.д.).
    - **308:** Постоянное перенаправление. Метод **НЕ МОЖЕТ** быть изменен для последующих запросов.

- **Вопрос:** *Что такое CORS и зачем он нужен?*
- **Технический ответ:** **Cross-Origin Resource Sharing** — это механизм, основанный на HTTP-заголовках, который позволяет серверу указать, каким источникам (домен, схема, порт) разрешен доступ к его ресурсам. Это позволяет безопасно обходить политику одного источника (Same-Origin Policy) для обмена данными между разными доменами. Сервер использует заголовки `Access-Control-Allow-Origin` для разрешения доступа и другие (`Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`) для настройки параметров.

> **Пояснение:** Если бы не было CORS, браузеры запрещали бы любые запросы между разными доменами. Это защищает от кражи данных, но мешает нормальной работе современных веб-приложений, где один сайт часто обращается к API другого. CORS — это компромисс между безопасностью и удобством.

- **Вопрос:** *Что такое "безопасный контекст" (secure context) в вебе и как он связан с HTTPS?*
- **Технический ответ:** **Безопасный контекст** — это `window` или `worker`, для которых существует разумная уверенность в том, что содержимое было доставлено безопасно, то есть через **HTTPS/TLS**. Многие мощные функции веб-платформы (например, доступ к камере, геолокация, уведомления, Payment Request API) доступны **только** в безопасном контексте. Это предотвращает атаки "человек посередине" и гарантирует, что доступ к чувствительным API происходит из проверенного источника.

## 11. Практический анализ HTTP/HTTPS трафика в Wireshark

Для анализа HTTP и HTTPS трафика в Wireshark используются следующие **display filters**:

| **Фильтр** | **Что показывает** |
| :--- | :--- |
| `http` | Весь HTTP-трафик. |
| `http.request.method == "GET"` | Только GET-запросы. |
| `http.request.method == "POST"` | Только POST-запросы. |
| `http.response.code == 404` | Ответы с кодом 404. |
| `http.host == "example.com"` | Запросы к конкретному хосту. |
| `http.cookie contains "session"` | Запросы, содержащие Cookie с "session". |
| `http.request.uri contains "admin"` | Запросы к URI, содержащим "admin". |
| `tcp.port == 443` | Трафик на порту 443 (HTTPS). |
| `http.response.code >= 400` | Ответы с кодами ошибок (4xx и 5xx). |
| `tls.handshake` | Весь TLS Handshake. |
| `tls.handshake.type == 1` | Сообщения Client Hello. |
| `tls.handshake.type == 2` | Сообщения Server Hello. |
| `tls.handshake.type == 11` | Сообщения Certificate. |

*Таб. 7. Полезные фильтры Wireshark для HTTP/HTTPS.*

**Быстрый сценарий диагностики:**
1.  Отфильтровать HTTP-трафик: `http`.
2.  Посмотреть, какие методы используются: `http.request.method`.
3.  Выявить ошибки: `http.response.code >= 400`.
4.  Для HTTPS-трафика можно увидеть только TLS Handshake, сами данные зашифрованы. Фильтр `tls.handshake` покажет процесс согласования.

## Заключение

HTTP и HTTPS являются фундаментальными протоколами Всемирной паутины и многих других сетевых приложений. Их понимание необходимо для любого специалиста, работающего с сетями и веб-технологиями. HTTPS обеспечивает безопасную передачу данных, хотя и не решает всех проблем безопасности (остаются уязвимости на уровне приложений). Эволюция от HTTP/1.1 к HTTP/2 и HTTP/3 показывает постоянное стремление к повышению эффективности и безопасности. Понимание атак, таких как CSRF, XSS и Response Splitting, а также механизмов защиты (CORS, HSTS, атрибуты Cookies) является критически важным для проектирования безопасных веб-приложений.
