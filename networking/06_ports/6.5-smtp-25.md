# Тема 6.5: SMTP (Simple Mail Transfer Protocol) — Порт 25

Изучение протокола передачи электронной почты SMTP: архитектура «клиент-сервер», команды и коды ответов, аутентификация (`AUTH PLAIN`, `AUTH LOGIN`) и шифрование (`STARTTLS`, неявный TLS), защита от спуфинга (`SPF`, `DKIM`, `DMARC`), анализ трафика в Wireshark, а также основные уязвимости (`SMTP Smuggling`, `Command Injection`, `Header Injection`).

---

## 1. SMTP — Базовые свойства

- **Уровень OSI:** Прикладной (L7).
- **Транспорт:** TCP (порты `25`, `587`, `465`).
- **PDU:** SMTP-сообщение (команды и ответы).
- **Принцип работы:** SMTP — протокол для отправки и пересылки электронной почты. Работает по схеме «клиент-сервер»: клиент (почтовый клиент или сервер отправителя) устанавливает TCP-соединение с сервером (MTA) и передаёт сообщение. SMTP не отвечает за получение почты — для этого используются POP3 или IMAP.

> **Почему это важно для SOC:** SMTP — один из старейших протоколов интернета ([RFC 821](https://datatracker.ietf.org/doc/html/rfc821), 1982 год). Через него распространяется фишинг, спам, вредоносные вложения. SMTP не проверяет подлинность отправителя — любой сервер может отправить письмо с любым обратным адресом. Это делает его идеальным каналом для спуфинга и мошенничества. Анализ SMTP-трафика позволяет выявить: подозрительные рассылки, поддельные домены, утечки данных через email, активность ботнетов.

### 1.1. Порты SMTP

| Порт | Назначение | Шифрование | RFC |
| :--- | :--- | :--- | :--- |
| **25** | Передача почты между SMTP-серверами (MTA-to-MTA). Часто блокируется провайдерами для пользовательских приложений. | Нет (или STARTTLS) | RFC 5321 |
| **587** | Отправка почты от клиента на сервер отправителя (submission). Современный стандарт. | STARTTLS | RFC 6409 |
| **465** | SMTPS — неявный TLS (шифрование с первого байта). Устаревший, но всё ещё используется. | Неявный TLS | RFC 8314 |
*Таб. 1. Порты SMTP.*

> **Примечание:** Порт 25 исторически использовался для релея между серверами. Сейчас для отправки из почтовых клиентов рекомендуется использовать **587 с STARTTLS**. Порт **465** — для случаев, когда требуется «TLS с первого байта» (неявное шифрование). Порт 2525 — не стандартизирован, используется как запасной в некоторых сервисах.

### 1.2. Основные компоненты

- **MTA (Mail Transfer Agent)** — почтовый сервер, передающий сообщения (Postfix, Sendmail, Exchange, Exim).
- **MUA (Mail User Agent)** — почтовый клиент (Outlook, Thunderbird, веб-интерфейс).
- **MSA (Message Submission Agent)** — сервер отправки (обычно на порту 587).
- **MX-запись** — DNS-запись, указывающая на почтовый сервер домена.
- **Envelope** — техническая информация (MAIL FROM, RCPT TO), которая может отличаться от заголовков письма.

> **Простыми словами:** MUA — это твой Outlook, который отправляет письмо. MTA — это почтовый сервер, который принимает письмо и передаёт его дальше. MX-запись говорит, куда именно отправлять почту для домена `example.com`.

### 1.3. Путь письма

```text
Приложение/Клиент → MSA (порт 587) → MTA отправителя → DNS (MX) → MTA получателя → Почтовый ящик
```

1. Клиент отправляет письмо на сервер отправителя (MSA).
2. Сервер отправителя определяет сервер получателя по MX-записям.
3. Устанавливается SMTP-соединение между MTA отправителя и MTA получателя.
4. Письмо передаётся и помещается в ящик получателя.

## 2. Структура SMTP-сессии

SMTP-сессия состоит из последовательности команд клиента и ответов сервера. Каждая команда завершается `<CRLF>`, ответ — трёхзначным кодом и текстом.

### 2.1. Основные команды

| Команда | Назначение | Синтаксис |
| :--- | :--- | :--- |
| `EHLO <domain>` | Представление клиента (Extended SMTP). Сервер отвечает списком расширений. | `EHLO client.example.com` |
| `HELO <domain>` | Устаревшее представление (без расширений). | `HELO client.example.com` |
| `MAIL FROM:<address>` | Указывает обратный адрес (envelope sender). | `MAIL FROM:<user@example.com>` |
| `RCPT TO:<address>` | Указывает получателя. Может быть несколько. | `RCPT TO:<recipient@example.org>` |
| `DATA` | Начало передачи тела письма. Завершается строкой с одной точкой. | `DATA` |
| `RSET` | Сброс текущей транзакции. | `RSET` |
| `VRFY <string>` | Проверка существования пользователя (часто отключена). | `VRFY username` |
| `EXPN <string>` | Раскрытие списка рассылки (часто отключена). | `EXPN listname` |
| `HELP [command]` | Справка. | `HELP` |
| `NOOP` | Пустая операция. | `NOOP` |
| `QUIT` | Завершение сессии. | `QUIT` |
*Таб. 2. Основные команды SMTP.*

> **Важно:** `MAIL FROM` и `RCPT TO` — это **envelope**-адреса, они не обязательно совпадают с заголовками `From:` и `To:` в теле письма. Это ключевое различие для понимания спуфинга и работы SPF/DKIM. Поле `From:` видит пользователь, а `MAIL FROM` используется для технических нужд (например, для уведомлений о недоставке).

### 2.2. Расширения ESMTP

Сервер объявляет поддерживаемые расширения в ответ на `EHLO`:

| Расширение | Назначение | RFC |
| :--- | :--- | :--- |
| `SIZE` | Максимальный размер сообщения. | RFC 1870 |
| `AUTH` | Аутентификация клиента. | RFC 4954 |
| `STARTTLS` | Переход на шифрованное соединение. | RFC 3207 |
| `8BITMIME` | Передача 8-битных данных. | RFC 1652 |
| `PIPELINING` | Конвейеризация команд. | RFC 2920 |
| `DSN` | Уведомления о доставке. | RFC 3461 |
| `HELP` | Поддержка справки. | RFC 5321 |
| `VRFY` | Поддержка проверки пользователей. | RFC 5321 |
*Таб. 3. Расширения ESMTP.*

> **Пояснение:** Расширения объявляются сервером в ответ на `EHLO`. Клиент может использовать только те, которые поддерживаются. Если клиент отправит команду, не объявленную в `EHLO`, сервер вернёт ошибку `500` или `502`.

### 2.3. Пример SMTP-сессии (полный цикл)

```text
S: 220 mail.example.com ESMTP Postfix
C: EHLO client.example.com
S: 250-mail.example.com
S: 250-PIPELINING
S: 250-SIZE 10240000
S: 250-STARTTLS
S: 250-AUTH PLAIN LOGIN
S: 250 8BITMIME
C: STARTTLS
S: 220 2.0.0 Ready to start TLS
... TLS handshake ...
C: EHLO client.example.com
S: 250-mail.example.com
S: 250-PIPELINING
S: 250-SIZE 10240000
S: 250-AUTH PLAIN LOGIN
S: 250 8BITMIME
C: AUTH PLAIN XDAwMHRlc3R1c2VyQGNvbnRvc28uY29tXDAwMCR1cDNSc1RyKW5n
S: 235 2.7.0 Authentication successful
C: MAIL FROM:<user@example.com>
S: 250 2.1.0 Ok
C: RCPT TO:<recipient@example.org>
S: 250 2.1.5 Ok
C: DATA
S: 354 End data with <CR><LF>.<CR><LF>
C: Subject: Test
C: From: user@example.com
C: To: recipient@example.org
C: 
C: Hello, world!
C: .
S: 250 2.0.0 Ok: queued as 12345
C: QUIT
S: 221 2.0.0 Bye
```

### 2.4. Порядок команд

1. `EHLO` (или `HELO`) — обязательно перед началом транзакции.
2. `STARTTLS` (опционально) — переход на шифрование.
3. Повторный `EHLO` после `STARTTLS`.
4. `AUTH` (опционально) — аутентификация.
5. `MAIL FROM` — начало транзакции.
6. `RCPT TO` (один или несколько).
7. `DATA` — передача тела письма.
8. `QUIT` — завершение сессии.

> **Важно:** `MAIL FROM` должен быть отправлен только если нет активной транзакции. Если отправить `MAIL FROM` дважды без `RSET`, сервер вернёт `503 Bad sequence of commands`.

## 3. Коды ответов SMTP

Коды ответов — трёхзначные числа. Первая цифра указывает на класс:

| Класс | Значение | Описание |
| :--- | :--- | :--- |
| **2xx** | Успех | Команда выполнена |
| **3xx** | Промежуточный | Требуется продолжение (например, `354` после `DATA`) |
| **4xx** | Временная ошибка | Можно повторить позже |
| **5xx** | Постоянная ошибка | Повтор не поможет |
*Таб. 4. Классы кодов ответов SMTP.*

### Основные коды

| Код | Значение | Когда используется |
| :--- | :--- | :--- |
| **220** | Сервер готов | При подключении |
| **221** | Закрытие соединения | После `QUIT` |
| **235** | Аутентификация успешна | После `AUTH` |
| **250** | Запрошенное действие выполнено | После `EHLO`, `MAIL FROM`, `RCPT TO`, `DATA` |
| **251** | Пользователь не локальный, будет переадресован | После `RCPT TO` |
| **252** | Не удалось проверить пользователя, но письмо будет принято | После `VRFY` |
| **334** | Сервер ждёт продолжения аутентификации | После `AUTH LOGIN` |
| **354** | Начало ввода данных | После `DATA` |
| **421** | Сервер недоступен, закрытие соединения | При перегрузке |
| **450** | Временная ошибка (ящик недоступен) | После `RCPT TO` |
| **451** | Временная ошибка (локальная) | После `DATA` |
| **452** | Недостаточно места | После `RCPT TO`, `DATA` |

| **500** | Синтаксическая ошибка, команда не распознана | Любая команда |
| **501** | Синтаксическая ошибка в параметрах | Любая команда |
| **502** | Команда не реализована | Любая команда |
| **503** | Нарушена последовательность команд | Любая команда |
| **504** | Параметр команды не реализован | Любая команда |
| **550** | Постоянная ошибка (ящик не найден, доступ запрещён) | После `RCPT TO`, `DATA` |
| **551** | Пользователь не локальный, попробуйте другой адрес | После `RCPT TO` |
| **552** | Превышено выделенное место | После `DATA` |
| **553** | Недопустимое имя ящика | После `MAIL FROM`, `RCPT TO` |
| **554** | Транзакция не выполнена | При подключении, после `DATA` |
| **555** | Параметры `MAIL FROM`/`RCPT TO` не распознаны | После `MAIL FROM`, `RCPT TO` |

## 4. Аутентификация и шифрование

### 4.1. AUTH PLAIN и AUTH LOGIN

SMTP-аутентификация используется для подтверждения права клиента отправлять почту через сервер.

**AUTH PLAIN:**
```text
S: 250 AUTH PLAIN
C: AUTH PLAIN XDAwMHRlc3R1c2VyQGNvbnRvc28uY29tXDAwMCR1cDNSc1RyKW5n
```
Клиент отправляет строку `\0username\0password` в **Base64**. В примере: `\0testuser@contoso.com\0$up3RsTr)ng`.

**AUTH LOGIN:**
```text
S: 250 AUTH LOGIN
C: AUTH LOGIN
S: 334 VXNlcm5hbWU=
C: dGVzdHVzZXI=
S: 334 UGFzc3dvcmQ=
C: cGFzc3dvcmQ=
S: 235 Authentication successful
```
Сервер запрашивает имя пользователя и пароль отдельно. `VXNlcm5hbWU=` — это `Username` в Base64, `UGFzc3dvcmQ=` — `Password`.

> **Важно:** Оба метода передают логин и пароль в **Base64**, что **не является шифрованием**. При перехвате трафика учётные данные легко декодируются. Использовать только внутри TLS (STARTTLS или SMTPS). Если сервер не поддерживает STARTTLS, использование этих методов небезопасно.

### 4.2. STARTTLS ([RFC 3207](https://www.ietf.org/rfc/rfc3207))

`STARTTLS` — расширение, позволяющее «апгрейдить» открытое соединение до шифрованного TLS.

**Как работает:**
1. Клиент подключается к порту 587.
2. Отправляет `EHLO`, сервер отвечает, что поддерживает `STARTTLS`.
3. Клиент отправляет `STARTTLS`.
4. Начинается TLS-рукопожатие.
5. После успешного TLS весь дальнейший обмен (включая AUTH и DATA) шифруется.
6. Клиент **обязан** снова отправить `EHLO`, так как список расширений может измениться.

> **Примечание:** После `STARTTLS` сервер может объявить новые расширения (например, `AUTH`), которые не были доступны до шифрования. Некоторые серверы требуют аутентификацию только после `STARTTLS`.

### 4.3. Порты 465 и 587

| Порт | Режим | Описание | RFC |
| :--- | :--- | :--- | :--- |
| **465** | Неявный TLS (SMTPS) | Шифрование с первого байта. Устаревший, но используется. | RFC 8314 |
| **587** | STARTTLS | Открытое соединение, затем апгрейд до TLS. Современный стандарт. | RFC 6409 |
*Таб. 6. Порты для шифрованного SMTP.*

> **Примечание:** В 2018 году [RFC 8314](https://www.ietf.org/rfc/rfc8314.txt) официально рекомендовал отказаться от использования порта 465 для SMTPS в пользу более гибкого подхода с командой STARTTLS на порту 587. Несмотря на это, порт 465 всё ещё встречается в устаревших системах или корпоративных политиках, где требуется «TLS с первого байта».

### 4.4. Сравнение подходов

| Критерий | Порт 465 (SMTPS) | Порт 587 (STARTTLS) |
| :--- | :--- | :--- |
| Момент установления шифрования | Сразу при подключении | После установления соединения и команды STARTTLS |
| Гибкость | Менее гибок | Более гибок, позволяет работать с устаревшими клиентами |
| Уязвимость | Может быть уязвим к downgrade-атакам | Первоначальное соединение открыто, что теоретически позволяет перехватить команду STARTTLS |
*Таб. 7. Сравнение SMTPS и STARTTLS.*

> **Рекомендация Microsoft:** Использовать порт 587 с STARTTLS для исходящей почты пользователей. Порт 465 — только в специфических случаях.

## 5. Защита от спуфинга: SPF, DKIM, DMARC

SMTP не проверяет подлинность отправителя. Любой сервер может отправить письмо с любым обратным адресом. Для борьбы со спуфингом используются три технологии:

### 5.1. SPF (Sender Policy Framework, [RFC 7208](https://www.rfc-editor.org/info/rfc7208/))

SPF позволяет домену опубликовать в DNS список IP-адресов, которым разрешено отправлять почту от его имени.

**Как работает:**
1. Принимающий сервер получает письмо.
2. Делает DNS-запрос к домену отправителя (из `MAIL FROM`).
3. Получает SPF-запись.
4. Сверяет IP-адрес отправляющего сервера со списком разрешённых.
5. Принимает решение: `pass`, `fail`, `softfail`, `neutral`, `permerror`, `temperror`.

**Пример SPF-записи:**
```dns
v=spf1 include:_spf.google.com ip4:185.100.50.25 -all
```

| Механизм | Описание | Пример |
| :--- | :--- | :--- |
| `ip4` | Разрешить конкретный IPv4-адрес или подсеть | `ip4:192.168.1.1` или `ip4:10.0.0.0/24` |
| `ip6` | Разрешить IPv6-адрес или подсеть | `ip6:2001:db8::/32` |
| `a` | Разрешить IP-адреса из A-записи домена | `a:mail.example.com` |
| `mx` | Разрешить IP-адреса из MX-записей домена | `mx` |
| `include` | Включить SPF-запись другого домена | `include:_spf.google.com` |
| `redirect` | Перенаправить проверку на другой домен | `redirect=_spf.example.com` |
*Таб. 8. Механизмы SPF.*

**Модификаторы по умолчанию:**

| Модификатор | Значение | Когда использовать |
| :--- | :--- | :--- |
| `+all` | Разрешить всё | Никогда |
| `~all` | Мягкий отказ (softfail) | На этапе тестирования |
| `-all` | Жёсткий отказ (fail) | В продакшене |
| `?all` | Нейтрально | Редко |
*Таб. 9. Модификаторы SPF.*

**Примеры SPF-записей:**

```dns
; Google Workspace
v=spf1 include:_spf.google.com -all

; Яндекс 360
v=spf1 include:_spf.yandex.net -all

; Mail.ru для бизнеса
v=spf1 include:_spf.mail.ru -all

; Комбинированная
v=spf1 include:_spf.google.com ip4:185.100.50.25 include:spf.sendpulse.com -all

; Домен, который не отправляет почту
v=spf1 -all
```

> **Важно:** SPF проверяет адрес из `MAIL FROM`, а не из заголовка `From:`. Лимит — **10 DNS-запросов** при обработке записи. Превышение приводит к ошибке `permerror`, и вся проверка считается проваленной. Заменяйте `include` на конкретные `ip4`/`ip6`, где это возможно.

> **Ограничение:** SPF ломается при пересылке писем, если сервер пересылки не указан в SPF-записи. В таких случаях помогает DKIM.

### 5.2. DKIM (DomainKeys Identified Mail, [RFC 6376](https://www.ietf.org/rfc/rfc6376))

DKIM добавляет цифровую подпись к письму. Отправитель подписывает заголовки и тело приватным ключом, получатель проверяет подпись публичным ключом из DNS.

**Как работает:**
1. Отправляющий сервер вычисляет хэш от заголовков и тела письма.
2. Шифрует хэш приватным ключом.
3. Добавляет подпись в заголовок `DKIM-Signature`.
4. Принимающий сервер извлекает домен и селектор.
5. Получает публичный ключ из DNS (`[селектор]._domainkey.[домен]`).
6. Расшифровывает подпись и сравнивает хэши.

**Пример DNS-записи DKIM:**
```dns
; Имя: google._domainkey.example.com
; Тип: TXT
v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC3QEKyU1fSm...
```

| Параметр | Описание |
| :--- | :--- |
| `v=DKIM1` | Версия протокола |
| `k=rsa` | Алгоритм ключа (rsa или ed25519) |
| `p=...` | Публичный ключ в Base64 |
| `t=s` | Строгий режим (запрещает поддомены) |
| `t=y` | Тестовый режим |
*Таб. 10. Параметры DKIM.*

**Пример заголовка письма:**
```text
DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=google; 
    h=from:to:subject:date;
    bh=...; b=...
```

> **Примечание:** DKIM устойчив к пересылке, так как подпись привязана к содержимому, а не к IP. Рекомендуется использовать ключи длиной не менее **2048 бит**. Ключи рекомендуется менять каждые 6–12 месяцев. При ротации используйте новый селектор и публикуйте новый ключ заранее.

> **RSA vs Ed25519:** Ed25519 — более современная альтернатива с компактными ключами (44 символа в Base64). Пока поддерживается не всеми провайдерами. Разумная стратегия — публиковать оба ключа с разными селекторами.

### 5.3. DMARC (Domain-based Message Authentication, Reporting and Conformance, [RFC 7489](https://datatracker.ietf.org/doc/html/rfc7489))

DMARC объединяет SPF и DKIM и задаёт политику для писем, не прошедших проверку.

**Ключевое понятие — alignment (выравнивание):** DMARC требует, чтобы домен в `From:` (который видит пользователь) совпадал с доменом, прошедшим SPF или DKIM. Без DMARC злоумышленник мог отправить письмо с `MAIL FROM: hacker@evil.com` (SPF пройдёт для evil.com) и заголовком `From: ceo@yourcompany.ru` (это увидит получатель). DMARC это пресекает.

**Пример DMARC-записи:**
```dns
; Имя: _dmarc.example.com
; Тип: TXT
v=DMARC1; p=reject; rua=mailto:dmarc-reports@example.com; ruf=mailto:dmarc-forensic@example.com; adkim=s; aspf=s; pct=100
```

| Параметр | Значения | Описание |
| :--- | :--- | :--- |
| `v` | DMARC1 | Версия (обязательный) |
| `p` | none, quarantine, reject | Политика для основного домена (обязательный) |
| `sp` | none, quarantine, reject | Политика для поддоменов |
| `rua` | mailto:адрес | Куда отправлять агрегированные отчёты |
| `ruf` | mailto:адрес | Куда отправлять forensic-отчёты |
| `adkim` | r (relaxed), s (strict) | Выравнивание для DKIM |
| `aspf` | r (relaxed), s (strict) | Выравнивание для SPF |
| `pct` | 1–100 | Процент писем, к которым применяется политика |
| `fo` | 0, 1, d, s | Условия генерации forensic-отчётов |
*Таб. 11. Параметры DMARC.*

**Политики DMARC:**

| Политика | Действие |
| :--- | :--- |
| `p=none` | Только мониторинг, письма доставляются как обычно |
| `p=quarantine` | Подозрительные письма отправляются в спам |
| `p=reject` | Письма отклоняются на уровне SMTP |
*Таб. 12. Политики DMARC.*

**Пример DMARC-записи для поддоменов:**
```dns
_dmarc.example.com TXT "v=DMARC1; p=reject; sp=reject; rua=mailto:dmarc@example.com"
```
Параметр `sp=reject` распространяет жёсткую политику на все поддомены.

> **Важно:** DMARC не заменяет SPF и DKIM, а строится на их результатах. DMARC считается пройденным, если выполнено хотя бы одно из условий:
> - SPF прошёл И домен в `MAIL FROM` совпадает с доменом в `From` (SPF alignment).
> - DKIM прошёл И домен в подписи совпадает с доменом в `From` (DKIM alignment).
>
> Именно поэтому рекомендуется настраивать и SPF, и DKIM. Даже если SPF ломается при пересылке, DKIM-подпись остаётся валидной, и письмо проходит DMARC.

### 5.4. Как эти стандарты работают вместе

```text
Входящее письмо
       │
       ▼
┌─────────────────┐
│  Проверка SPF   │ ← IP отправителя в списке?
│  (MAIL FROM)    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Проверка DKIM  │ ← Подпись валидна?
│  (заголовок)    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Проверка DMARC │ ← SPF или DKIM прошли
│  (alignment +   │    И домен совпадает с From?
│   политика)     │
└────────┬────────┘
         │
    ┌────┴────┐
    │  pass   │  fail
    ▼         ▼
 Доставка   Применение политики
            (none/quarantine/reject)
```

> **Практический совет:** Начинайте с аудита — составьте полный список всех сервисов, отправляющих почту от вашего домена (CRM, рассылки, helpdesk, мониторинг). Настройте SPF и DKIM для всех. Затем добавьте DMARC в режиме `p=none` и собирайте отчёты 2–4 недели. После анализа ужесточайте политику: `p=quarantine` (с нарастающим `pct`), затем `p=reject`.

## 7. Разбор сложных инженерных ситуаций и аномалий

### 7.1. Аномалия: SMTP Smuggling (CVE-2023-51766)

**Суть:** Злоумышленник использует различия в обработке `DATA` между SMTP-серверами. Внедряя специальные последовательности `\r\n.\r\n`, он может «протащить» второе письмо в рамках одной сессии, обходя SPF.

**Пример:** Атакующий отправляет письмо с `MAIL FROM: attacker@evil.com`, но внутри `DATA` вставляет `\r\n.\r\nMAIL FROM: ceo@company.com\r\nRCPT TO: victim@company.com\r\nDATA\r\n...`. Один сервер воспринимает это как одно письмо, другой — как два. Второе письмо выглядит как отправленное от `ceo@company.com`.

**Как обнаружить:**
- В логах SMTP-сервера — необычные последовательности в `DATA`.
- В Wireshark — подозрительные точки в конце строк.
- Аномально длинные сессии с несколькими `MAIL FROM`.

**Защита:** Обновление серверов до последних версий. Использование современных SMTP-серверов (Postfix, Exim, Sendmail) с патчами.

### 7.2. Аномалия: SMTP Command Injection (CVE-2025-59419)

**Суть:** В библиотеке Netty (Java) параметры команд SMTP не фильтровались на `\r\n`. Злоумышленник мог внедрить произвольные SMTP-команды, отправляя письма от имени доверенного сервера. Поскольку инжектированные команды отправляются с доверенного IP-адреса, письма проходят SPF и DKIM, выглядя легитимными.

**Уязвимые версии:** Netty < 4.1.128.Final и < 4.2.7.Final.

**Защита:** Обновление Netty до версий 4.1.129.Final / 4.2.8.Final. Валидация входных данных на наличие `\r` и `\n`.

### 7.3. Аномалия: Header Injection (VU#517845)

**Суть:** Использование специального синтаксиса в заголовке `From:` (например, `<attacker@example.com>:<spoofed@example.com>`) позволяет обойти DMARC и выдать письмо за другого отправителя. Многие почтовые клиенты отображают только последний адрес, и получатель не знает, что письмо якобы от нескольких отправителей.

**Пример:** Атакующий отправляет письмо с `From: <attacker@example.com>:<ceo@company.com>`. Получатель видит `ceo@company.com`, но технически письмо отправлено с `attacker@example.com`.

**Защита:** Проверка заголовков на стороне сервера, обновление milter-фильтров (Milterfrom 1.0.4+). Пользователям — проверять оригинальные заголовки при подозрении.

### 7.4. Аномалия: Open Relay

**Суть:** SMTP-сервер настроен на пересылку почты от любого отправителя к любому получателю без аутентификации. Это позволяет злоумышленникам использовать сервер для рассылки спама.

**Как обнаружить:**
- В логах сервера — множество писем от разных отправителей к разным получателям.
- Аномально высокий исходящий трафик на порт 25.
- Жалобы от других провайдеров.

**Защита:** Настройка аутентификации, ограничение релея только для доверенных сетей.

### 7.5. Аномалия: Brute Force AUTH

**Суть:** Злоумышленник подбирает пароли к SMTP-серверу через `AUTH LOGIN` или `AUTH PLAIN`.

**Как обнаружить:**
- Массовые `535` (Authentication failed) в логах.
- Повторяющиеся `AUTH` с одного IP.

**Защита:** Rate limiting, fail2ban, блокировка после N неудачных попыток, использование сложных паролей.

### 8.2. Инженерный FAQ

**Вопрос: Чем SMTP отличается от IMAP и POP3?**
**Ответ:** SMTP — для отправки. IMAP и POP3 — для получения. SMTP работает по принципу «push» (отправка на сервер), IMAP/POP3 — «pull» (получение с сервера).

**Вопрос: Что такое envelope sender и header From?**
**Ответ:** Envelope sender — адрес в `MAIL FROM` (технический, используется для уведомлений о недоставке). Header From — то, что видит пользователь. Они могут различаться, что используется для спуфинга.

**Вопрос: Что такое STARTTLS?**
**Ответ:** Расширение, позволяющее перейти на TLS после установления соединения. Обычно используется на порту 587. После `STARTTLS` клиент должен снова отправить `EHLO`.

**Вопрос: Что такое SPF alignment?**
**Ответ:** Требование DMARC, чтобы домен в `MAIL FROM` совпадал с доменом в `From:`. Если не совпадает — SPF не защищает от спуфинга.

**Вопрос: Как проверить, настроен ли SPF/DKIM/DMARC у домена?**
**Ответ:** `dig TXT example.com` (SPF), `dig TXT google._domainkey.example.com` (DKIM), `dig TXT _dmarc.example.com` (DMARC).

**Вопрос: Почему письмо попало в спам, хотя SPF и DKIM настроены?**
**Ответ:** Причин может быть несколько: репутация IP-адреса, содержание письма, отсутствие DMARC, неправильная настройка alignment, пересылка через сервер без DKIM.

**Вопрос: Что такое MTA-STS?**
**Ответ:** Mail Transfer Agent Strict Transport Security — политика, позволяющая домену требовать шифрованное соединение с его MX-серверами. Аналог HSTS для почты.

**Вопрос: Что такое DANE?**
**Ответ:** DNS-based Authentication of Named Entities — использование DNSSEC для публикации сертификатов. Позволяет проверять подлинность почтовых серверов без публичных CA.

## Заключение

SMTP — фундаментальный протокол электронной почты. Понимание его команд, кодов ответов, аутентификации и шифрования необходимо для анализа трафика и выявления атак. Защита от спуфинга строится на SPF, DKIM и DMARC. Уязвимости, такие как SMTP Smuggling, Command Injection и Header Injection, требуют внимания при обновлении ПО и настройке серверов. SOC-аналитик должен уметь анализировать SMTP-логи, Wireshark-дампы и проверять конфигурацию DNS-записей. Email-аутентификация — это не опциональная рекомендация, а необходимый минимум для любого домена, отправляющего почту.
