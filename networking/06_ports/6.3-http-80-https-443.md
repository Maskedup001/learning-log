# Тема 6.3: HTTP (порт 80) и HTTPS (порт 443)

Изучение протоколов HTTP и HTTPS — фундаментальных механизмов передачи гипертекста и защищённого обмена данными в сети. Рассматриваются структура сообщений, методы, коды состояния, заголовки, различия между HTTP и HTTPS (TLS), а также основные уязвимости и методы их обнаружения.

---

## 1. HTTP — Базовые свойства

- **Уровень OSI:** Прикладной (L7).
- **Транспорт:** TCP (по умолчанию порт `80` для HTTP, `443` для HTTPS).
- **PDU:** HTTP-сообщение (запрос или ответ).
- **Принцип работы:** Протокол «запрос-ответ» (клиент-сервер). Каждое сообщение состоит из стартовой строки, заголовков и тела (опционально). HTTP не сохраняет состояние (stateless) — каждый запрос независим.

![Вывод команды netstat -tuln.png](/attachments/networking/06_ports/6.3-http-80-https-443/Вывод%20команды%20netstat%20-tuln.png)

*Рис. 1. Вывод команды netstat -tuln: видно, что порт 80 (HTTP) и порт 22 (SSH) находятся в состоянии LISTEN.*

> **Почему это важно:** Отсутствие состояния означает, что сервер не помнит предыдущие запросы. Все данные о сессии (например, логин) передаются в каждом запросе через заголовки (Cookie, Authorization). Это упрощает масштабирование, но требует аккуратной работы с куками и токенами для обеспечения безопасности.

### 1.1. URI и URL

Ресурс в HTTP идентифицируется через URI (Uniform Resource Identifier). Формат `http://host:port/path?query`:
- `http` или `https` — схема;
- `host` — доменное имя или IP;
- `port` — порт (по умолчанию `80` для HTTP, `443` для HTTPS);
- `path` — путь к ресурсу;
- `query` — параметры запроса.

**Пример:** `https://example.com:443/search?q=test&lang=ru`

**Важно:** Согласно [RFC 9110](https://www.rfc-editor.org/info/rfc9110/), URI `http://example.com:80` и `http://example.com` эквивалентны (нормализация по умолчанию).

> **Пояснение про порт:** Если в URI не указан порт, браузер автоматически подставит `80` для HTTP и `443` для HTTPS. Это избавляет от необходимости писать `http://example.com:80`.

### 1.2. Origin (Происхождение)

Для «https» URI: `{"https", "example.com", "443"}`. Два origin считаются разными, если отличаются схемой, хостом или портом. Это важно для политики безопасности браузеров.

> **Примечание:** Origin — ключевое понятие для CORS (Cross-Origin Resource Sharing). Браузер разрешает запросы к ресурсу только если origin совпадает или сервер явно разрешает (через заголовок `Access-Control-Allow-Origin`). Неправильная настройка CORS может привести к утечке данных.

## 2. Структура HTTP-сообщения

Каждое HTTP-сообщение (запрос или ответ) состоит из:
1. **Стартовая строка** (request-line или status-line).
2. **Заголовки** (header fields) — пары `имя: значение`.
3. **Пустая строка** (CRLF).
4. **Тело сообщения** (message-body) — опционально.

### 2.1. Запрос (Request)

```http
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html
```

- **Метод:** `GET`, `POST`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`, `TRACE`, `CONNECT`.
- **Путь:** `/index.html` (origin-form).
- **Версия:** `HTTP/1.1`.

> **Важно:** В HTTP/1.1 тело запроса может отсутствовать (например, в `GET`). Если тело есть, его размер обязательно указывается в заголовке `Content-Length`. Отсутствие этого заголовка при наличии тела — ошибка.

### 2.2. Ответ (Response)

```http
HTTP/1.1 200 OK
Date: Mon, 27 Jul 2009 12:28:53 GMT
Server: Apache
Content-Length: 51
Content-Type: text/html

<html>...</html>
```

- **Статус-код:** `200 OK`.
- **Заголовки:** `Date`, `Server`, `Content-Type` и др.
- **Тело:** содержимое ресурса.

### 2.3. Формы request-target

| Форма | Описание | Использование |
| :--- | :--- | :--- |
| **origin-form** | `/path?query` | Обычные запросы к origin-серверу |
| **absolute-form** | Полный URI | Запрос к прокси |
| **authority-form** | `host:port` | Метод `CONNECT` (туннель) |
| **asterisk-form** | `*` | Метод `OPTIONS *` (проверка сервера) |
*Таб. 1. Формы request-target.*

> **Примечание:** В HTTP/1.1 обязательно должен быть заголовок `Host`, даже если используется `absolute-form`. Это нужно для виртуального хостинга, когда на одном IP-адресе работает несколько сайтов. Если `Host` отсутствует, сервер вернёт `400 Bad Request`.

## 3. Методы HTTP

| Метод | Описание | Идемпотентность | Безопасность | Кэшируемость |
| :--- | :--- | :--- | :--- | :--- |
| `GET` | Получить представление ресурса | Да | Да | Да |
| `HEAD` | Как GET, но без тела ответа | Да | Да | Да |
| `POST` | Отправить данные на обработку | Нет | Нет | Да (при явном указании) |
| `PUT` | Создать/заменить ресурс | Да | Нет | Нет |
| `DELETE` | Удалить ресурс | Да | Нет | Нет |
| `OPTIONS` | Определить возможности сервера | Да | Да | Нет |
| `TRACE` | Диагностика (loop-back) | Да | Да | Нет |
| `CONNECT` | Установить туннель (например, для TLS) | Нет | Нет | Нет |
*Таб. 2. Основные методы HTTP и их свойства.*

> **Почему это важно:** Методы `GET` и `HEAD` безопасны — они не изменяют состояние сервера, поэтому их можно повторять без риска. `POST` не идемпотентен: повторная отправка одного и того же запроса может создать несколько одинаковых ресурсов (например, дублировать комментарий). Поэтому автоматические повторные запросы (например, при обрыве связи) для `POST` должны выполняться с осторожностью.

## 4. Коды состояния HTTP

Коды состояния — трёхзначные числа, сгруппированные по классам:

| Класс | Диапазон | Назначение |
| :--- | :--- | :--- |
| **1xx** | 100–199 | Информационные (промежуточные ответы) |
| **2xx** | 200–299 | Успешные |
| **3xx** | 300–399 | Перенаправления |
| **4xx** | 400–499 | Ошибки клиента |
| **5xx** | 500–599 | Ошибки сервера |
*Таб. 3. Классы кодов состояния.*

> **Совет для SOC:** При анализе HTTP-трафика обращай внимание на коды `301` и `302`. Они могут указывать на попытку редиректа на вредоносный сайт. А вот массовые `404` в логах — признак сканирования директорий (Directory Bruteforce).

![Пример перенаправления 301 Moved Permanently.png](/attachments/networking/06_ports/6.3-http-80-https-443/Пример%20перенаправления%20301%20Moved%20Permanently.png)

*Рис. 2. Пример перенаправления 301 Moved Permanently: заголовок Location указывает на новый адрес.*

### Основные коды

- **200 OK** — запрос успешен.
- **201 Created** — ресурс создан.
- **204 No Content** — успех, тело отсутствует.
- **301 Moved Permanently** — постоянное перенаправление.
- **302 Found** — временное перенаправление.
- **304 Not Modified** — ресурс не изменился (кэш актуален).
- **400 Bad Request** — синтаксическая ошибка запроса.
- **401 Unauthorized** — требуется аутентификация.
- **403 Forbidden** — доступ запрещён.
- **404 Not Found** — ресурс не найден.
- **405 Method Not Allowed** — метод не поддерживается для данного ресурса.
- **500 Internal Server Error** — внутренняя ошибка сервера.
- **502 Bad Gateway** — ошибка шлюза/прокси.
- **503 Service Unavailable** — сервер временно недоступен.

> **Примечание:** Код `404` иногда намеренно возвращается вместо `403`, чтобы скрыть существование ресурса от неавторизованных пользователей (защита от перебора). Если атакующий получает `403` — он знает, что ресурс есть, но доступ запрещён; `404` говорит, что ресурса нет вообще.

## 5. Заголовки HTTP

Заголовки делятся на:

- **General headers** — общие для запросов и ответов.
- **Request headers** — только в запросах.
- **Response headers** — только в ответах.
- **Entity headers** — метаданные тела.

### Ключевые заголовки

| Заголовок | Назначение |
| :--- | :--- |
| `Host` | Доменное имя и порт (обязательный в HTTP/1.1) |
| `Content-Length` | Размер тела в байтах |
| `Content-Type` | MIME-тип тела (например, `text/html`) |
| `Content-Encoding` | Кодировка тела (gzip, deflate) |
| `Authorization` | Учётные данные для аутентификации |
| `Cookie` | Данные сессии (куки) |
| `User-Agent` | Идентификация клиента |
| `Referer` | Источник ссылки |
| `Location` | Адрес перенаправления (в ответах 3xx) |
| `Set-Cookie` | Установка куки |
| `Cache-Control` | Политика кэширования |
| `Upgrade` | Переключение протокола (например, на WebSocket) |
| `Vary` | Параметры, влияющие на представление ресурса |
*Таб. 4. Основные заголовки HTTP.*

> **Важно для ИБ:** Заголовок `Server` раскрывает версию веб-сервера. Злоумышленник может использовать эту информацию для поиска известных уязвимостей (CVE). Рекомендуется скрывать или изменять `Server` для уменьшения поверхности атаки.

## 6. HTTP vs HTTPS (TLS)

### 6.1. Что такое HTTPS

**HTTPS** — это HTTP, работающий поверх TLS (Transport Layer Security). 

**Обеспечивает:**
- **Конфиденциальность** — шифрование данных.
- **Целостность** — защита от подмены.
- **Аутентификацию** — проверка подлинности сервера через сертификаты.

Порт по умолчанию: `443` (для HTTPS).

### 6.2. TLS Handshake (упрощённо)

1. **ClientHello** — клиент предлагает версии TLS, шифры и отправляет случайное число.
2. **ServerHello** — сервер выбирает параметры, отправляет сертификат.
3. **Certificate** — сервер отправляет свой X.509-сертификат (содержит публичный ключ).
4. **Key Exchange** — стороны вырабатывают общий сеансовый ключ (например, через ECDHE).
5. **Finished** — обмен подтверждениями, после чего данные передаются зашифрованными.

> **Примечание:** В TLS 1.3 алгоритм рукопожатия упрощён (0-RTT), но главное отличие — весь обмен ключами происходит после `ServerHello` и до `Finished`. Также в TLS 1.3 **SNI (Server Name Indication)** остаётся видимым в открытом виде (он передаётся в ClientHello), но **URL/путь запроса шифруются**. Это важно для анализа трафика: по SNI можно определить, к какому сайту идёт запрос, но не конкретный URL.

### 6.3. Анализ HTTPS в Wireshark

- До `ClientHello` виден только TCP Handshake.
- После `ServerHello` и `Certificate` — обмен ключами, затем всё шифруется.
- В Wireshark для расшифровки можно импортировать приватный ключ сервера (pre-master secret) или использовать SSLKEYLOGFILE.

> **Фильтр для быстрого поиска:** `tls.handshake.extensions_server_name` — этот фильтр показывает, к какому домену идёт запрос по SNI. Это помогает быстро определить, какой сайт посетил пользователь, даже если данные зашифрованы.

```bash

netstat -tuln | grep -E ':80|:443'

# Более детальный вывод с PID процесса (нужны права root)
sudo netstat -tulnp | grep -E ':80|:443'

# Быстрый запрос к серверу (заголовки ответа)
curl -I http://example.com
curl -I https://example.com

# Запустить локальный HTTP-сервер для теста (на порту 80, нужны права root)
sudo python3 -m http.server 80
```

## 8. Разбор сложных инженерных ситуаций и аномалий

### 8.1. Аномалия: Content-Length и Transfer-Encoding (Request Smuggling)

Одна из наиболее опасных уязвимостей HTTP/1.1 — **HTTP Request Smuggling** (контрабанда запросов). Возникает, когда фронтенд и бэкенд по-разному интерпретируют границы запроса, используя заголовки `Content-Length` (CL) и `Transfer-Encoding: chunked` (TE).

- **CL.TE**: Фронтенд использует `Content-Length`, бэкенд — `Transfer-Encoding`.
- **TE.CL**: Фронтенд использует `Transfer-Encoding`, бэкенд — `Content-Length`.

**Пример CL.TE:**
```http
POST / HTTP/1.1
Host: example.com
Content-Length: 43
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: example.com
```

Фронтенд читает 43 байта тела (включая `0\r\n\r\n`), передаёт всё на бэкенд. Бэкенд видит `chunked`, завершает запрос на `0`, а остальное (`GET /admin...`) считает новым запросом — **смоуклинг**.

> **Почему это опасно:** Злоумышленник может «протащить» второй запрос, который бэкенд выполнит, но фронтенд не увидит. Это позволяет обходить WAF, фильтры безопасности и отравлять кэш. Например, можно подменить содержимое кэшируемой страницы, чтобы другие пользователи получили вредоносный ответ.

**Пример проверки уязвимости через netcat:**

```bash
# Отправка запроса с двумя заголовками для проверки
# Если сервер отвечает 400 Bad Request или следующим запросом является ваш "GET /admin",
# значит, сервер уязвим для CL.TE
printf 'POST / HTTP/1.1\r\nHost: example.com\r\nContent-Length: 6\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nG' | nc example.com 80
```

![Реальный ответ сервера на подозрительный запрос с двумя заголовками (Content-Length и Transfer-Encoding).png](/attachments/networking/06_ports/6.3-http-80-https-443/Реальный%20ответ%20сервера%20на%20подозрительный%20запрос%20с%20двумя%20заголовками%20(Content-Length%20и%20Transfer-Encoding).png)

*Рис. 10. Реальный ответ сервера на подозрительный запрос с двумя заголовками (Content-Length и Transfer-Encoding). Сервер вернул 400 Bad Request, что указывает на корректную защиту от Request Smuggling.*

> **Пояснение:** В этом примере мы отправляем запрос с `Content-Length: 6` и `Transfer-Encoding: chunked`. Фронтенд, читающий по `Content-Length`, передаст на бэкенд все 6 байт (`0\r\n\r\nG`). Бэкенд, интерпретирующий по `chunked`, увидит `0\r\n\r\n` как конец запроса, а оставшийся символ `G` станет началом **следующего** запроса, который атакующий может "подделать".

**Как обнаружить:** Отправьте запрос с обоими заголовками и проверьте ответ — если следующий запрос возвращает неожиданный код (например, `404`), возможно, есть уязвимость.

**Защита:** Не допускайте одновременного присутствия `Content-Length` и `Transfer-Encoding`; унифицируйте ПО фронтенда и бэкенда; используйте HTTP/2.

### 8.2. Аномалия: SQL Injection (SQLi)

**Сценарий:** Пользовательские данные попадают в SQL-запрос без экранирования.
- Например, в поле поиска вводят `' OR 1=1 --` — запрос возвращает все записи.
- **Обнаружение:** В Wireshark видите необычные символы в параметрах; в логах приложения — ошибки SQL.
- **Защита:** Использование параметризованных запросов (prepared statements), валидация и экранирование ввода.

> **Важно:** SQLi — это не только про поиск. Через `POST`-запросы можно внедрить команды в любые поля, которые попадают в запрос к БД. Поэтому валидируйте все пользовательские данные, а не только GET-параметры.

### 8.3. Аномалия: XSS (Cross-Site Scripting)

**Сценарий:** Внедрение JavaScript в HTML-страницу, отображаемую другим пользователям.
- **Reflected XSS:** Полезная нагрузка немедленно возвращается в ответе.
- **Stored XSS:** Полезная нагрузка сохраняется на сервере (например, в комментариях).
- **DOM-based XSS:** Выполняется в браузере без отправки на сервер.
- **Обнаружение:** В Wireshark видим HTML-код с `<script>` или `onerror`; в браузере — подозрительное поведение.
- **Защита:** Кодирование вывода (escaping), CSP (Content-Security-Policy), валидация ввода.

> **Примечание:** XSS может быть использован для кражи куки (Cookie theft), перехвата сессий или выполнения действий от имени жертвы. Именно поэтому многие сайты используют заголовок `Content-Security-Policy` для ограничения выполнения скриптов.

### 8.4. Аномалия: MITM (Man-in-the-Middle)

**Сценарий:** Злоумышленник перехватывает трафик, подменяя сертификат сервера.
- **Обнаружение:** Предупреждение браузера о недействительном сертификате; несовпадение отпечатка при первом подключении.
- **Защита:** Использование HTTPS, проверка сертификатов, HSTS (Strict-Transport-Security).

> **Что такое HSTS:** Заголовок `Strict-Transport-Security` заставляет браузер всегда использовать HTTPS для данного домена. Это предотвращает атаку понижения (SSL Stripping), когда злоумышленник принуждает клиента перейти на HTTP.

## 9. Расширенный ИБ-контекст и инженерный FAQ

### 9.1. Векторы атак на HTTP/HTTPS

- **Request Smuggling** (CL.TE, TE.CL, TE.TE) — обход фильтров, отравление кэша.
- **Response Splitting** (CRLF-инъекция) — внедрение HTTP-заголовков.
- **Open Redirect** — перенаправление на вредоносный сайт через параметры.
- **HTTP Parameter Pollution** — подмена параметров.
- **Cookie Theft** — кража сессионных куки (через XSS или MITM).
- **SSL Stripping** — понижение до HTTP (если нет HSTS).

> **Про SSL Stripping:** Эта атака работает, только если сервер не отправляет заголовок `HSTS`. Если ты видишь в логах, что клиент сначала обращается по HTTP, а потом редиректится на HTTPS — это может быть признаком попытки перехвата.

### 9.2. Инженерный FAQ

**Вопрос: Почему HTTPS использует порт 443, а не 80?**
**Ответ:** Порт 443 закреплён для HTTPS в реестре IANA. Использование отдельного порта позволяет легко различать защищённые и незащищённые соединения без анализа содержимого.

**Вопрос: Что такое HSTS?**
**Ответ:** Заголовок `Strict-Transport-Security` заставляет браузер всегда использовать HTTPS для данного домена, предотвращая атаки понижения до HTTP.

**Вопрос: Как можно увидеть URL в HTTPS-трафике?**
**Ответ:** В TLS 1.3 URL (кроме SNI) зашифрован. SNI (Server Name Indication) виден до установления шифрования — это имя хоста, но не путь.

**Вопрос: Почему POST-запросы не кэшируются?**
**Ответ:** POST может изменять состояние сервера (не идемпотентен), поэтому кэширование по умолчанию запрещено. Только если ответ содержит явные указания (Content-Location и свежесть), он может быть закэширован.

**Вопрос: Что делать при обнаружении HTTP Request Smuggling?**
**Ответ:** Следуйте рекомендациям: отключить повторное использование соединений, перейти на HTTP/2, унифицировать ПО, включить WAF.

## Заключение

HTTP и HTTPS — основа современного веба. Понимание структуры сообщений, методов, кодов состояния и заголовков необходимо для анализа сетевого трафика, выявления уязвимостей и настройки защиты. Особое внимание следует уделять обработке `Content-Length` и `Transfer-Encoding`, а также валидации пользовательского ввода против SQLi и XSS. Современные протоколы (HTTP/2, HTTP/3) снижают риск smugglings, но не устраняют полностью необходимость правильной конфигурации.
