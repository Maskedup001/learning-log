# Тема 6.4: DNS (Domain Name System) — Порт 53

Изучение системы доменных имён — распределённой базы данных, преобразующей понятные человеку имена в IP-адреса. Рассматриваются иерархия DNS-серверов, типы ресурсных записей, структура DNS-сообщения, транспорт (UDP/TCP), практическая диагностика (`dig`, `nslookup`, `host`), анализ в Wireshark, а также основные уязвимости (DNS Spoofing, Cache Poisoning, DNS Tunneling).

---

## 1. DNS — Базовые свойства

- **Уровень OSI:** Прикладной (L7).
- **Транспорт:** UDP (по умолчанию порт `53` для стандартных запросов) и TCP (порт `53` для зонных передач AXFR и больших ответов).
- **PDU:** DNS-сообщение (запрос/ответ).
- **Принцип работы:** DNS (Domain Name System) — распределённая система, которая переводит доменные имена в IP-адреса. Работает по схеме «запрос-ответ»: клиент (резолвер) отправляет запрос DNS-серверу, тот возвращает IP-адрес или другую информацию.

> **Почему это важно для SOC:** DNS — это «телефонная книга интернета». Практически любой сетевой трафик начинается с DNS-запроса. Анализ DNS-логов позволяет выявить: подозрительные домены (C2-серверы), DNS-туннелирование (утечка данных), попытки фишинга (поддельные домены), а также работу вредоносного ПО, которое использует DNS для связи с управляющим сервером.

### 1.1. Иерархия DNS

DNS построен по иерархическому принципу (дерево). Каждый уровень делегирует ответственность нижестоящим:

1. **Корневые серверы (Root Servers):** На вершине иерархии. Всего 13 корневых серверов (дублированы по всему миру). Знают, где находятся серверы TLD.
2. **Серверы TLD (Top-Level Domain):** Управляют доменами верхнего уровня (`.com`, `.net`, `.org`, `.ru`). Знают, где находятся авторитетные серверы для конкретных доменов.
3. **Авторитетные серверы:** Содержат информацию о конкретном домене (например, `example.com`). Возвращают окончательный IP-адрес.
4. **Рекурсивные резолверы:** Посредники между клиентом и DNS-серверами. Выполняют полный поиск от имени клиента, кэшируют ответы.

> **Уточнение:** Формально существует **13 корневых серверов** (A–M), но физически их гораздо больше — сотни серверов по всему миру, работающих через **anycast**. Это обеспечивает отказоустойчивость и низкую задержку при запросах.

![Иерархия DNS-серверов.png](/attachments/networking/06_ports/6.4-dns-53/Иерархия%20DNS-серверов.png)

*Рис. 1. Иерархия DNS-серверов: от корневой зоны (root) через домены первого уровня (.com, .ru, .org) до доменов второго и третьего уровня, а также поддоменов.*

> **Простыми словами:** Ты вводишь `example.com` в браузере. Твой компьютер обращается к рекурсивному резолверу (обычно это DNS-сервер провайдера). Тот, если не знает ответ, идёт к корневому серверу, затем к серверу `.com`, затем к авторитетному серверу `example.com`, получает IP и возвращает его тебе. Всё это происходит за миллисекунды.

### 1.2. Зоны и Делегирование

- **Зона** — часть дерева доменных имён, размещаемая как единое целое на одном DNS-сервере.
- **Делегирование** — передача ответственности за часть дерева другому лицу/организации. В родительскую зону добавляются «склеивающие» записи (NS и A), указывающие на DNS-серверы дочерней зоны.

> **Примечание:** Делегирование позволяет распределённость администрирования. Например, `example.com` может быть делегирован компании, которая сама управляет своими поддоменами (`mail.example.com`, `www.example.com`).

## 2. Структура DNS-сообщения

Все DNS-сообщения имеют единый формат, разделённый на 5 секций:

1. **Header** — всегда присутствует (12 байт).
2. **Question** — вопрос к серверу (QNAME, QTYPE, QCLASS).
3. **Answer** — RRs, отвечающие на вопрос.
4. **Authority** — RRs, указывающие на авторитетный сервер.
5. **Additional** — RRs с дополнительной информацией (например, A-записи для NS).

### 2.1. Заголовок (Header Section)

```abnf
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                      ID                       |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|QR|   Opcode  |AA|TC|RD|RA|   Z    |   RCODE   |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                    QDCOUNT                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                    ANCOUNT                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                    NSCOUNT                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                    ARCOUNT                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
```

| Поле | Описание |
| :--- | :--- |
| **ID** | 16-битный идентификатор для сопоставления ответа с запросом |
| **QR** | 0 — запрос, 1 — ответ |
| **Opcode** | 0 — стандартный запрос (QUERY), 1 — инверсный (IQUERY), 2 — статус (STATUS) |
| **AA** | Authoritative Answer: сервер является авторитетным для зоны |
| **TC** | Truncation: сообщение было обрезано (если > 512 байт по UDP) |
| **RD** | Recursion Desired: клиент просит рекурсивный поиск |
| **RA** | Recursion Available: сервер поддерживает рекурсию |
| **RCODE** | 0 — NOERROR, 1 — FORMERR, 2 — SERVFAIL, 3 — NXDOMAIN, 4 — NOTIMP, 5 — REFUSED |

> **Важно для SOC:** Код `NXDOMAIN` (3) означает, что домен не существует. Аномально большое количество `NXDOMAIN` в логах может указывать на сканирование доменов (DNS brute-force) или попытки подключения к мёртвым C2-серверам. `SERVFAIL` (2) может свидетельствовать о проблемах с вышестоящим сервером или о перегрузке.

### 2.2. Секция Вопросов (Question Section)

```abnf
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
/                     QNAME                     /
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                     QTYPE                     |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                     QCLASS                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
```

- **QNAME** — доменное имя в формате последовательности меток (например, `example.com`).
- **QTYPE** — тип запроса (A, AAAA, MX, NS, TXT и т.д.).
- **QCLASS** — класс запроса (IN — Internet).

> **Пояснение:** QNAME передаётся в специфическом формате: каждая метка начинается с байта длины. Например, `example.com` будет закодировано как `\x07example\x03com\x00`. В Wireshark это видно в деталях пакета.

### 2.3. Ресурсные записи (Resource Records)

Формат RR одинаков для секций Answer, Authority и Additional:

```abnf
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
/                      NAME                     /
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                      TYPE                     |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                     CLASS                     |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                      TTL                      |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                   RDLENGTH                    |
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
/                     RDATA                     /
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
```

- **NAME** — имя, к которому относится запись.
- **TYPE** — тип записи (A, NS, CNAME, MX, TXT, SOA, PTR).
- **CLASS** — класс (IN).
- **TTL** — время жизни записи в кэше (в секундах).
- **RDLENGTH** — длина поля RDATA.
- **RDATA** — данные, зависящие от типа записи.

> **Важно для SOC:** TTL имеет критическое значение. Если TTL очень короткий (например, 0 или 1), это может указывать на DNS Rebinding-атаку (злоумышленник меняет IP-адрес домена очень часто, чтобы обойти политику безопасности).

## 3. Типы DNS-записей (Resource Records)

| Тип       | Значение | Назначение                                       |
| :-------- | :------- | :----------------------------------------------- |
| **A**     | 1        | IPv4-адрес хоста                                 |
| **AAAA**  | 28       | IPv6-адрес хоста                                 |
| **CNAME** | 5        | Каноническое имя (алиас)                         |
| **MX**    | 15       | Почтовый сервер для домена                       |
| **NS**    | 2        | Авторитетный DNS-сервер                          |
| **TXT**   | 16       | Текстовая информация (SPF, DKIM, DMARC)          |
| **SOA**   | 6        | Начальная запись зоны                            |
| **PTR**   | 12       | Обратный указатель (IP → домен)                  |
| **SRV**   | 33       | Сервер для конкретного сервиса (VoIP, IM)        |
| **CAA**   | 257      | Ограничение выдачи сертификатов                  |
| **AXFR**  | 252      | Полная передача зоны (только по TCP)             |
| **ANY**   | 255      | Запрос всех записей (используется в DDoS-атаках) |

> **Простыми словами:**
> - **A** — «какой IP у example.com?» → `192.0.2.1`.
> - **AAAA** — то же, но для IPv6.
> - **CNAME** — «www.example.com — это алиас на example.com».
> - **MX** — «куда отправлять почту для example.com?» → `mail.example.com` с приоритетом 10.
> - **NS** — «какие DNS-серверы обслуживают example.com?».
> - **TXT** — используется для верификации домена и борьбы со спамом (SPF, DKIM, DMARC).
> - **SOA** — содержит информацию о зоне: серийный номер, время обновления (refresh), повторные попытки (retry), время истечения (expire), минимальный TTL.

### 3.1. Подробный разбор SOA-записи

SOA (Start of Authority) — ключевая запись для каждой зоны. Поля:

| Поле | Описание |
| :--- | :--- |
| **MNAME** | Имя основного DNS-сервера зоны |
| **RNAME** | Почта администратора зоны (в формате `hostmaster.example.com`) |
| **SERIAL** | Версия зоны (увеличивается при каждом изменении) |
| **REFRESH** | Период обновления зоны для вторичных серверов |
| **RETRY** | Пауза перед повторной попыткой обновления после ошибки |
| **EXPIRE** | Максимальное время, после которого зона считается недействительной |
| **MINIMUM** | Минимальный TTL для всех RRs зоны |

> **Примечание:** [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html) определяет, что MINIMUM используется как TTL для негативных ответов (NXDOMAIN, NODATA). Это позволяет кэшировать «отсутствие» домена и уменьшать нагрузку на DNS-серверы.

## 4. Транспорт: UDP и TCP

### 4.1. UDP (стандартные запросы)

- **Порт:** 53 (UDP).
- **Максимальный размер:** 512 байт (без EDNS), или до 4096 байт с EDNS ([RFC 6891](https://www.ietf.org/rfc/rfc6891)).
- **Преимущества:** Быстрее, меньшая задержка, меньше накладных расходов.
- **Недостатки:** Нет гарантии доставки; возможна потеря пакетов.

> **Почему это важно:** Если ответ превышает 512 байт, сервер устанавливает бит `TC` (Truncation), и клиент должен повторить запрос по TCP. Это стандартное поведение для больших ответов (например, с DNSSEC-подписями или большим количеством записей).

### 4.2. TCP (зонные передачи и большие ответы)

- **Порт:** 53 (TCP).
- **Использование:**
  - **AXFR** — передача всей зоны (только по TCP).
  - **Большие ответы** — когда UDP-ответ обрезан (TC=1).
- **Преимущества:** Гарантированная доставка, больший размер сообщений.

> **Важно для ИБ:** Зонные передачи (AXFR) — чувствительная операция. Если злоумышленник получит доступ к зоне, он сможет узнать все внутренние IP-адреса. Поэтому AXFR должен быть разрешён только доверенным вторичным серверам.

> **Дополнительно:** Помимо **AXFR** (полная передача зоны), существует **IXFR** (инкрементальная передача зоны) — она передаёт только изменения с момента последней версии. IXFR также работает по TCP.

## 5. Практическая диагностика

### 5.1. Команды для работы с DNS

**Утилита `dig` (Domain Information Groper):**
```bash
# Базовый запрос A-записи
dig example.com

# Запрос через конкретный DNS-сервер
dig @8.8.8.8 example.com

# Запрос MX-записей
dig example.com MX

# Запрос NS-записей
dig example.com NS

# Обратный DNS-запрос (по IP получить домен)
dig -x 8.8.8.8

# Сокращённый вывод (только IP)
dig +short example.com

# Трассировка всей цепочки делегирования
dig +trace example.com
```

**Утилита `nslookup`:**
```bash
# Базовый запрос
nslookup example.com

# Запрос MX-записей
nslookup -type=mx example.com

# Запрос через конкретный DNS-сервер
nslookup example.com 8.8.8.8

# Интерактивный режим
nslookup
> set type=mx
> example.com
```

**Утилита `host`:**
```bash
# Базовый запрос
host example.com

# Запрос MX-записей
host -t mx example.com

# Обратный DNS
host 8.8.8.8
```

**Утилита `whois`:**
```bash
# Информация о домене
whois example.com

# Информация об IP-адресе
whois 8.8.8.8
```

> **Совет для SOC:** `dig +trace` — незаменимый инструмент для диагностики проблем с делегированием. Если цепочка обрывается на каком-то шаге, это может указывать на неправильную конфигурацию DNS-серверов или на блокировку трафика.

> **Полезный совет:** `dig +trace` показывает весь путь от корневых серверов до авторитетного. Если на каком-то шаге ответ не приходит, это помогает локализовать проблему (например, неправильное делегирование или блокировка на фаерволе).

### 5.3. Анализ в Wireshark

| Фильтр | Что показывает |
| :--- | :--- |
| `dns` | Все DNS-пакеты (запросы и ответы) |
| `dns.flags.response == 0` | Только DNS-запросы |
| `dns.flags.response == 1` | Только DNS-ответы |
| `dns.qry.name contains "example.com"` | Запросы к доменам, содержащим `example.com` |
| `dns.qry.name == "example.com"` | Запросы к точному домену |
| `dns.flags.rcode != 0` | Пакеты с кодами ошибок (NXDOMAIN, SERVFAIL) |
| `dns.flags.rcode == 3` | Пакеты с NXDOMAIN |
| `dns.qry.type == 1` | Запросы A-записей |
| `dns.qry.type == 28` | Запросы AAAA-записей |
| `dns.qry.type == 15` | Запросы MX-записей |

> **Как это работает в Wireshark:** Фильтр `dns.flags.response == 0` показывает только исходящие запросы, `dns.flags.response == 1` — только ответы. Комбинируй их с `dns.qry.name` для поиска конкретных доменов. Например: `dns.qry.name contains "malware" && dns.flags.response == 0` — найти запросы к подозрительным доменам.

> **Практический пример:** Чтобы найти все DNS-запросы к домену `evil.com`, используй фильтр:
> `dns.qry.name contains "evil.com" && dns.flags.response == 0`
> Это позволит быстро выявить подозрительную активность.

## 6. Разбор сложных инженерных ситуаций и аномалий

### 6.1. Аномалия: DNS Spoofing (Подмена ответа)

**Суть:** Злоумышленник отправляет поддельный DNS-ответ раньше, чем настоящий сервер ответит. Если он угадает 16-битный ID транзакции и порт, жертва получит ложный IP-адрес.

**Как обнаружить:**
- В Wireshark видите **два ответа** на один запрос (один от настоящего сервера, один от злоумышленника).
- Ответ приходит с **другого IP-адреса**, не совпадающего с DNS-сервером, которому был отправлен запрос.
- В логах DNS-сервера — аномально высокая частота запросов к одному домену.

> **Почему это опасно:** Жертва подключается к поддельномy сайту, который выглядит идентично оригиналу. Это может привести к краже паролей, данных карт или установке вредоносного ПО.

**Защита:**
- **DNSSEC** — добавляет цифровые подписи к DNS-ответам, позволяя проверить их подлинность.
- **Рандомизация UDP-портов** — усложняет угадывание порта.
- **Использование DoH/DoT** (DNS over HTTPS/TLS) — шифрует DNS-трафик, что делает подмену невозможной без перехвата TLS.

### 6.2. Аномалия: DNS Cache Poisoning (Отравление кэша)

**Суть:** Злоумышленник «отравляет» кэш рекурсивного резолвера поддельными записями. После этого сервер выдаёт ложные IP-адреса всем клиентам.

**Как обнаружить:**
- В логах резолвера — большое количество поддельных ответов, которые прошли проверку.
- Клиенты подключаются к неожиданным IP-адресам (сравните с внешним DNS-сервером, например, `dig @8.8.8.8 example.com`).

> **Пояснение:** Атака Камински — классический метод отравления кэша. Злоумышленник заставляет резолвер запросить несуществующий поддомен (например, `random123.example.com`). В поддельном ответе он указывает авторитетный NS-сервер для `example.com`, который контролирует сам. Так он может получить контроль над всей зоной.

**Защита:**
- **Рандомизация портов** на стороне резолвера.
- **DNSSEC.**
- **Корректная настройка TTL** — слишком длинный TTL усугубляет последствия атаки.

### 6.3. Аномалия: DNS Tunneling (Туннелирование)

**Суть:** Злоумышленник использует DNS как скрытый канал для передачи данных (обычно с целью эксфильтрации или управления ботнетом). Данные кодируются в доменных именах или в TXT-записях.

**Как обнаружить:**
- **Аномально длинные DNS-запросы** — доменные имена в запросах длиннее обычных (например, `a1b2c3d4...example.com`).
- **Высокая частота запросов** к одному домену.
- **Подозрительные TXT-запросы** — запросы к TXT-записям для доменов, которые обычно не используют TXT.
- **Случайные поддомены** — в имени домена присутствуют случайные символы (base64-кодированные данные).

> **Почему это опасно:** Злоумышленник может выкачивать данные из заражённой сети, обходя традиционные брандмауэры и DLP-системы. DNS-трафик обычно разрешён, поэтому такой канал сложно заблокировать.

**Защита:**
- **Мониторинг аномалий** — анализ длины имён, частоты запросов.
- **Фильтрация DNS-трафика** — блокировка подозрительных доменов.
- **Использование DNS-фильтров** (например, Cisco Umbrella).

### 6.4. Аномалия: DNS Rebinding (Перепривязка)

**Суть:** Злоумышленник использует короткий TTL, чтобы заставить браузер жертвы сначала подключиться к внешнему серверу, а затем — к внутреннему (например, `127.0.0.1` или `192.168.1.100`).

**Как обнаружить:**
- В Wireshark видите, что один и тот же домен сначала резолвится в публичный IP, а затем в частный.
- В логах веб-приложения — запросы к `Host: evil.example` от внутренних IP.

**Защита:**
- **Валидация заголовка `Host`** на стороне сервера — сервер должен отклонять запросы, где `Host` не совпадает с ожидаемым.
- **Использование HTTPS** — в некоторых браузерах HTTPS смягчает последствия Rebinding.
- **Требование аутентификации** даже для локальных сервисов.

### 6.5. Аномалия: DNS Amplification (Усиленный DDoS)

**Суть:** Злоумышленник использует открытые рекурсивные DNS-серверы для проведения DDoS-атаки. Маленький запрос (например, `dig ANY example.com`) приводит к большому ответу (десятки килобайт), который отправляется на IP-адрес жертвы.

**Как обнаружить:**
- В логах DNS-сервера — запросы от одного IP, но с подменённым источником (spoofed source IP).
- В Wireshark — огромное количество DNS-ответов на маленький запрос.

> **Почему это опасно:** Соотношение «усиления» может достигать 100x и выше. Даже один маленький запрос может создать мегабайты трафика на жертву.

**Защита:**
- **Ограничение рекурсии** — только доверенные клиенты могут выполнять рекурсивные запросы.
- **Закрытие открытых резолверов** — не разрешать внешним пользователям делать рекурсивные запросы.
- **Rate limiting** — ограничение количества запросов с одного IP-адреса.
- **Мониторинг и фильтрация** — блокировка подозрительного трафика.

> **Важно:** Для DNS Amplification злоумышленники часто используют запросы типа **ANY** (255), так как они возвращают все записи домена и создают максимальный объём ответа при маленьком запросе.

## 7. Расширенный ИБ-контекст и инженерный FAQ

### 7.1. Векторы атак на DNS

| Атака | Цель | Обнаружение | Защита |
| :--- | :--- | :--- | :--- |
| **DNS Spoofing** | Перенаправление трафика | Два ответа на один запрос | DNSSEC, рандомизация портов |
| **DNS Cache Poisoning** | Отравление кэша резолвера | Подозрительные IP в ответах | DNSSEC, рандомизация портов |
| **DNS Tunneling** | Эксфильтрация данных | Длинные домены, частые TXT | Мониторинг, DNS-фильтры |
| **DNS Rebinding** | Обход Same-Origin Policy | Переключение IP у одного домена | Валидация Host, HTTPS |
| **DNS Amplification** | DDoS-атака | Большой ответ на маленький запрос | Ограничение рекурсии, rate limiting |
| **NXDOMAIN Flood** | DDoS на инфраструктуру | Массовые NXDOMAIN | Rate limiting, кэширование |

### 7.2. Инженерный FAQ

**Вопрос: Почему DNS использует UDP, а не TCP?**
**Ответ:** UDP — быстрее и имеет меньшие накладные расходы. Для стандартных запросов (один вопрос → один ответ) это оптимально. TCP используется только для зонных передач (AXFR) и когда ответ превышает размер UDP-пакета (TC=1).

**Вопрос: Что такое EDNS ([RFC 6891](https://www.ietf.org/rfc/rfc6891))?**
**Ответ:** EDNS (Extension Mechanisms for DNS) — расширение, позволяющее увеличить максимальный размер UDP-пакета с 512 байт до 4096 (и больше). Это необходимо для поддержки DNSSEC-подписей и IPv6-адресов. Также EDNS добавляет поле OPT pseudo-RR для передачи дополнительных опций (например, DNSSEC OK).

**Вопрос: Что такое DNSSEC?**
**Ответ:** DNSSEC — расширение DNS, добавляющее криптографические подписи к DNS-записям. Это позволяет резолверу проверить, что ответ пришёл от авторитетного сервера и не был изменён. Без DNSSEC DNS-ответы не защищены от подмены.

**Вопрос: Что такое DoH и DoT?**
**Ответ:**
- **DoH (DNS over HTTPS)** — DNS-запросы передаются по HTTPS (порт 443). Это шифрует трафик и делает его неотличимым от обычного HTTPS.
- **DoT (DNS over TLS)** — DNS-запросы передаются по TLS (порт 853). Оба метода защищают DNS от подмены и прослушивания.

**Вопрос: Что такое PTR-запись и зачем она нужна?**
**Ответ:** PTR-запись — это обратный DNS (reverse DNS). Она связывает IP-адрес с доменным именем (например, `8.8.8.8` → `dns.google`). PTR-записи используются для проверки отправителя почты (анти-спам), а также для диагностики.

**Вопрос: Как проверить, не отравлен ли кэш DNS-сервера?**
**Ответ:** Сравните ответы от подозрительного резолвера с ответами от внешнего доверенного сервера:
```bash
# Ответ от подозрительного сервера
dig @192.168.1.1 example.com

# Ответ от внешнего доверенного сервера
dig @8.8.8.8 example.com
```
Если IP-адреса различаются — кэш может быть отравлен.

**Вопрос: В чём разница между рекурсивным и итеративным DNS-запросом?**
**Ответ:** При **рекурсивном** запросе DNS-сервер полностью выполняет поиск от имени клиента и возвращает конечный результат (IP-адрес или NXDOMAIN). При **итеративном** запросе сервер возвращает только тот ответ, который знает сам (например, адрес вышестоящего сервера), не выполняя полный поиск за клиента.

**Вопрос: Что такое DNS query flood?**
**Ответ:** Это разновидность DDoS-атаки, при которой злоумышленник отправляет огромное количество DNS-запросов на сервер, чтобы перегрузить его ресурсы. В отличие от Amplification, здесь не используется подмена IP, но атака может быть направлена на рекурсивный резолвер, что приводит к деградации обслуживания легитимных клиентов.

## Заключение

DNS — фундаментальная система интернета, позволяющая преобразовывать доменные имена в IP-адреса. Понимание иерархии DNS-серверов, типов записей, структуры сообщений и транспорта (UDP/TCP) необходимо для анализа сетевого трафика, выявления аномалий и защиты от атак. Утилиты (`dig`, `nslookup`, `host`), Wireshark-фильтры и знания о векторах атак (Spoofing, Cache Poisoning, Tunneling, Rebinding, Amplification) являются обязательными инструментами SOC-аналитика. Внедрение DNSSEC, DoH/DoT и правильная конфигурация серверов значительно повышают безопасность инфраструктуры.
