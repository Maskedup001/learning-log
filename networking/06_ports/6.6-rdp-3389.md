# Тема 6.6: RDP (Remote Desktop Protocol) — Порт 3389

Изучение протокола удалённого рабочего стола RDP: архитектура «клиент-сервер», история версий, методы аутентификации и шифрования (NLA, CredSSP, TLS), основные уязвимости (BlueKeep, BlueGate, MS12-020), векторы атак (Brute Force, Session Hijacking, MitM, Tunneling, Amplification), анализ логов Windows (Event ID), инструменты диагностики и защиты.

---

## 1. RDP — Базовые свойства

- **Уровень OSI:** Прикладной (L7).
- **Транспорт:** TCP (порт `3389`), UDP (порт `3389` — для RDP over UDP, используется в современных версиях).
- **PDU:** RDP-сообщение (мультиплексированные виртуальные каналы).
- **Принцип работы:** RDP (Remote Desktop Protocol) — проприетарный протокол Microsoft для удалённого управления рабочим столом. Позволяет пользователю подключаться к удалённому компьютеру или серверу под управлением Windows, видеть его рабочий стол и управлять им через клавиатуру и мышь. Работает по схеме «клиент-сервер»: клиент (`mstsc.exe`, `xfreerdp`, `rdesktop`) подключается к серверу (Terminal Services / Remote Desktop Services).

> **Почему это важно для SOC:** RDP — один из самых популярных векторов начального доступа для вымогателей (ransomware). Через RDP злоумышленники получают интерактивный доступ к системе, могут перемещаться по сети (lateral movement), устанавливать вредоносное ПО и разворачивать атаки. По статистике, **~80% взломов RDP** связаны не с уязвимостями, а со слабыми паролями. Анализ RDP-логов и трафика позволяет выявить брутфорс, подозрительные подключения и попытки перехвата сессий.

### 1.2. Основные компоненты

- **RDP Client** — программа для подключения (`mstsc.exe`, `xfreerdp`, `rdesktop`, `Remmina`).
- **RDP Server** — служба Remote Desktop Services (Terminal Services) на Windows.
- **RD Session Host** — сервер, хостящий сессии.
- **RD Gateway (RDG)** — шлюз для маршрутизации RDP-трафика (прокси).
- **Виртуальные каналы (SVC/DVC)** — двунаправленные каналы для передачи данных (звук, буфер обмена, принтеры).

## 2. Архитектура и структура RDP-сессии

RDP-сессия состоит из последовательных этапов: установление TCP-соединения, согласование параметров, аутентификация и передача данных через виртуальные каналы.

### 2.1. Последовательность установки соединения

**Порядок этапов зависит от режима безопасности.**

**При использовании RDP Security Layer (без NLA):**
1. **TCP Handshake** — клиент подключается к порту 3389.
2. **X.224 Connection Request** — клиент отправляет запрос на подключение.
3. **Negotiation** — согласование параметров безопасности.
4. **MCS Connect Initial** — инициализация мультиплексного канала (MCS).
5. **GCC Conference Create** — создание конференции, настройка виртуальных каналов (SVC).
6. **Security Commencement** — начало безопасности.
7. **Интерактивная аутентификация** — ввод логина/пароля на экране входа.
8. **Data Transfer** — передача графики, клавиатуры, мыши.

> **Именно потому, что SVC создаются до начала безопасности (Security Commencement), становится возможной эксплуатация BlueKeep — злоумышленник манипулирует виртуальными каналами до аутентификации.** При NLA этот вектор закрыт, так как аутентификация происходит раньше создания SVC.

**При использовании NLA (CredSSP):**
1. **TCP Handshake**
2. **X.224 Connection Request**
3. **Negotiation** — согласование, включая NLA
4. **CredSSP аутентификация** — аутентификация через TLS-канал **до** MCS
5. **MCS Connect Initial** — только после успешной аутентификации
6. **GCC Conference Create** — создание SVC
7. **Data Transfer**

> **Критически важный нюанс:** При использовании **NLA (CredSSP)** аутентификация происходит **до** установки MCS-сессии и создания виртуальных каналов (SVC). Именно поэтому NLA закрывает BlueKeep: уязвимость эксплуатируется через манипуляцию SVC, которые при NLA ещё не созданы.

### 2.2. Виртуальные каналы

- **SVC (Static Virtual Channels)** — статические каналы, создаются при установке сессии и существуют до её завершения. Windows Server 2000 определил 32 SVC.
- **DVC (Dynamic Virtual Channels)** — динамические каналы, создаются и удаляются по запросу, содержатся внутри выделенного SVC.
- **MS_T120** — специальный внутренний канал, зарезервированный Microsoft для внутренних целей. Привязывается к каналу №31. Использование имени `MS_T120` на другом канале приводит к повреждению памяти (BlueKeep).

### 2.3. RDP over UDP (RDP-UDP)

Современный транспорт для RDP, используемый в Windows 10 / Server 2016+. Работает на **UDP/3389**, улучшает производительность при потере пакетов. Именно из-за него возможна амплификация (см. раздел 4.8).

## 3. Аутентификация и шифрование

### 3.1. Network Level Authentication (NLA)

**NLA** — механизм, требующий аутентификацию пользователя **до** создания RDP-сессии, а не после.

**Как работает:**
1. Клиент подключается к порту 3389.
2. Сервер предлагает методы аутентификации, включая NLA.
3. NLA использует **CredSSP (Credential Security Support Provider)** для шифрования и передачи учётных данных.
4. Сервер проверяет учётные данные **до** выделения ресурсов сессии и создания SVC.
5. Только после успешной аутентификации создаётся RDP-сессия.

**Преимущества NLA:**

| Преимущество | Описание |
| :--- | :--- |
| Сокращение поверхности атаки | Неаутентифицированный трафик не достигает уровня сессии |
| Защита от брутфорса | Неудачные попытки отклоняются до создания сессии (меньше нагрузки на сервер) |
| Экономия ресурсов | Память и CPU выделяются только после успешной аутентификации |
| Шифрование CredSSP | Учётные данные передаются по зашифрованному каналу |
| Соответствие требованиям | NIST, CIS Controls рекомендуют предварительную аутентификацию |
| Защита от BlueKeep | Аутентификация происходит до создания SVC |
*Таб. 2. Преимущества NLA и их описание.*

**Ограничения NLA:**
- Проверяет только учётные данные, не оценивает состояние устройства.
- Защищает только RDP, не другие протоколы.
- Не работает после успешного входа — не отслеживает действия пользователя.
- Требует совместимости клиента (CredSSP поддерживается Windows Vista+).

**Как включить NLA:**
- **Через System Properties:** «Разрешить подключения только с компьютеров, на которых запущен удалённый рабочий стол с проверкой подлинности на уровне сети».
- **Через Group Policy:** `Computer Configuration → Administrative Templates → Windows Components → Remote Desktop Services → Remote Desktop Session Host → Security → Require user authentication for remote connections by using Network Level Authentication`.

> **По умолчанию NLA включена** в Windows Vista+ (клиент) и Windows Server 2008+ (сервер). Для старых систем требуется проверка совместимости.

*Рис. 1. Group Policy: настройка «Require user authentication for remote connections by using Network Level Authentication».*

![Group Policy раздел Remote Desktop Session Host.png](/attachments/networking/06_ports/6.6-rdp-3389/Group%20Policy%20раздел%20Remote%20Desktop%20Session%20Host.png)

### 3.2. Шифрование: RDP Security Layer vs TLS

RDP поддерживает два подхода к шифрованию:

| Критерий               | RDP Security Layer (встроенное)                                       | TLS (внешнее)                               |
| :--------------------- | :-------------------------------------------------------------------- | :------------------------------------------ |
| Где реализовано        | Внутри протокола RDP                                                  | Отдельный протокол Transport Layer Security |
| Аутентификация сервера | Нет                                                                   | Да (через сертификат)                       |
| Уязвимость к MitM      | Да                                                                    | Нет                                         |
| Совместимость с NLA    | Нет                                                                   | Да                                          |
| Стойкость шифрования   | Классический RDP: RC4 (40/56/128 бит). FIPS-режим: 3DES. RDP 8+: AES. | TLS 1.2/1.3                                 |
| Рекомендация           | Только для устаревших систем                                          | Современный стандарт                        |
*Таб. 3. Сравнение RDP Security Layer и TLS.*

> **Важно:** RDP Security Layer **не обеспечивает аутентификацию сервера**, что делает соединение уязвимым для атак «человек посередине» (MitM).

> **Почему RDP Security Layer и NLA несовместимы:** NLA использует CredSSP, который для шифрования учётных данных требует TLS. RDP Security Layer — это встроенное шифрование без TLS. Поэтому при включённом NLA используется TLS-канал, а RDP Security Layer отключается.

> **Настройка Negotiate:** На практике часто используется настройка «Negotiate» — сервер автоматически выбирает самый безопасный метод, который поддерживает клиент. Если клиент и сервер понимают TLS — используется TLS; если нет — откат к встроенному шифрованию RDP. Это баланс между безопасностью и совместимостью.

> **TLS 1.3** оптимизирует рукопожатие (0-RTT), ускоряя установление соединения, при этом обеспечивая ту же криптостойкость, что и TLS 1.2.

## 4. Уязвимости и атаки

### 4.1. BlueKeep (CVE-2019-0708)

**Суть:** Критическая уязвимость в реализации RDP (не в самом протоколе, а в службе), позволяющая **неаутентифицированному** злоумышленнику выполнить произвольный код (RCE) на целевой системе. Оценка CVSS — **9.8 из 10**.

**Механизм:**
1. RDP резервирует канал `MS_T120` за номером 31.
2. Драйвер `termdd.sys` не проверяет, не создан ли уже пользовательский динамический канал с именем `MS_T120`.
3. Злоумышленник создаёт свой канал `MS_T120` и привязывает его к **другому** номеру (например, 4).
4. При закрытии канала происходит освобождение памяти, но остаётся висячий указатель на внутренний канал `MS_T120`.
5. Обращение к висячему указателю → **повреждение кучи (heap corruption)** → RCE.

**Уязвимые системы (по бюллетеню Microsoft):**
- Windows 7 (SP1)
- Windows Server 2008 R2
- Windows Server 2008
- Windows XP (SP3)
- Windows 2000 (уязвима по данным CISA AA19-168A; патч Microsoft не выпускала, так как ОС была вне поддержки)
- Windows Server 2003 (SP2)
- Windows Server 2003 R2 (SP2)
- Windows Vista

> **Важно:** CISA AA19-168A подтверждает, что Windows 2000 **уязвима** к BlueKeep, несмотря на отсутствие патча Microsoft. CISA провела тестирование и достигла RCE на этой ОС. Metasploit также поддерживает Windows 2000 x86 (все Service Packs).

**Червеподобный потенциал:** Уязвимость эксплуатируется **до аутентификации**, что позволяет ей распространяться автоматически по сети (как червь WannaCry), сканируя открытые порты 3389.

**Эксплуатация:**
- Metasploit: `exploit/windows/rdp/cve_2019_0708_bluekeep_rce`
- Проверка: `auxiliary(scanner/rdp/cve_2019_0708_bluekeep)`
- Техника heap spraying для предсказуемого размещения кода в куче.

**Защита:**
- Установить патч Microsoft от 14 мая 2019 года (KB4499175).
- Включить NLA (при NLA аутентификация происходит **до** создания динамических каналов).
- Заблокировать внешний доступ к порту 3389 через фаервол.
- Отключить RDP, если он не используется.

> **Важно:** Более новые версии Windows (начиная с Windows 8 / Server 2012) этой уязвимости не подвержены.

### 4.2. BlueGate (CVE-2020-0609/0610)

**Суть:** Уязвимости в компоненте **Windows Remote Desktop Gateway (RDG)** в Windows Server 2012/2012 R2/2016/2019. Позволяют неаутентифицированному злоумышленнику выполнить произвольный код через RDP.

**Механизм:**
- RDG поддерживает протоколы HTTP, HTTPS, UDP.
- Уязвимости — только в коде обработки **UDP** (порт 3391).
- **CVE-2020-0609:** ошибка проверки границ при сборке фрагментированных UDP-сообщений. Смещение вычисляется как `fragment_id * 1000`, но проверка не учитывает смещение → запись за пределами буфера кучи.
- **CVE-2020-0610:** массив для отслеживания фрагментов имеет размер 64, но `fragment_id` может быть до 65535 → запись за пределами массива.

**Защита:**
- Установить патчи Microsoft от января 2020 года.
- Отключить UDP-протокол RDG или заблокировать порт UDP/3391.

### 4.3. MS12-020 (CVE-2012-0002)

**Суть:** Уязвимость в RDP, позволяющая выполнить произвольный код или вызвать DoS (BSOD). Проверяется скриптом Nmap `rdp-vuln-ms12-020`.

### 4.4. RDP Brute Force

**Суть:** Самая распространённая атака на RDP — подбор паролей. По статистике, **~80% взломов RDP** связаны не с уязвимостями, а со слабыми паролями.

**Инструменты:**
- **Hydra:** `hydra -L usernames.txt -p 'password123' <IP> rdp`
- **Ncrack:** `ncrack -vv --user <user> -P pwds.txt rdp://<IP>`
- **Patator:** `patator rdp_login host=<IP> user=FILE0 password=FILE1 0=user.txt 1=passwords.txt`
- **Crowbar:** `crowbar -b rdp -s <IP>/32 -U users.txt -c 'password123'`

![Пример брутфорса RDP через Hydra.png](/attachments/networking/06_ports/6.6-rdp-3389/Пример%20брутфорса%20RDP%20через%20Hydra.png)

*Рис. 2. Пример брутфорса RDP через Hydra: 1 логин, 1 пароль, 0 валидных паролей найдено (тестовая VM).*

> **Что показывает этот пример:**
> - Hydra успешно подключилась к порту 3389 и начала перебор.
> - Пароль из словаря не подошёл → 0 valid password found.
> - Модуль RDP в Hydra помечен как **experimental** — не всегда стабилен.
> - При наличии политики блокировки (Account Lockout) такая атака быстро заблокирует учётную запись `Administrator`, что сделает её заметной в логах (Event ID 4740).

**Как обнаружить:**
- Массовые Event ID **4625** (Failed logon) с **Logon Type 10** (RemoteInteractive) или **Type 3** (Network).
- Коды ошибок: `0xC000006A` (неверный пароль), `0xC0000064` (неизвестное имя пользователя).
- Успешный вход (**4624**) после серии неудач с тем же IP.

**Защита:**
- Политика блокировки учётной записи (например, после 3 неудачных попыток).
- Сложные пароли, менеджеры паролей.
- Двухфакторная аутентификация (2FA).
- Rate limiting, fail2ban.

> **Внимание:** При брутфорсе возможна блокировка учётных записей (account lockout). Использовать с осторожностью.

### 4.5. MitM-атака на RDP (Seth)

**Суть:** Злоумышленник выдаёт себя за RDP-сервер, перехватывая учётные данные пользователя. Работает при отсутствии аутентификации сервера (RDP Security Layer без TLS).

**Инструмент:** **Seth** (SySS-Research).
```bash
git clone https://github.com/SySS-Research/Seth.git
cd Seth
pip install -r requirements.txt
apt install dsniff
/usr/share/seth/seth.sh
```

**Как работает:**
1. Атакующий запускает Seth, указывая интерфейс и цели.
2. Пользователь пытается подключиться по RDP.
3. Seth подменяет сертификат, пользователь видит предупреждение о конфликте сертификатов.
4. Пользователь нажимает «Да», вводит учётные данные.
5. Seth перехватывает **NTLM-хеш** и/или **пароль в открытом виде**.

**Защита:** Обязательное использование TLS с проверкой сертификата. NLA.

### 4.6. RDP Session Hijacking (MITRE T1563.002)

**Суть:** Злоумышленник с привилегиями SYSTEM перехватывает активную сессию другого пользователя **без знания его пароля**.

**Как работает:**
1. Злоумышленник получает локальный доступ с правами администратора.
2. Использует `query user` для получения списка активных сессий.
3. Повышает привилегии до SYSTEM (`mimikatz` → `token::elevate`).
4. Подключается к чужой сессии через `tscon`:
   ```cmd
   tscon <ID> /dest:<SESSIONNAME>
   ```
5. Получает интерактивный доступ к рабочему столу жертвы.

![Список активных RDP-сессий через query user.png](/attachments/networking/06_ports/6.6-rdp-3389/Список%20активных%20RDP-сессий%20через%20query%20user.png)

*Рис. 3. Список активных RDP-сессий через query user: сессия администратора (rdp-tcp#16, ID 1, Active).*

![Справка по команде tscon.png](/attachments/networking/06_ports/6.6-rdp-3389/Справка%20по%20команде%20tscon.png)

*Рис. 4. Справка по команде tscon: используется для перехвата сессии другого пользователя.*

**Альтернативы:**
- **Mimikatz:** `ts::sessions` (список), `ts::remote /id:2` (подключение).
- **RDP Shadowing (Remote Control):**
  ```cmd
  qwinsta /server:<IP>
  quser /server:<IP>
  mstsc /v:<IP> /shadow:<SESSION_ID> /control /noconsentprompt
  ```
  Управляется политикой `HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services\Shadow` (0–4).

> **Важно:** Подключение к активной сессии отключает пользователя или текущую сессию — это заметно. Злоумышленники часто используют метод для доступа к открытым KeePass, MMC, браузерам с сохранёнными паролями.

**Защита:**
- Ограничить количество администраторов.
- Ограничить RDP-доступ.
- Мониторить Event ID 4778/4779 (переподключение/отключение сессии).

#### 4.6.1. RDPInception (Process Injection)

**Суть:** Если злоумышленник имеет локальный админ-доступ на машине, куда подключается пользователь по RDP, он может инжектировать свой beacon в процесс `rdpclip.exe` (RDP Clipboard) и действовать **от имени этого пользователя**.

**Как работает:**
1. Злоумышленник ждёт подключения пользователя (`net logons`).
2. Находит процесс `rdpclip.exe` в его сессии.
3. Инжектирует beacon (например, через Cobalt Strike: `inject <PID> x64 tcp-local`).
4. Через `\\tsclient\c` получает доступ к диску **оригинальной машины жертвы**.
5. Может записать backdoor в startup-папку жертвы:
```cmd
beacon> cd \\tsclient\c\Users\<username>\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup
beacon> upload C:\Payloads\pivot.exe
```

**Защита:** Мониторинг инжектов в `rdpclip.exe`, ограничение RDP-доступа.

#### 4.6.2. Scheduled Tasks as Logged-On User

**Суть:** Если пользователь залогинен, локальный админ может выполнить код **от его имени без пароля** через Task Scheduler.

```cmd
schtasks /create /S <HOST> /RU "<DOMAIN\user>" /SC ONCE /ST 00:00 /TN "Updater" /TR "cmd.exe /c whoami > C:\Windows\Temp\whoami.txt"
schtasks /run /S <HOST> /TN "Updater"
```

**Нюанс:** Если пользователь **не залогинен**, Windows потребует пароль для создания задачи. Если залогинен — задача переиспользует существующий контекст.

**Защита:** Мониторинг создания задач от имени других пользователей.

#### 4.6.3. Sticky Keys / Utilman Backdoor

**Суть:** Комбинация доступа к сессии + замена `sethc.exe` (Sticky Keys) или `utilman.exe` (Utility Manager) на `cmd.exe` даёт командную строку с правами SYSTEM на экране входа.

**Обнаружение:** Проверка целостности системных файлов, поиск подменённых бинарников.

**Инструмент для поиска:** [Sticky-Keys-Slayer](https://github.com/linuz/Sticky-Keys-Slayer).

#### 4.6.4. CredUI Prompt Abuse

**Суть:** После получения доступа в сессию жертвы можно показать **настоящий Windows credential prompt** через API `CredUIPromptForWindowsCredentials` и собрать учётные данные.

**Преимущество:** Prompt рендерится стандартными Windows API, а не фейковой HTML-формой — жертва не заподозрит фишинг.

#### 4.6.5. Requesting a PFX in Victim Context

**Суть:** Через scheduled task можно запросить сертификат/PFX от имени жертвы и использовать его для AD-аутентификации через PKINIT — **без кражи пароля**.

**Защита:** Мониторинг запросов сертификатов, ограничение прав на enrollment.

#### 4.6.6. RDP Shadowing Policy Values

Политика `HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services\Shadow`:

| Значение | Режим |
| :--- | :--- |
| **0** | Disabled |
| **1** | EnableInputNotify (управление, с подтверждением) |
| **2** | EnableInputNoNotify (управление, без подтверждения) |
| **3** | EnableNoInputNotify (просмотр, с подтверждением) |
| **4** | EnableNoInputNoNotify (просмотр, без подтверждения) |
*Таб. 4. Значения политики Shadow.*

```cmd
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" /v Shadow
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" /v Shadow /t REG_DWORD /d 2 /f
quser /server:<HOST>
mstsc /v:<HOST> /shadow:<SESSION_ID> /control /noconsentprompt /prompt
```

### 4.7. RDP Tunneling (SSH, SOCKS)

**Суть:** Обход фаерволов, блокирующих порт 3389, через туннелирование RDP-трафика в разрешённые протоколы (SSH, HTTPS).

**SSH-туннель:**
```bash
ssh -L 3390:<RDP_TARGET>:3389 user@<SSH_SERVER>
# Затем подключение к localhost:3390
```
Трафик RDP идёт через зашифрованный SSH-канал.

**SOCKS-прокси:**
- **SocksOverRDP** — добавляет SOCKS-прокси через Dynamic Virtual Channels.
- **rdp2tcp** — TCP-туннелирование через RDP-каналы.
- **proxychains** — запуск приложений через SOCKS.

#### 4.7.1. rdp2tcp (TCP-туннелирование через виртуальные каналы RDP)

```bash
xfreerdp /u:<user> /v:<IP> /rdp2tcp:/path/to/rdp2tcp/client/rdp2tcp
```

**Защита:**
- Блокировка нестандартных портов и туннелей.
- DPI (Deep Packet Inspection) для выявления RDP внутри других протоколов.
- Ограничение исходящих соединений.

### 4.8. RDP Amplification (DDoS)

**Суть:** Использование открытых RDP-серверов (UDP/3389) для усиления DDoS-атак.

**Механизм:**
- Атакующий отправляет маленький UDP-пакет (несколько байт) на порт UDP/3389.
- Сервер отвечает пакетом размером **1260 байт**.
- **Коэффициент усиления — 85.9x** (до 750 Гбит/сек).
- Порт RD Gateway UDP — **3391**.

> **Источник:** Исследование Netscout (2021). Коэффициент усиления — 85.9x, что позволяло достигать атак до 750 Гбит/сек. Microsoft рекомендовала использовать TCP/3389 вместо UDP/3389 и размещать RDP за VPN.

**Защита:**
- Использовать TCP-порт 3389 вместо UDP.
- Разместить RDP за VPN.
- Ограничить доступ к UDP/3389.

## 7. Разбор сложных инженерных ситуаций и аномалий

### 7.1. Аномалия: Подозрительная активность RDP в логах

**Сценарий:** В логах сервера — серия Event ID 4625 (Failed logon) с Logon Type 10, затем Event ID 4624 (Successful logon) с того же IP.

**Что делать:**
1. Проверить IP-адрес источника — легитимный ли он?
2. Проверить, с какой учётной записи произошёл вход.
3. Проверить, какие действия выполнялись после входа (запуск процессов, создание файлов).
4. Проверить Event ID 4740 (Account Lockout) — была ли блокировка учётной записи.
5. Если вход успешен — расследовать как инцидент (возможная компрометация).

### 7.2. Аномалия: Session Hijacking

**Сценарий:** В логах — Event ID 4778 (Session Reconnected) для сессии, которая не должна была переподключаться, или подключение к сессии другого пользователя.

**Что делать:**
1. Проверить, кто инициировал переподключение.
2. Проверить наличие подозрительных процессов (Mimikatz, `tscon.exe`).
3. Проверить, были ли повышения привилегий до SYSTEM.
4. Проверить использование `query user` / `qwinsta` — это может указывать на подготовку к атаке.

### 7.3. Аномалия: BlueKeep Exploit

**Сценарий:** В Wireshark — аномальные RDP-пакеты с созданием канала `MS_T120` на нестандартном номере (не 31). В логах — краш службы RDP.

**Что делать:**
1. Проверить версию Windows — уязвима ли она?
2. Проверить наличие патча KB4499175.
3. Проверить, включена ли NLA.
4. Если NLA отключена — срочно включить.

### 7.4. Аномалия: RDP Amplification

**Сценарий:** Массовые UDP-пакеты на порт 3389 с подменённым source IP.

**Что делать:**
1. Проверить, открыт ли UDP/3389 для внешнего доступа.
2. Ограничить доступ к UDP/3389.
3. Рассмотреть переход на TCP/3389.

### 8.4. Инженерный FAQ

**Вопрос: Почему NLA считается обязательной мерой безопасности?**
**Ответ:** NLA требует аутентификацию **до** создания RDP-сессии (до MCS и SVC). Это блокирует BlueKeep (каналы создаются после аутентификации), снижает нагрузку от брутфорса и защищает от MitM (Credentials передаются через CredSSP).

**Вопрос: В чём разница между RDP Security Layer и TLS?**
**Ответ:** RDP Security Layer — встроенное шифрование, но без аутентификации сервера (уязвимо к MitM). TLS — внешнее шифрование с аутентификацией сервера через сертификат. TLS безопаснее. Они взаимоисключающие с NLA.

**Вопрос: Что такое MS_T120 и почему он важен?**
**Ответ:** Это внутренний виртуальный канал Microsoft, зарезервированный за номером 31. Уязвимость BlueKeep позволяет создать пользовательский канал с именем MS_T120 на другом номере, что приводит к повреждению кучи и RCE.

**Вопрос: Как обнаружить брутфорс RDP в логах?**
**Ответ:** Event ID 4625 (Failed logon) с Logon Type 10 (RemoteInteractive). Массовые события с одного IP. Коды ошибок `0xC000006A` (неверный пароль) или `0xC0000064` (несуществующий пользователь). Возможна корреляция с Event ID 4740 (Account Lockout).

**Вопрос: Что такое RDP Shadowing?**
**Ответ:** Функция Windows, позволяющая администратору просматривать или управлять сессией другого пользователя. Управляется политикой `Shadow`. Злоумышленники могут использовать для перехвата сессий.

**Вопрос: Как защититься от RDP Amplification?**
**Ответ:** Использовать TCP/3389 вместо UDP/3389, разместить RDP за VPN, ограничить внешний доступ.

**Вопрос: Что такое CredSSP?**
**Ответ:** Credential Security Support Provider — протокол, используемый NLA для шифрования и передачи учётных данных между клиентом и сервером. Использует TLS.

**Вопрос: Какие порты использует RDP?**
**Ответ:** TCP/3389 (основной), UDP/3389 (RDP over UDP для современных версий), UDP/3391 (RD Gateway).

**Вопрос: Что такое RDPInception?**
**Ответ:** Техника, при которой злоумышленник инжектирует beacon в процесс `rdpclip.exe` пользователя, подключившегося по RDP, и через `\\tsclient\c` получает доступ к его локальному диску.

**Вопрос: Что такое Sticky Keys Backdoor?**
**Ответ:** Замена `sethc.exe` или `utilman.exe` на `cmd.exe` даёт командную строку с правами SYSTEM на экране входа. Обнаруживается через Sticky-Keys-Slayer.

**Вопрос: Почему Windows 2000 не указан в уязвимых для BlueKeep?**
**Ответ:** На момент выхода патча (май 2019) Windows 2000 уже был вне поддержки Microsoft, и официальный бюллетень его не включал. Патч для него не выпускался.

## 9. Рекомендации по защите RDP

1. **Включить NLA** — обязательно.
2. **Использовать TLS** (1.2/1.3) с валидным сертификатом.
3. **Отключить RDP**, если он не используется.
4. **Ограничить доступ** — VPN, IP-whitelist, не выставлять порт 3389 в интернет.
5. **Использовать сложные пароли** и менеджеры паролей.
6. **Настроить политику блокировки** — например, после 3 неудачных попыток.
7. **Включить 2FA** — двухфакторная аутентификация.
8. **Ограничить количество администраторов** с RDP-доступом.
9. **Регулярно обновлять** Windows и патчить уязвимости.
10. **Мониторить логи** — Event ID 4624, 4625, 1149, 21, 23, 24, 25, 4740.
11. **Использовать Sysmon** для глубокого мониторинга.
12. **Настроить ограничение времени сессии** — через Group Policy.
13. **Блокировать учётные записи с пустыми паролями**.
14. **Сделать резервные копии** — только для админов, с ограниченными правами.
15. **Мониторинг инжектов** в `rdpclip.exe` (RDPInception).
16. **Мониторинг создания задач** от имени других пользователей.
17. **Проверка целостности** `sethc.exe` и `utilman.exe`.
18. **Мониторинг enrollment сертификатов** (PFX abuse).
19. **Ограничение прав** на RDP Shadowing.

## Заключение

RDP — мощный инструмент удалённого управления, но одновременно — один из главных векторов атак для вымогателей. Понимание архитектуры RDP, версий, методов аутентификации (NLA, CredSSP) и шифрования (TLS) критически важно для SOC-аналитика. Уязвимости (BlueKeep, BlueGate), атаки (Brute Force, Session Hijacking, MitM, Tunneling, Amplification) и методы их обнаружения (Event ID, Wireshark, Sysmon) — обязательный минимум для расследования инцидентов. Защита строится на комплексе мер: NLA, TLS, ограничение доступа, мониторинг логов.
