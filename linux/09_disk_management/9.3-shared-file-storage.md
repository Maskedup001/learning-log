# Тема 9.3: Общее файловое хранилище

В данной теме рассматривается создание общего файлового хранилища в Yandex Cloud для двух виртуальных машин. Разбираются этапы создания инфраструктуры, подключения хранилища, монтирования через `virtiofs`, проверки работы общего доступа, настройки автоматического монтирования через `/etc/fstab`, а также поиск и устранение возможных проблем. Дополнительно рассматривается альтернативный вариант реализации общего хранилища через NFS на локальных виртуальных машинах.

---

## 1. Цель урока — Базовые свойства

- **Контекст/Уровень:** Облачные вычисления / Общие файловые хранилища / Yandex Cloud.
- **Основное назначение:** Настроить общее файловое хранилище для двух виртуальных машин в Yandex Cloud, чтобы обе машины имели доступ к одним и тем же данным.
- **Принцип работы:** Файловое хранилище подключается к виртуальным машинам через интерфейс Yandex Cloud, затем монтируется на каждой ВМ с помощью файловой системы `virtiofs`.

### 1.1. Сценарии использования общего файлового хранилища

| Сценарий | Описание |
| :--- | :--- |
| Централизованное хранение логов | Все серверы пишут логи в единое хранилище |
| Общие конфигурации | Несколько серверов используют одинаковые конфигурационные файлы |
| Задачи кэширования | Общий кэш для ускорения работы приложений |
| Распределённые вычисления | Обмен данными между узлами кластера |
| Отказоустойчивость и балансировка нагрузки | Несколько серверов работают с общими данными |

*Таб. 1. Сценарии использования общего файлового хранилища.*

---

## 2. Создание инфраструктуры в Yandex Cloud

### 2.1. Создание виртуальных машин

В консоли Yandex Cloud выбрать сервис **Compute Cloud** и создать две виртуальные машины со следующими параметрами:

| Параметр | Значение |
| :--- | :--- |
| Дистрибутив | Ubuntu |
| Вычислительные ресурсы | Своя конфигурация |
| Гарантированная доля vCPU | 20% |
| Оперативная память | 1 ГБ |
| Доступ | По OS Login |
| Размер диска | 10 ГБ (достаточно для учебных задач) |

*Таб. 2. Параметры виртуальных машин.*

> **Важное замечание:** Для учебных задач достаточно минимальной конфигурации. Гарантированная доля vCPU 20% означает, что виртуальная машина получит 20% вычислительных ресурсов физического ядра.

### 2.2. Создание файлового хранилища

1. В меню слева выбрать **Файловое хранилище**.
2. Нажать **Создать новое файловое хранилище**.
3. Задать имя (например, `hdd15`) и размер (**15 ГБ**).

### 2.3. Подключение хранилища к виртуальным машинам

Для каждой виртуальной машины:

1. В меню файлового хранилища выбрать **Подключить к виртуальной машине**.
2. Выбрать виртуальную машину из выпадающего списка.
3. Указать имя устройства (например, `hdd15`).
4. Нажать **Подключить**.

После подключения в свойствах хранилища отображается список подключённых ВМ.

> **Важное замечание:** При удалении ресурсов важно соблюдать последовательность: сначала отключить хранилище от ВМ, затем удалить хранилище, потом удалить ВМ. Если этого не сделать, после исчерпания гранта Yandex выставит счёт за использование ресурсов.

## 3. Подключение к виртуальным машинам

Для подключения используется SSH:

```bash
ssh -l <имя_пользователя> -i "<путь_к_приватному_ключу>" <публичный_IP>
```

Параметры подключения можно скопировать в свойствах каждой виртуальной машины в разделе подключения.

## 4. Монтирование файлового хранилища

### 4.1. Проверка доступности хранилища

После подключения в интерфейсе Yandex Cloud хранилище не отображается в выводе `df -h`. Его необходимо смонтировать вручную.

### 4.2. Создание точки монтирования

На обеих виртуальных машинах:

```bash
sudo mkdir /media/extradrive
```

> **Важное уточнение:** В данной теме используется `/media/extradrive`, так как это каталог для съёмных носителей. Для серверных задач чаще используют `/mnt`, но `/media` также допустим. Важно, чтобы точка монтирования существовала и была доступна для записи.

### 4.3. Монтирование

```bash
sudo mount -t virtiofs hdd15 /media/extradrive
```

Разбор команды:

| Параметр | Описание |
| :--- | :--- |
| `-t virtiofs` | Тип файловой системы (драйвер `virtiofs`) |
| `hdd15` | Имя устройства, указанное при подключении в Yandex Cloud |
| `/media/extradrive` | Точка монтирования |

*Таб. 3. Разбор команды монтирования.*

### 4.4. Проверка

```bash
df -h
```

В выводе появится строка с `hdd15`, типом `virtiofs` и точкой монтирования `/media/extradrive`.

> **Важное уточнение:** `virtiofs` — это тип файловой системы для общего хранилища в Yandex Cloud. Она обеспечивает высокую производительность при работе с виртуальными машинами.

## 5. Проверка работы общего хранилища

### 5.1. Создание файлов на первой машине

```bash
cd /media/extradrive
touch f1 f2 f3
```

### 5.2. Проверка на второй машине

```bash
ls /media/extradrive
```

Вывод: `f1 f2 f3`

### 5.3. Редактирование файла на второй машине

```bash
nano /media/extradrive/f1
# добавить текст, сохранить (Ctrl+O, Ctrl+X)
```

### 5.4. Проверка на первой машине

```bash
cat /media/extradrive/f1
```

Изменения отображаются на обеих машинах — это подтверждает, что хранилище является общим.

## 6. Автоматическое монтирование при загрузке

### 6.1. Создание резервной копии `/etc/fstab`

```bash
sudo cp /etc/fstab /etc/fstab.backup
```

### 6.2. Редактирование `/etc/fstab`

```bash
sudo nano /etc/fstab
```

Добавить строку:

```
hdd15  /media/extradrive  virtiofs  rw  0  0
```

### 6.3. Разбор полей записи

| Поле | Значение | Описание |
| :--- | :--- | :--- |
| 1 | `hdd15` | Имя устройства (как указано в Yandex Cloud) |
| 2 | `/media/extradrive` | Точка монтирования |
| 3 | `virtiofs` | Тип файловой системы |
| 4 | `rw` | Опции: чтение и запись |
| 5 | `0` | Dump (резервное копирование) — отключено |
| 6 | `0` | Проверка fsck — отключена |

*Таб. 4. Разбор полей записи в `/etc/fstab`.*

### 6.4. Проверка конфигурации

```bash
sudo umount /media/extradrive    # размонтировать
df -h | grep extradrive          # убедиться, что строки нет
sudo mount -a                    # смонтировать всё по fstab
df -h | grep extradrive          # проверить, что строка появилась
```

Если `mount -a` не выдаёт ошибок, а диск появился в `df -h`, конфигурация верна.

> **Важное уточнение:** В Yandex Cloud автоматическое монтирование может работать через `systemd` mount units (например, `media-extra_drive.mount`), которые создаются автоматически при настройке ВМ через `cloud-init`. В этом случае запись в `/etc/fstab` может не требоваться, так как `systemd` монтирует хранилище при загрузке через собственные юниты.

> **Пример проверки systemd юнита:**
> ```bash
> systemctl list-units --type=mount | grep extra_drive
> ```
> или универсальный вариант:
> ```bash
> systemctl list-units --type=mount
> ```

## 7. Поиск и устранение возможных проблем

### 7.1. Ошибка при монтировании: `wrong fs type`

**Симптом:**

```bash
sudo mount -t virtiofs ssd-15 /media/extra_drive
mount: /media/extra_drive: wrong fs type, bad option, bad superblock on ssd-15, missing codepage or helper program, or other error.
```

**Возможные причины:**
1. Неправильное имя устройства (не `ssd-15`, а `hdd15`).
2. Хранилище не подключено к данной ВМ.
3. Ошибка в имени файловой системы.

**Решение:** Проверить точное имя устройства через Yandex Cloud CLI.

### 7.2. Ошибка при получении информации о ВМ

**Симптом:**

```bash
yc comtupe instance get <vm_id>
bash: comtupe: command not found
```

**Причина:** Опечатка в команде.

**Решение:** Использовать правильную команду:

```bash
yc compute instance get <vm_id>
```

### 7.3. Проблема: mount не находит устройство

Если `mount` не находит устройство `hdd15`, необходимо проверить точное имя устройства в Yandex Cloud:

1. Открыть **Cloud Shell** в консоли Yandex Cloud.
2. Выполнить команду:

```bash
yc compute instance get <идентификатор_ВМ>
```

3. В выводе найти раздел `file_systems` и поле `device_name` — это имя, которое нужно использовать при монтировании.

## 8. Удаление ресурсов

### 8.1. Отключение хранилища от виртуальных машин

1. В свойствах файлового хранилища перейти на вкладку **Виртуальные машины**.
2. Выделить обе ВМ и нажать **Отключить файловое хранилище**.

### 8.2. Удаление хранилища

После отключения от всех ВМ хранилище можно удалить кнопкой **Удалить**.

### 8.3. Удаление виртуальных машин

В списке Compute Cloud нажать меню (три точки) → **Удалить** для каждой ВМ.

> **Важное замечание:** Рекомендуется также удалить облако и платёжный аккаунт, чтобы избежать списания средств после исчерпания гранта. Удаление облака можно выполнить в консоли управления: выбрать облако → меню → **Удалить облако**. Срок удаления облака по умолчанию — 7 дней, в течение которых тарификация продолжается.

## 9. Альтернативный вариант: общее хранилище через NFS

Вместо Yandex Cloud можно реализовать общее хранилище на локальных виртуальных машинах с помощью **NFS** (Network File System).

### 9.1. Инфраструктура и сетевая настройка

Две локальные виртуальные машины в VirtualBox с Ubuntu Server. В настройках VirtualBox выбран режим **«Мостовой адаптер»** (Bridged Adapter), чтобы обе машины получили IP-адреса в одной локальной подсети.

**IP-адреса виртуальных машин:**
- **Сервер NFS:** `192.168.1.73`
- **Клиент NFS:** `192.168.1.72`

### 9.2. Настройка Сервера NFS (Машина 1, IP 192.168.1.73)

#### Создание папки для общего хранилища

```bash
sudo mkdir -p /srv/shared
```

#### Установка NFS-сервера

```bash
sudo apt update
sudo apt install nfs-kernel-server
```

#### Настройка экспорта (доступа к папке)

В файле `/etc/exports` на сервере добавить строку:

```text
/srv/shared 192.168.1.0/24(rw,sync,no_subtree_check)
```

Разбор параметров:

| Параметр | Описание |
| :--- | :--- |
| `/srv/shared` | Папка, которая отдаётся по сети |
| `192.168.1.0/24` | Диапазон IP-адресов, которым разрешён доступ |
| `rw` | Чтение и запись |
| `sync` | Синхронная запись |
| `no_subtree_check` | Отключение проверки поддеревьев |

*Таб. 5. Параметры экспорта NFS.*

#### Применение настроек

```bash
sudo exportfs -a
sudo systemctl restart nfs-kernel-server
```

### 9.3. Настройка Клиента NFS (Машина 2, IP 192.168.1.72)

#### Создание точки монтирования

```bash
sudo mkdir -p /mnt/nfs_share
```

#### Установка NFS-клиента

```bash
sudo apt install nfs-common
```

#### Монтирование удалённого хранилища

```bash
sudo mount -t nfs 192.168.1.73:/srv/shared /mnt/nfs_share
```

> **Важное замечание:** Не используйте угловые скобки `< >` вокруг IP-адреса — они воспринимаются как текст, а не как переменная. Команда `sudo mount -t nfs <192.168.1.73>:/srv/shared /mnt/nfs_share` выдаст ошибку `No such file or directory`.

#### Проверка

```bash
df -h
```

В выводе появится строка:

```text
192.168.1.73:/srv/shared  8,1G  5,1G  2,6G  67%  /mnt/nfs_share
```

### 9.4. Проверка работы общего хранилища

**На Сервере:**
```bash
cd /srv/shared
touch f1 f2 f3
ls /srv/shared
```

**На Клиенте:**
```bash
ls /mnt/nfs_share
nano /mnt/nfs_share/f1
# добавить текст, сохранить (Ctrl+O, Enter, Ctrl+X)
```

**Проверка на Сервере:**
```bash
cat /srv/shared/f1
```

Изменения, сделанные на клиенте, видны на сервере.

### 9.5. Автоматическое монтирование при загрузке (fstab)

#### Бэкап

```bash
sudo cp /etc/fstab /etc/fstab.backup
```

#### Редактирование fstab

```bash
sudo nano /etc/fstab
```

Добавить строку:

```text
192.168.1.73:/srv/shared  /mnt/nfs_share  nfs  rw,soft,intr,noatime  0  0
```

#### Применение и проверка

```bash
sudo mount -a
```

После перезагрузки машины (`sudo reboot`) строка `192.168.1.73:/srv/shared` снова появится в `df -h`, подтверждая правильность настроек.

### 9.6. Поиск и устранение проблем в NFS

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `mount.nfs: No such file or directory` | Угловые скобки вокруг IP-адреса | Убрать скобки, использовать правильный формат команды |
| `device is busy` при `umount` | Терминал находится в папке монтирования | Выйти из папки (`cd ~`) и повторить `sudo umount /mnt/nfs_share` |

*Таб. 6. Типичные проблемы при настройке NFS.*

> **Важное уточнение:** При настройке NFS необходимо синхронизировать UID/GID между сервером и клиентом. Если у локальной папки группа-владелец имеет GID 1455, то на клиенте нужно создать группу с таким же GID и включить в неё необходимых пользователей. Без синхронизации UID/GID права доступа в NFS будут работать некорректно.

> **Пример синхронизации UID/GID:**
> ```bash
> # На сервере и на клиенте
> sudo groupadd -g 1455 shared_group
> sudo usermod -a -G shared_group username
> 
> # На сервере - настроить права на папку
> sudo chown -R root:shared_group /srv/shared
> sudo chmod 770 /srv/shared
> ```

## 10. Сравнение подходов: Yandex Cloud vs NFS

| Критерий | Yandex Cloud (virtiofs) | NFS |
| :--- | :--- | :--- |
| Инфраструктура | Облачная | Локальная |
| Требования | Учётная запись Yandex Cloud, грант | Две ВМ в одной сети |
| Тип файловой системы | `virtiofs` | `nfs` |
| Сложность настройки | Низкая (всё через интерфейс) | Средняя (ручная настройка сервера и клиента) |
| Производительность | Высокая | Средняя (зависит от сети) |
| Стоимость | Платно после исчерпания гранта | Бесплатно |
| Совместимость | Только Yandex Cloud | Любая Linux-система |

*Таб. 7. Сравнение Yandex Cloud и NFS.*

> **Важное замечание:** Существуют и другие протоколы для общего доступа к файлам. Например, **Samba** реализует протокол SMB/CIFS (как в Windows), что делает её универсальным решением для смешанных сред.

> **Samba** — протокол SMB/CIFS (как в Windows). Устанавливается через `sudo apt install samba`, после чего настраивается в `/etc/samba/smb.conf`.

## 11. Контрольные вопросы

### Вопрос 1. Какой тип файловой системы используется для общего хранилища в Яндекс.Облаке?

- `virtiofs`
- `ntfs`
- `ext4`
- `xfs`

**Пояснение:** Для общего файлового хранилища в Yandex Cloud используется `virtiofs` — специальный тип файловой системы для виртуальных машин.

### Вопрос 2. В каких каталогах принято создавать точки монтирования?

- `/media` или `/mnt`
- `/etc` или `/bin`
- `/var` или `/opt`
- `/home` или `/tmp`

**Пояснение:** Точки монтирования обычно создаются в каталогах `/media` или `/mnt`. Каталоги `/etc` и `/bin` предназначены для конфигурационных файлов и исполняемых файлов.

### Вопрос 3. Какой командой можно обнаружить ошибки в файле `fstab`?

- `mount --verify`
- `sudo fstab check`
- `sudo mount -a`
- `fsck /etc/fstab`

**Пояснение:** Команда `sudo mount -a` монтирует все файловые системы, указанные в `/etc/fstab`. Если в записи есть ошибка, команда выведет сообщение об этом.

### Вопрос 4. Как получить информацию о виртуальной машине в Яндекс.Облаке? (команда в консоли Cloud Shell)

- `cloud instance show <vm_id>`
- `yc vm info <vm_id>`
- `yc compute instance get <vm_id>`
- `yc machine details <vm_id>`

**Пояснение:** Правильная команда — `yc compute instance get <vm_id>`. Обратите внимание на слово `compute` — в исходном конспекте была опечатка `comtupe`.

### Вопрос 5. Что нужно сделать перед удалением файлового хранилища?

- Отключить его от всех виртуальных машин
- Удалить все файлы в хранилище
- Остановить все виртуальные машины
- Создать резервную копию файлового хранилища

**Пояснение:** Перед удалением файлового хранилища необходимо отключить его от всех виртуальных машин. В противном случае удаление может быть заблокировано системой.

## 12. Разбор сложных инженерных ситуаций, граничных кейсов и аномалий

### 12.1. Проблема: система монтирует хранилище без записи в `/etc/fstab`

**Вопрос:** _Почему хранилище монтируется автоматически без записи в `/etc/fstab`?_

**Ответ:** В Yandex Cloud автоматическое монтирование может работать через `systemd` mount units (например, `media-extra_drive.mount`), которые создаются автоматически при настройке ВМ через `cloud-init` или метаданные ВМ. Systemd монтирует хранилище при загрузке через собственные юниты — это более гибкий и надёжный способ для облачных сред.

> **Пример проверки systemd юнита:**
> ```bash
> systemctl list-units --type=mount
> ```
> В выводе найдите юнит, соответствующий вашему хранилищу.

### 12.2. Проблема: ошибка при монтировании `virtiofs`

**Симптом:**

```bash
sudo mount -t virtiofs ssd-15 /media/extra_drive
mount: /media/extra_drive: wrong fs type, bad option, bad superblock on ssd-15, missing codepage or helper program, or other error.
```

**Возможные причины:**
1. Неправильное имя устройства (использовано `ssd-15` вместо `hdd15`).
2. Хранилище не подключено к данной ВМ.
3. Ошибка в имени файловой системы.

**Решение:** Проверить точное имя устройства через Yandex Cloud CLI:

```bash
yc compute instance get <vm_id>
```

В выводе найти раздел `file_systems` и поле `device_name`.

### 12.3. Проблема: опечатка в команде Yandex Cloud CLI

**Симптом:**

```bash
yc comtupe instance get <vm_id>
bash: comtupe: command not found
```

**Решение:** Использовать правильную команду:

```bash
yc compute instance get <vm_id>
```

### 12.4. Проблема: терминал находится в папке монтирования при `umount`

**Симптом:**

```bash
sudo umount /mnt/nfs_share
umount: /mnt/nfs_share: target is busy
```

**Решение:** Выйти из папки (`cd ~`) и повторить команду.

### 12.5. Проблема: синхронизация UID/GID в NFS

**Вопрос:** _Как правильно настроить права доступа в NFS?_

**Ответ:** При настройке NFS необходимо синхронизировать UID/GID между сервером и клиентом. Если у локальной папки группа-владелец имеет GID 1455, то на клиенте нужно создать группу с таким же GID и включить в неё необходимых пользователей. Без синхронизации UID/GID права доступа будут работать некорректно.

## 13. Лимиты, оптимизация и масштабирование

- **Грант Yandex Cloud:** После исчерпания гранта за использование ресурсов взимается плата. Важно своевременно удалять ресурсы.
- **Производительность `virtiofs`:** Обеспечивает высокую производительность при работе с виртуальными машинами, близкую к нативным файловым системам.
- **NFS в локальной сети:** Производительность зависит от пропускной способности сети. Для больших объёмов данных рекомендуется использовать гигабитные соединения.
- **Масштабирование:** Общее хранилище можно подключать к нескольким виртуальным машинам одновременно, что делает его удобным для кластерных решений.

## 14. Влияние на смежные системы и компоненты

### 14.1. Зависимости

- **`/etc/fstab`** — влияет на загрузку системы. Ошибки в этом файле могут привести к невозможности загрузки.
- **`systemd`** — использует `/etc/fstab` для монтирования файловых систем при загрузке. Изменения требуют `systemctl daemon-reload`.
- **`cloud-init`** — в Yandex Cloud может автоматически создавать `systemd` mount units для файловых хранилищ.

### 14.2. Влияние на производительность

- **`virtiofs`** — высокопроизводительная файловая система для облачных сред, обеспечивает низкую задержку при доступе к данным.
- **NFS** — производительность зависит от сети и настроек сервера. Рекомендуется использовать `sync` для надёжности, но это снижает производительность.

### 14.3. Влияние на безопасность

- **Неправильные права доступа** в NFS могут привести к несанкционированному доступу к данным.
- **Несинхронизированные UID/GID** приводят к некорректной работе прав доступа.
- **Удаление ресурсов Yandex Cloud** без отключения хранилища от ВМ может привести к ошибкам или дополнительным расходам.

## 15. Расширенный ИБ-контекст и инженерный FAQ

### 1. Векторы атак и уязвимости (Security Context)

- **NFS без ограничения доступа:** Если в `/etc/exports` указать `*` вместо конкретного диапазона IP-адресов, любой хост в сети сможет получить доступ к общим данным. Это критическая уязвимость.
- **Несинхронизированные UID/GID:** Могут привести к некорректной работе прав доступа или несанкционированному доступу.
- **Ошибки в `/etc/fstab`:** Могут привести к отказу загрузки системы (DoS-атака на доступность).
- **Удаление ресурсов Yandex Cloud:** Если не отключить хранилище от ВМ, удаление может быть заблокировано, что приведёт к дополнительным расходам.

### 2. Инженерный FAQ

**Вопрос:** _Что такое `virtiofs` и чем она отличается от `ext4`?_

**Ответ:** `virtiofs` — это файловая система, оптимизированная для работы в виртуализированных средах. Она обеспечивает высокую производительность при доступе к данным с виртуальных машин. В отличие от `ext4`, `virtiofs` не является локальной файловой системой — она предназначена для работы с общими хранилищами в облачных средах.

**Вопрос:** _Что такое Cloud Shell в Yandex Cloud?_

**Ответ:** Cloud Shell — это консоль в интерфейсе Yandex Cloud, которая предоставляет доступ к облачным сервисам и командам через интерфейс командной строки. Она позволяет управлять инфраструктурой без установки дополнительного ПО.

**Вопрос:** _Можно ли использовать Samba вместо NFS для общего хранилища?_

**Ответ:** Да, Samba реализует протокол SMB/CIFS (как в Windows), что делает её универсальным решением для смешанных сред. Samba позволяет подключаться к общим папкам как с Linux, так и с Windows.

**Вопрос:** _Что делать, если после исчерпания гранта Yandex выставил счёт?_

**Ответ:** Рекомендуется своевременно удалять все ресурсы: отключить хранилище от ВМ, удалить хранилище, удалить ВМ, удалить облако и платёжный аккаунт. Если счёт уже выставлен, можно попытаться обратиться в поддержку Yandex Cloud, но, как показывает практика, списание задолженности маловероятно.

**Вопрос:** _Почему в Yandex Cloud хранилище может монтироваться автоматически без записи в `/etc/fstab`?_

**Ответ:** Yandex Cloud использует современный подход через `systemd` mount units, которые создаются автоматически при настройке ВМ через `cloud-init` или метаданные. `systemd` монтирует хранилище при загрузке через собственные юниты — это более гибкий и надёжный способ для облачных сред.

## Заключение

Общее файловое хранилище — ключевой компонент для организации совместной работы нескольких серверов. В Yandex Cloud оно реализуется через `virtiofs` и может автоматически монтироваться через `systemd` mount units. Альтернативные решения, такие как NFS и Samba, позволяют организовать общее хранилище в локальных сетях без использования облачных сервисов. Правильная настройка прав доступа и синхронизация UID/GID — критически важные аспекты для обеспечения безопасности и корректной работы общего доступа.
