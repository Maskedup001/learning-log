# Тема 1.3: Настройка SSH-сервера и устранение сетевых проблем (Полный разбор)

В данной теме детально разбирается установка и управление SSH-сервером на Linux, изучение, как настроить сетевые адаптеры в VirtualBox (режимы Bridged и NAT), решение реальной проблемы с Wi-Fi с помощью USB-адаптера, диагностирование типичных ошибок (`No route to host`, `REMOTE HOST IDENTIFICATION`, `PATH`) и вывод критически важного порядка запуска виртуальных машин, без которого SSH просто не будет работать. Всё объясняется с точки зрения системного администратора: что, зачем и почему.

---

## 1. SSH и управление службами — Базовые свойства

* **Контекст/Уровень:** Системное администрирование / Сетевая безопасность (Прикладной уровень OSI).
* **Основное назначение:** Обеспечение безопасного удалённого доступа к командной оболочке (shell) сервера для выполнения административных задач, управления сервисами и разработки.
* **Принцип работы:** SSH (Secure Shell) — криптографический протокол, который шифрует весь трафик между клиентом и сервером (пароли, команды, файлы) и передаёт его через TCP-порт 22. Клиент и сервер проходят аутентификацию (по паролю или по ключам), после чего устанавливается защищённый канал.

### 1.1. Ключевые термины

| **Термин** | **Определение** | **Аналогия** |
| :--- | :--- | :--- |
| **SSH** | Протокол безопасного удалённого управления. | Как «закрытая дверь» для доступа к серверу. |
| **VPS** | Виртуальный выделенный сервер (Virtual Private Server). | Как отдельная квартира в дата-центре. |
| **SSH-клиент** | Программа, которая инициирует подключение. | Как ключ от двери. |
| **SSH-сервер (sshd)** | Демон на сервере, слушает порт 22. | Как охранник, который проверяет ключ. |
| **Приватный ключ** | Секретный файл, хранится только у клиента. | Как личный паспорт. |
| **Публичный ключ** | Открытый файл на сервере, связанный с учётной записью. | Как образец подписи в банке. |
| **Порт 22** | Стандартный порт для SSH. | Как конкретный вход в здание. |

### 1.2. Способы аутентификации в SSH
1. **По логину и паролю:** Менее безопасный, пароль можно подобрать или перехватить.
2. **По паре ключей (приватный + публичный):** Рекомендуемый метод. Клиент доказывает владение ключом без передачи его по сети.

## 2. Установка и управление SSH-сервером (Пошаговый процесс с разбором)

### 2.1. Обновление списка пакетов
Перед установкой любого ПО необходимо синхронизировать локальный список доступных пакетов с репозиториями.

```bash
sudo apt update
```

**Детальный разбор команды:**
- `sudo` — **SuperUser DO** (выполнить с правами администратора). Требуется, потому что установка пакетов изменяет системные файлы, к которым обычный пользователь не имеет доступа.
- `apt` — **Advanced Package Tool** (пакетный менеджер Debian/Ubuntu). Он управляет установкой, обновлением и удалением ПО.
- `update` — обновляет индекс пакетов: список того, что есть в репозиториях, и их версии. Без этого `apt` не знает, что вышла новая версия, и может установить устаревший софт.

> **Важное замечание о пароле:** Когда вы вводите пароль после `sudo`, **на экране не отображаются никакие символы** (ни звёздочек, ни движущегося курсора). Это стандартная мера безопасности, чтобы никто не мог подсмотреть длину пароля. Просто напечатайте пароль вслепую и нажмите Enter.

### 2.2. Установка пакета SSH-сервера

```bash
sudo apt install openssh-server
```

**Что устанавливается:**
- `openssh-server` — сам SSH-сервер (демон `sshd`), который будет принимать входящие подключения на порту `22`.
- `openssh-client` — SSH-клиент, который позволяет подключаться к другим серверам (обычно уже есть, но устанавливается заодно).
- Вспомогательные утилиты для генерации ключей и управления конфигурацией.

**Что произошло «под капотом»:**
1. `apt` скачивает пакет из репозитория.
2. Распаковывает его в системные папки.
3. Создаёт конфигурационные файлы (например, `/etc/ssh/sshd_config`).
4. Регистрирует службу в системе для управления через `systemd`.

### 2.3. Управление службой SSH (systemctl)

После установки SSH-сервер **не запускается автоматически** — его нужно запустить и настроить автозагрузку.

**Запуск службы:**
```bash
sudo systemctl start ssh
```

**Разбор:**  
`systemctl` — это утилита управления системными службами (демонами) в Linux. Слово `start` говорит системе: «запусти эту службу прямо сейчас».

**Добавление в автозагрузку:**
```bash
sudo systemctl enable ssh
```

`enable` создаёт симлинк в папке автозагрузки, чтобы служба запускалась при каждой перезагрузке системы. Если этого не сделать, после перезагрузки сервера SSH будет выключен, и вы не сможете подключиться удалённо.

**Проверка статуса:**
```bash
sudo systemctl status ssh
```

В выводе вы должны увидеть ключевые строки:
- `Active: active (running)` — служба работает.
- `ListenStream: 0.0.0.0:22` — сервер слушает порт `22` на всех интерфейсах.

Если статус `inactive (dead)`, значит, служба не запущена — проверьте предыдущие шаги.

### 2.4. Получение IP-адреса сервера

Для подключения по SSH вам нужен IP-адрес сервера. Команда:

```bash
hostname -I
```

**Разбор:**
- `hostname` — команда для работы с именем хоста и его сетевыми адресами.
- `-I` (заглавная i) — показывает **только реальные IP-адреса** всех сетевых интерфейсов (кроме петлевого `127.0.0.1`).
- **Важно:** Не путайте с `hostname -i` (строчная i). Она показывает только адреса, связанные с loopback-интерфейсом, который не подходит для внешнего подключения. Если вы попытаетесь подключиться к `127.0.0.1`, вы попадёте на самого себя, а не на сервер.

## 3. Настройка сети в VirtualBox (Режимы Bridged и NAT)

Если Linux установлен как виртуальная машина в VirtualBox, а подключение выполняется с хостовой системы (Windows), необходимо убедиться, что обе машины находятся в одной сети.

### 3.1. Что такое Bridged Adapter и зачем он нужен?

В VirtualBox есть несколько режимов сетевых адаптеров. По умолчанию используется **NAT**, но для SSH-подключений из локальной сети нам нужен **Bridged Adapter**.

**Bridged Adapter (сетевой мост)** — это режим, при котором виртуальная машина подключается напрямую к физическому сетевому адаптеру (Wi-Fi или Ethernet) вашего ноутбука. ВМ становится **полноправным устройством в вашей домашней сети** и получает свой собственный IP-адрес от роутера (например, `192.168.1.73`).

**Почему мы переходим с NAT на Bridged?**

| Режим | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **NAT** | ВМ скрыта за хостом, использует его IP для выхода в интернет. | Простота, безопасность (не видна извне). | Нельзя подключиться к ВМ по SSH с другого компьютера. |
| **Bridged** | ВМ имеет свой IP в локальной сети. | Можно подключаться с любого устройства в сети (ноутбук, телефон). | Требует правильной настройки, может конфликтовать с Wi-Fi. |
| **Host-only** | Изолированная сеть между хостом и ВМ. | Полная изоляция, безопасно для отладки. | Нет выхода в интернет. |

Для обучения и реальной работы мы выбираем **Bridged**, потому что он даёт гибкость и доступность.

### 3.2. Проблема: VirtualBox не дружит с Wi-Fi

Когда мы переключили **обе** виртуалки на Bridged через встроенный Wi-Fi ноутбука, мы столкнулись с проблемой: **только одна виртуалка получала IP-адрес**. Вторая оставалась без сети (интерфейс в состоянии `UP`, но без IPv4).

**Причина (технически):**  
У ноутбука **только одна физическая Wi-Fi-антенна**. VirtualBox пытается «занять» эту антенну для одной виртуалки. Когда вторая виртуалка тоже просит IP через тот же адаптер, возникает конфликт, и одна из них остаётся без адреса.

**Как это проверить?**  
На проблемной ВМ выполните `ip a`. Если вы видите интерфейс `enp0s3` со статусом `UP`, но без строки `inet 192.168.1.xxx`, значит, IP не получен.

### 3.3. Решение: USB Wi-Fi-адаптер

Чтобы обойти эту проблему, мы используем **внешний USB-адаптер Wi-Fi**. Это даёт нам **второй физический сетевой интерфейс** на ноутбуке.

**Архитектура:**
- **Встроенный Wi-Fi** → для графической виртуалки (`UbuntuLocal`).
- **USB-адаптер** → для сервера (`UbuntuServer`).

**Настройка в VirtualBox:**
1. Выключите обе виртуальные машины.
2. В настройках каждой ВМ перейдите в **«Сеть» (Network)**.
3. Убедитесь, что **Адаптер 1** включён и имеет тип **«Сетевой мост (Bridged Adapter)»**.
4. В поле **«Имя»** выберите соответствующий адаптер:
   - Для `UbuntuLocal` → встроенный Wi-Fi (например, `Intel(R) Wi-Fi 6 AX201`).
   - Для `UbuntuServer` → USB-адаптер (например, `TP-Link Wireless USB Adapter`).
5. Нажмите **ОК** и запустите виртуалки.

**Результат:** Обе ВМ получают свои IP-адреса в одной подсети (`192.168.1.0/24`) и могут видеть друг друга.

### 3.4. Добавление NAT на сервер — резервный канал и интернет

**Важный нюанс:**  
Если сервер имеет один Bridged-адаптер и получает реальный IP (например, `192.168.1.73`), а клиент находится в той же локальной сети, то **SSH-подключение по этому IP работает без NAT**. NAT не является обязательным условием для SSH.

**Зачем же тогда мы добавляем NAT на сервер?**

1. **Интернет для сервера.** Если Bridged-адаптер теряет связь с роутером (например, из-за перезагрузки Wi-Fi), сервер остаётся без интернета. NAT даёт ему стабильный выход в сеть через хост.
2. **Резервный маршрут для SSH.** Если Bridged «отваливается», сервер всё равно имеет внутренний IP-адрес от NAT (например, `10.0.2.15`). Клиент может подключиться по этому внутреннему IP через виртуальную сеть VirtualBox.
3. **Внутренняя маршрутизация.** VirtualBox использует NAT для связи между виртуальными машинами. Это гарантирует, что даже при нестабильном Bridged ВМ всё равно увидят друг друга.

**Таким образом, NAT на сервере — это не «обязательное условие для SSH», а надёжная страховка, которая делает лабораторию устойчивой к сбоям сети.**

> **Примечание:** Если вы уверены в стабильности Wi-Fi и роутера, можете не добавлять NAT — SSH будет работать по локальному IP. Но в реальной лаборатории с VirtualBox NAT настоятельно рекомендуется как страховка.

**Шаги:**
1. Выключить сервер (`UbuntuServer`).
2. В настройках VirtualBox → **«Сеть» (Network)** → вкладка **Адаптер 2**.
3. Поставить галочку `Включить сетевой адаптер`.
4. `Attached to` = **`NAT`**.
5. Запустить сервер.

**Итоговая конфигурация:**

| Виртуальная машина          | Адаптер 1                  | Адаптер 2    |
| :-------------------------- | :------------------------- | :----------- |
| **`UbuntuLocal`** (графика) | Bridged (встроенный Wi-Fi) | NAT отключён |
| **`UbuntuServer`** (сервер) | Bridged (USB-адаптер)      | NAT включён  |

**Почему это полезно:**  
NAT создаёт внутренний маршрут между виртуалками, который гарантирует связь даже при сбое Bridged. Это делает лабораторию отказоустойчивой.

## 4. Критически важный порядок запуска виртуальных машин

При использовании двух виртуалок в режиме Bridged через разные адаптеры (встроенный и USB) наблюдается конфликт сетевых ресурсов.

### 4.1. Проблема (что происходит при неправильном порядке)

Если вы запускаете **серверную виртуалку (`UbuntuServer`) первой**, то графическая виртуалка (`UbuntuLocal`) **теряет свой IPv4-адрес**, хотя интерфейс `enp0s3` остаётся в состоянии `UP`.

**Симптомы:**
- На графической ВМ пропадает интернет.
- `ip a` показывает интерфейс `UP`, но без строки `inet 192.168.1.xxx`.
- Попытка подключиться по SSH к графике выдаёт `Connection timed out`.

### 4.2. Причина (как это работает на уровне ОС)

Windows и VirtualBox используют **общий сетевой стек** (драйверы Wi-Fi). Когда сервер запускается первым через USB-адаптер, он резервирует сетевой канал для себя. Графическая ВМ, которая пытается использовать встроенный Wi-Fi, сталкивается с конфликтом — канал уже занят.

Если вы запускаете сервер первым, он «захватывает» управление сетевым стеком, и графике не хватает ресурсов для получения IP. Это не ошибка конфигурации, а архитектурная особенность VirtualBox на Windows.

### 4.3. Решение (жёсткий порядок действий)

Чтобы обе виртуалки стабильно работали, соблюдайте следующий порядок:

**Шаг 1. Первый заход — на графику (`UbuntuLocal`)**
1. Запустите графическую ВМ через VirtualBox.
2. Откройте терминал (`Ctrl+Alt+T`) и проверьте её состояние:
   ```bash
   ip a
   ```
   Убедитесь, что у неё есть IP вида `192.168.1.xxx`.
3. Проверьте интернет: `ping 8.8.8.8 -c 4`.
4. **Не выключайте графику** — оставьте её запущенной.

**Шаг 2. Второй заход — на сервер (`UbuntuServer`)**
1. Только после того как графика получила IP, запустите сервер.
2. Зайдите на сервер (через окно VirtualBox или через SSH с графики).
3. Проверьте его IP: `ip a`.
4. Убедитесь, что сервер тоже получил IP вида `192.168.1.xxx`.

**Итог:** Обе виртуалки стабильно работают и видят друг друга по SSH.

### 4.4. План восстановления (если уже сломалось)

Если вы случайно запустили сервер первым и графика потеряла IP, действуйте так:

1. Выйдите из сервера (`exit`).
2. Выключите серверную ВМ (`Power off`).
3. Отключите USB-адаптер от Wi-Fi (в Windows нажмите «Отключиться»).
4. Перезагрузите графическую ВМ (`Reset` или `Power off` → `Start`).
5. Подождите, пока графика получит IP (проверьте `ip a`).
6. Запустите серверную ВМ.
7. Теперь всё будет работать по правильному порядку.

**Важный вывод:**  
**Сначала графика, потом сервер. Никогда не наоборот.** Если ошиблись — выключите сервер, перезагрузите графику и начните заново.

## 5. Подключение к SSH-серверу с клиентской машины

### 5.1. Определение имени пользователя на сервере

На сервере выполните команду:
```bash
whoami
```

**Разбор:**  
`whoami` — сокращение от «who am I?». Она возвращает имя текущего пользователя, под которым вы вошли в систему. Это имя вам понадобится для подключения.

### 5.2. Подключение через встроенный терминал Windows (cmd)

```bash
ssh <username>@<IP-адрес>
```
Пример: `ssh maskedup@192.168.1.73`.

**Разбор:**  
- `ssh` — команда для запуска SSH-клиента.
- `maskedup` — имя пользователя на сервере.
- `@` — разделитель между пользователем и адресом.
- `192.168.1.73` — IP-адрес сервера.

### 5.3. Подключение через PuTTY (Windows)

PuTTY — классический графический SSH-клиент для Windows.

**Инструкция:**
1. Запустите PuTTY.
2. В поле **Host Name** введите `<username>@<IP-адрес>` (например, `itguy@192.168.1.100`).
3. Убедитесь, что порт — `22`, а тип подключения — SSH.
4. Нажмите **Open**.
5. При запросе введите пароль пользователя.

> **Совет:** PuTTY рекомендуется скачивать только с официального сайта разработчика: `https://www.chiark.greenend.org.uk/~sgtatham/putty/latest.html`.

## 6. Настройка SSH в Windows (проблема PATH)

### 6.1. В чём суть проблемы?

В командной строке (`cmd`) команда `ssh` может выдавать ошибку:
```
"ssh" не является внутренней или внешней командой, исполняемой программой или пакетным файлом.
```

**Причина:** Windows не знает, где находится исполняемый файл `ssh.exe`. По умолчанию он лежит в папке `C:\Windows\System32\OpenSSH`, но эта папка не добавлена в системную переменную `PATH`.

### 6.2. Что такое переменная PATH?

`PATH` — это специальная системная переменная, которая содержит список папок, в которых Windows ищет исполняемые файлы. Когда вы набираете `ssh`, Windows просматривает все папки из `PATH` и, если находит `ssh.exe`, запускает его. Если папка не добавлена, Windows не может найти программу.

### 6.3. Решение через PowerShell (рекомендуемое)

Запустите PowerShell от имени администратора и выполните одну строку:

```powershell
[Environment]::SetEnvironmentVariable("Path", $env:Path + ";C:\Windows\System32\OpenSSH", "Machine")
```

**Что делает эта команда:**
- `[Environment]::SetEnvironmentVariable` — функция .NET для изменения переменных окружения.
- `"Path"` — имя переменной, которую мы меняем.
- `$env:Path + ";C:\Windows\System32\OpenSSH"` — добавляет путь к уже существующему значению.
- `"Machine"` — указывает, что изменение должно применяться для всех пользователей системы.

После этого закройте `cmd` и откройте заново — команда `ssh` заработает.

### 6.4. Альтернативный способ (через графический интерфейс)

1. Нажмите `Win + R`, введите `sysdm.cpl` и нажмите Enter.
2. Перейдите на вкладку **«Дополнительно»**.
3. Нажмите **«Переменные среды...»**.
4. В разделе «Системные переменные» найдите `Path` и нажмите **«Изменить...»**.
5. Нажмите **«Создать»** и добавьте `C:\Windows\System32\OpenSSH`.
6. Нажмите **«ОК»** во всех окнах и перезагрузите `cmd`.

## 7. Устранение типичных ошибок при подключении (с разбором)

### 7.1. Ошибка `No route to host`

**Пример вывода:**
```
ssh: connect to host 192.168.1.73 port 22: No route to host
```

**Причина:** Клиент не может найти маршрут до сервера. Это может быть вызвано:
- Сервер выключен.
- SSH-сервер не запущен.
- Сетевые адаптеры настроены неправильно (например, разные подсети).

**Пошаговое решение:**
1. На сервере проверьте IP-адрес: `hostname -I`. Убедитесь, что он в той же подсети, что и клиент (например, оба в `192.168.1.0/24`).
2. **Проверьте статус SSH-сервера:** `sudo systemctl status ssh`.
   - Если статус `inactive (dead)`, запустите его: `sudo systemctl start ssh`.
   - Если статус `active (running)`, но подключение всё равно не работает — проверьте сетевые адаптеры.
3. Проверьте, что сервер слушает порт 22: `sudo ss -tlnp | grep ssh`.

### 7.2. Ошибка `REMOTE HOST IDENTIFICATION HAS CHANGED!`

**Пример вывода:**
```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
```

**Причина:** Ранее вы подключались к этому IP-адресу, но сервер изменил свои SSH-ключи (например, переустановили систему или заменили ВМ). SSH воспринимает это как потенциальную атаку «человек посередине».

**Решение:** Удалить сохранённый ключ для этого хоста:

```bash
ssh-keygen -R 192.168.1.73
```

После этого команда `ssh` снова запросит подтверждение (`yes/no`) при первом подключении.

### 7.3. Первое подключение (запрос подтверждения)

При первом подключении к новому серверу вы увидите:
```
The authenticity of host '192.168.1.73' can't be established.
Are you sure you want to continue connecting (yes/no)?
```

**Что это значит?**  
SSH проверяет, что сервер — действительно тот, за кого себя выдаёт. Он показывает вам отпечаток ключа (fingerprint), и вы должны вручную подтвердить, что доверяете этому серверу.

**Действие:** Введите `yes` и нажмите Enter. Ключ сервера будет сохранён в файле `~/.ssh/known_hosts`. В следующий раз запрос не появится.

## 8. Лимиты, оптимизация и масштабирование

### 8.1. Сравнение типов сетевого подключения в VirtualBox

| Тип адаптера | Описание | Когда использовать |
| :--- | :--- | :--- |
| **NAT** | ВМ скрыта за хостом, имеет выход в интернет, но извне недоступна. | Если нужен только интернет, без внешнего доступа. |
| **Bridged** | ВМ становится отдельным устройством в сети, имеет свой IP. | Для SSH-подключений из локальной сети. |
| **Host-only** | Изолированная сеть между хостом и ВМ без выхода в интернет. | Для отладки без риска внешних атак. |

### 8.2. Оптимизация сетевой архитектуры

В лабораториях с двумя виртуалками рекомендуется:
- На клиенте (`UbuntuLocal`) — только Bridged.
- На сервере (`UbuntuServer`) — Bridged + NAT (по желанию, для интернета и стабильности).

> **Примечание:** При этом SSH-подключение по локальному IP (например, `192.168.1.73`) работает и без NAT — он нужен только как резервный канал.

## 9. Влияние на смежные системы и компоненты

### 9.1. Зависимости
- **Сетевая инфраструктура:** Для SSH-подключений необходима корректная настройка сети (Bridged, NAT, Host-only). Неправильный выбор режима может сделать сервер недоступным.
- **Системные ресурсы:** Запуск SSH-сервера и работа с ключами требуют минимальных ресурсов, но при большом количестве подключений нагрузка на CPU и память возрастает.

### 9.2. Влияние на производительность
- **Нагрузка на CPU и RAM:** SSH-сервер использует ресурсы при каждом подключении. При большом количестве одновременных сессий нагрузка на систему увеличивается.
- **Нагрузка на диск:** Логирование SSH-подключений и передача файлов создают дополнительную нагрузку на диск.

### 9.3. Влияние на безопасность
- **Поверхность атаки:** SSH-сервер, доступный в локальной сети, создаёт потенциальную точку входа. Если он доступен из интернета, необходимы дополнительные меры защиты.
- **Управление ключами:** Приватные ключи должны храниться строго на клиентской машине. Их компрометация даёт полный доступ к серверу.
- **Порты:** Использование стандартного порта 22 делает сервер лёгкой целью для автоматических сканеров. Рекомендуется менять порт на нестандартный.

## 10. Расширенный ИБ-контекст и инженерный FAQ

### 10.1. Векторы атак и уязвимости (Security Context)

- **Атаки на SSH:** Подбор паролей (Brute-force), перехват сессии при использовании незашифрованных версий протокола, эксплуатация уязвимостей в старых версиях OpenSSH.
- **Защита:** Отключение входа по паролю (использование только ключей), смена стандартного порта `22`, настройка `fail2ban` для автоматической блокировки подозрительных IP.
- **Компрометация приватного ключа:** Если приватный ключ попадает в руки злоумышленника, он получает полный доступ к серверу. **Никогда не передавайте приватный ключ третьим лицам.**

### 10.2. Инженерный FAQ (На основе разбора дискуссий)

- **Вопрос:** *Почему в терминале при вводе пароля не отображаются символы?*  
  **Ответ:** Это стандартная мера безопасности, чтобы никто не мог подсмотреть длину пароля. Ввод происходит, просто индикация отключена.

- **Вопрос:** *Почему команда `hostname -I` показывает несколько IP-адресов?*  
  **Ответ:** Потому что на сервере может быть несколько сетевых интерфейсов (например, адаптер 1 и адаптер 2). `hostname -I` выводит все реальные IP-адреса, кроме петлевого.

- **Вопрос:** *Что делать, если после изменения типа сети на Bridged IP не меняется?*  
  **Ответ:** Попробуйте полностью перезагрузить виртуальную машину. Если не помогает, измените тип подключения на `Host-only`, примените, затем снова на `Bridged`. Иногда помогает пересоздание адаптера.

- **Вопрос:** *В чём разница между NAT и Bridged с точки зрения безопасности?*  
  **Ответ:** NAT скрывает виртуальную машину за хостом — она не видна извне. Bridged делает её полноценным устройством в сети, поэтому она потенциально уязвима для атак из локальной сети.

- **Вопрос:** *Почему USB-адаптер решает проблему с Wi-Fi?*  
  **Ответ:** Потому что он предоставляет второй физический сетевой интерфейс. Встроенный Wi-Fi остаётся для одной виртуалки, USB-адаптер — для другой, и конфликт за один канал исчезает.

## 11. Итоговые шпаргалки

### Шпаргалка по командам (быстрый доступ)

| Команда | Для чего |
| :--- | :--- |
| `sudo apt update` | Обновить список пакетов. |
| `sudo apt install openssh-server` | Установить SSH-сервер. |
| `sudo systemctl start ssh` | Запустить SSH-сервер. |
| `sudo systemctl enable ssh` | Включить автозагрузку SSH. |
| `sudo systemctl status ssh` | Проверить статус SSH-сервера. |
| `hostname -I` | Показать IP-адреса сервера. |
| `whoami` | Узнать имя текущего пользователя. |
| `ssh пользователь@IP` | Подключиться по SSH. |
| `ssh-keygen -R IP` | Удалить сохранённый ключ для хоста. |
| `exit` | Выйти из SSH-сессии. |

| :-------- | :----------- | :------- |

| Host-only | Нет          | Нет      |

## Заключение

SSH — это фундаментальный протокол для безопасного управления серверами. Его освоение — обязательный шаг для каждого системного администратора. Установка и настройка SSH-сервера, грамотное конфигурирование сетевых адаптеров в VirtualBox (Bridged + NAT), использование USB-адаптера для обхода конфликта Wi-Fi и соблюдение правильного порядка запуска виртуальных машин обеспечивают стабильную, отказоустойчивую среду для удалённого администрирования. Понимание этих принципов позволяет диагностировать и устранять типичные ошибки, такие как `No route to host` или проблемы с `PATH`, что является обязательным навыком для работы с серверной инфраструктурой.
