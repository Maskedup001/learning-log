# Тема 7.3: Специальные биты и права по умолчанию

В данной теме рассматриваются специальные биты прав доступа в Linux: SUID, SGID и Sticky Bit, а также маска прав по умолчанию `umask`. Разбираются их назначение, установка и снятие, отображение в `ls -l`, примеры применения на практике и вычисление прав по умолчанию для новых файлов и директорий.

---

## 1. Специальные биты — Базовые свойства

- **Контекст/Уровень:** Системное администрирование / Управление файловой системой.
- **Основное назначение:** Изменение стандартного поведения прав доступа для решения задач, требующих повышенных привилегий или совместного доступа.
- **Принцип работы:** Помимо стандартных прав `rwx`, в Linux существуют три специальных бита (SUID, SGID, Sticky Bit), которые изменяют поведение системы при работе с файлами и директориями.

### 1.1. Подготовка тестовой среды

Перед рассмотрением специальных битов необходимо очистить рабочую директорию и создать тестовые файлы.

```bash
rm -r *                 # удалить все файлы и папки в текущей директории
touch public_executable_file private_executable_file
```

## 2. Специальные биты

Помимо стандартных прав `rwx`, в Linux существуют три специальных бита, которые изменяют поведение системы при работе с файлами и директориями.

- **SUID (Set User ID)** — при запуске файла временно заменяет реального пользователя на владельца файла, что позволяет обычным пользователям выполнять привилегированные действия (например, `passwd` меняет файл `/etc/shadow` от имени root).
- **SGID (Set Group ID)** — при запуске файла подменяет группу пользователя на группу файла (для файлов), а для каталогов — заставляет все новые объекты наследовать группу родительского каталога, что нужно для организации общего доступа к файлам внутри одной группы.
- **Sticky bit** — ограничивает удаление файлов в общем каталоге так, что удалить или переименовать файл может только его владелец, root или владелец каталога, что используется для защиты чужих файлов в общедоступных местах (например, `/tmp`).

---

### 2.1. SUID (Set User ID)

**Назначение:** При запуске исполняемого файла процесс получает права владельца файла, а не пользователя, который его запустил.

**Установка и снятие:**
```bash
chmod u+s filename      # установить SUID
chmod u-s filename      # снять SUID
```

**Отображение в `ls -l`:**

| Отображение | Значение |
| :--- | :--- |
| `-rws------` | SUID установлен, право на исполнение (`x`) есть. |
| `-rwS------` | SUID установлен, права на исполнение нет (бессмысленная комбинация). |
*Таб. 1. Отображение SUID в `ls -l`.*

**Пример:**
```bash
# Дать владельцу право на исполнение
chmod u+x public_executable_file

# Установить SUID
chmod u+s *

ls -l
# -rwsr-xr-x 1 itguy itguy 0 ... public_executable_file   (s маленькая)
# -rwSr--r-- 1 itguy itguy 0 ... private_executable_file  (S большая)
```

**Поведение:**
- `public_executable_file`: SUID + `x` → любой пользователь при запуске получает права владельца (`itguy`).
- `private_executable_file`: SUID без `x` → файл нельзя запустить, SUID не имеет эффекта.

> **Почему `S` (заглавная) — это важно:** Заглавная `S` в правах означает, что SUID установлен, но у владельца нет права на исполнение. Это **визуальный маркер ошибки администратора** — система показывает, что SUID бесполезен, пока не будет восстановлено право `x`. Если позже владелец получит право `x`, `S` автоматически превратится в `s`, и SUID «проснётся».

**Важное ограничение:** SUID **не работает на shell-скриптах** (bash, python и т.д.) из соображений безопасности. Работает только с бинарными файлами.

> **Почему SUID не работает на скриптах?**  
> Если SUID установлен на скрипт, система **игнорирует** его, потому что скрипт запускается интерпретатором (например, `bash`), а не напрямую. При запуске скрипта его читает интерпретатор, который уже работает от имени пользователя. Поэтому SUID на скриптах **не имеет эффекта** — это ограничение безопасности.

**Примеры системных файлов с SUID:**
```bash
ls -l /bin/passwd /bin/ping /bin/su
# -rwsr-xr-x 1 root root ... /bin/passwd
# -rwsr-xr-x 1 root root ... /bin/ping
# -rwsr-xr-x 1 root root ... /bin/su
```

Эти файлы имеют владельца `root` и установленный SUID, поэтому любой пользователь может запустить `passwd` (для смены своего пароля) или `ping` с правами root.

> **Практическое применение SUID (реальные примеры):**
> 1. `passwd` — позволяет пользователю менять свой пароль, записывая хэш в `/etc/shadow`, доступный только root.
> 2. `ping` — позволяет отправлять ICMP-пакеты через raw socket, что требует прав root (в старых дистрибутивах).
> 3. `sudo` — сама команда `sudo` имеет SUID, чтобы проверять права пользователя в `/etc/sudoers`.

### 2.2. SGID (Set Group ID)

**Назначение:** Изменяет поведение в зависимости от типа объекта:
- **Для исполняемых файлов:** процесс получает права группы-владельца файла.
- **Для директорий:** новые файлы и папки, создаваемые внутри, наследуют группу родительской директории (вместо группы создателя).

**Установка и снятие:**
```bash
chmod g+s filename      # установить SGID
chmod g-s filename      # снять SGID
```

**Отображение в `ls -l`:**

| Отображение | Значение |
| :--- | :--- |
| `-rw-rwsr--` | SGID установлен, право на исполнение (`x`) есть. |
| `-rw-r-Sr--` | SGID установлен, права на исполнение нет (бессмысленная комбинация). |
*Таб. 2. Отображение SGID в `ls -l`.*

**Подготовка примера:**
```bash
# Дать группе право на исполнение
chmod 674 public_executable_file   # 6 = rw- для владельца, 7 = rwx для группы
ls -l public_executable_file
# -rw-rwxr-- ... public_executable_file

# Установить SGID на оба файла
chmod g+s *
ls -l
# -rw-rwsr-- ... public_executable_file   (s маленькая)
# -rw-r-Sr-- ... private_executable_file  (S большая)
```

**Поведение:**
- `public_executable_file`: SGID + `x` → любой пользователь при запуске получает права группы-владельца.
- `private_executable_file`: SGID без `x` → файл нельзя запустить, SGID не имеет эффекта.

**SGID на директориях (наследование группы):**
```bash
mkdir shared
chmod g+s shared
```

Все файлы, созданные внутри `shared/`, будут принадлежать группе родительской директории, а не группе создателя. Это удобно для организации общего доступа к файлам внутри одной группы.

> **Пример:** В директории `/var/shared/` установлен SGID. Пользователь `ivan` из группы `users` создаёт файл. Файл автоматически получает группу `developers` (группу директории), а **не** `users` (группу создателя). Это позволяет всем членам группы `developers` иметь доступ к файлу, даже если они не знакомы с `ivan`.

> **Практические примеры использования SGID:**
> 1. **Совместная работа в общей папке:** В директории `/var/shared/` с установленным SGID все новые файлы автоматически получают группу `developers`, даже если их создал пользователь из другой группы.
> 2. **Демоны:** Некоторые демоны (например, `crond`) запускают скрипты от разных пользователей, но они должны сохранять группу-владельца.

### 2.3. Sticky Bit

**Назначение:** Применяется к директориям. Защищает файлы внутри от удаления пользователями, которые не являются их владельцами.

**Установка и снятие:**
```bash
chmod +t directory      # установить sticky bit
chmod -t directory      # снять sticky bit
```

**Отображение в `ls -ld`:**
```bash
chmod +t .
ls -ld .
# drwxr-xr-t ... .   (t в конце прав)
```

**Поведение:**
- Владелец файла может удалить свой файл.
- `root` может удалить любой файл.
- Остальные пользователи не могут удалить чужие файлы (даже если имеют право `w` на директорию).

**Пример системной директории со Sticky Bit:**
```bash
ls -ld /tmp
# drwxrwxrwt ... /tmp
```

Папка `/tmp` — общедоступная директория, где любой пользователь может создавать файлы, но удалять может только свои.

## 4. Права по умолчанию — `umask`

### 4.1. Основные свойства

- **Контекст/Уровень:** Системное администрирование / Управление файловой системой.
- **Основное назначение:** Определение прав доступа, которые будут установлены для вновь создаваемых файлов и директорий.
- **Принцип работы:** `umask` (user file-creation mode mask) вычисляет права по умолчанию как `666` (для файлов) или `777` (для директорий) минус маска.

### 4.2. Просмотр и установка маски

```bash
umask           # просмотр текущей маски (обычно 002 или 022)
umask 333       # установить новую маску
umask -S        # показать маску в символьном виде
```

### 4.3. Принцип работы

Права по умолчанию вычисляются как:

- **Для файлов:** `666` (`rw-rw-rw-`) минус `umask`.
- **Для директорий:** `777` (`rwxrwxrwx`) минус `umask`.

#### 4.3.1. Пример с `umask 0002`

```bash
umask 0002
touch file1
ls -l file1
# -rw-rw-r-- ... file1   (664)
```

- **Максимум:** `666` → `110 110 110`
- **Маска:** `002` → `000 000 010`
- **Результат:** `110 110 100` → `rw-rw-r--`

#### 4.3.2. Пример с `umask 333`

```bash
umask 333
touch file2
ls -l file2
# -r--r--r-- ... file2   (444)
```

- **Максимум:** `666` → `110 110 110`
- **Маска:** `333` → `011 011 011` (в восьмеричной)
- **Результат:** `100 100 100` → `r--r--r--`

> **Почему `umask` не влияет на `x` у файлов?**  
> Для файлов стандартные права всегда `666` (без `x`), потому что выполнение для новых файлов обычно не требуется. `umask` может только **убрать** права, но не **добавить** их. Поэтому даже с `umask 000` новые файлы получают `rw-rw-rw-` (без `x`), а директории — `rwxrwxrwx` (с `x`).

> **Подробное объяснение про работу маски (AND и ~umask):**
> 
> `umask` работает как **побитовая маска**, которая запрещает определённые права. Она вычисляется как **побитовое И** (AND) между запрошенными правами и **инверсией маски** (`~umask`).
> 
> **Формула:**
> 
> `Результат = Запрошенные_права AND ~umask`
> 
> **Пример с `umask 333`:**
> - Запрошенные права: `664` (двоично: `110 110 100`)
> - `umask`: `333` (двоично: `011 011 011`)
> - Инверсия `umask` (`~333`): `100 100 100` (то есть, всё, что **не запрещено**)
> - Результат: `664 AND ~333` = `110 110 100` AND `100 100 100` = `100 100 100` = `444` (`r--r--r--`)
> 
> **Пример с `321` (запрошенные права):**
> - Запрошенные права: `321` (двоично: `011 010 001`)
> - Инверсия `umask` (`~333`): `100 100 100`
> - Результат: `321 AND ~333` = `011 010 001` AND `100 100 100` = `000 000 000` = `000` (`---------`)
> 
> **Ключевой вывод:** `umask` **ограничивает** запрошенные права, а не просто вычитает их. Если запрошенные права уже меньше ограничений маски, они могут быть **полностью обнулены** (например, `321` в примере выше превратился в `000`). Это объясняет, почему `umask` не всегда даёт одинаковый результат.

### 4.4. Часто используемые значения `umask`

| umask | Права для файлов | Права для директорий | Описание |
| :--- | :--- | :--- | :--- |
| `002` | `664` (`rw-rw-r--`) | `775` (`rwxrwxr-x`) | По умолчанию в многих дистрибутивах |
| `022` | `644` (`rw-r--r--`) | `755` (`rwxr-xr-x`) | Стандарт для серверов |
| `077` | `600` (`rw-------`) | `700` (`rwx------`) | Максимально закрытый режим |
*Таб. 4. Часто используемые значения `umask`.*

> **Расшифровка `umask 0022`:**  
> `0022` — это восьмеричное число, где каждая цифра соответствует правам для:  
> - `0` для владельца: ничего не запрещено (владелец получает все права по умолчанию).  
> - `2` для группы: запрещена запись (`w`).  
> - `2` для остальных: запрещена запись (`w`).  
>
> **Пример:**  
> - Для файлов: `666 - 022 = 644` (`rw-r--r--`).  
> - Для директорий: `777 - 022 = 755` (`rwxr-xr-x`).

### 4.5. Важные замечания

- `umask` действует только в рамках текущей сессии (терминала).
- После закрытия терминала маска сбрасывается к системному значению (обычно `002` или `022`).
- Системное значение по умолчанию можно изменить в конфигурационных файлах (`/etc/profile`, `~/.bashrc`).

## 5. Практические примеры

### 5.1. Работа со специальными битами

```bash
# Подготовка
touch some_file
chmod u+x some_file

# Установка SUID

```


```bash

```

## 6. Разбор сложных ситуаций и типичных вопросов

### 6.1. Зачем нужна заглавная `S` в правах?

**Вопрос:** *В чём практическая польза от `S` (заглавной) без `x`? Если нет права на исполнение, зачем ставить SUID?*

**Ответ:** Это исторически сложившийся **визуальный маркер**. Если вы видите `S`, это означает, что SUID установлен, но у владельца нет права на исполнение — либо это ошибка администратора, либо временное состояние. Если позже владелец получит право `x`, `S` автоматически превратится в `s`, и SUID «проснётся».

### 6.2. Для чего нужен SUID на практике?

**Вопрос:** *Какие реальные примеры использования SUID в Linux?*

**Ответ:** SUID нужен для решения дилеммы: как дать обычному пользователю возможность выполнить важное действие, требующее прав root, но не дать ему пароль администратора.

**Примеры:**

**Пример 1. Команда `passwd` (смена собственного пароля)**
Вы — обычный пользователь `ivan`. Хотите поменять свой пароль и пишете `passwd`. Проблема: ваши пароли хранятся в `/etc/shadow`, доступном только root.
Как спасает SUID: на `/usr/bin/passwd` установлен SUID-бит, а владелец — root. Когда `ivan` запускает `passwd`, программа на пару секунд получает права root, вписывает новый хэш пароля в `/etc/shadow` и завершает работу. Иван выполнил задачу, но доступа к чужим секретам не получил.

**Пример 2. Команда `ping` (проверка сети)**
Чтобы отправить ICMP-запрос, программе нужно открыть raw socket. Это привилегия, доступная только root.
Как спасает SUID: в старых дистрибутивах на `ping` вешали SUID. Обычный пользователь запускает команду, она от имени root на миллисекунду получает доступ к сетевой карте, отправляет пакет и возвращает управление.

**Пример 3. Команда `sudo` (власть на минуту)**
Сама команда `sudo` работает благодаря SUID-биту! Чтобы проверить, разрешено ли вам запускать команды от имени админа, `sudo` должна заглянуть в `/etc/sudoers`. Но обычный пользователь этот файл читать не может. Поэтому `sudo` обязана запускаться с правами root прямо в момент старта, проверять ваши права, и только потом выполнять то, что вы попросили.

### 6.3. Чем отличаются `S` и `s` в правах?

**Вопрос:** *Что означают строчная `s` и заглавная `S` в правах?*

**Ответ:**
- Строчная `s` — SUID (или SGID) установлен, и право на исполнение (`x`) присутствует. Всё работает.
- Заглавная `S` — SUID (или SGID) установлен, но права на исполнение (`x`) нет. SUID бесполезен, пока не будет добавлено `x`.

### 6.4. Почему `umask` не «вычитает» права из максимальных?

**Вопрос:** *Как правильно понимать работу `umask`?*

**Ответ:** `umask` **ограничивает** права, а не вычитает их из максимальных. Она определяет, какие права **запрещены** для новых файлов. Если файл запрашивает `664`, а маска `333`, результат будет `444` — потому что запрошенные права ограничиваются маской. Если файл запрашивает `321`, он получит `321`, так как его запрос уже меньше ограничений.

### 6.5. Можно ли работать с `umask` через символьные права?

**Вопрос:** *Можно ли устанавливать маску через символьный синтаксис?*

**Ответ:** Да, можно использовать `umask -S` для просмотра маски в символьном виде, а также `umask u=rwx,g=,o=` для установки маски в символьной форме.

### 6.6. Что означает `chmod +s`?

**Вопрос:** *Что делает команда `chmod +s`?*

**Ответ:** `chmod +s` устанавливает оба специальных бита, если они применимы:
- Для исполняемого файла — SUID.
- Для директории — SGID.

**Практические ситуации, где это может понадобиться:**

1. **Программы, требующие прав владельца и группы одновременно.** Например, утилита должна записывать логи от имени пользователя `logger` (setuid), но при этом читать конфиги, доступные только группе `admin` (setgid).

2. **Совместная работа с файлами в группе.** Скрипт, который создаёт файлы в `/var/shared/`, должен запускаться от текущего пользователя, но все новые файлы должны автоматически получать группу `developers` (setgid).

3. **Наследование окружения демона.** Демон (например, `crond`) запускает скрипты от разных пользователей, но они должны сохранять группу-владельца (setgid).

Примеры:
```bash
chmod +s /usr/bin/special_program  # Установит SUID, если файл исполняемый
chmod +s /shared_dir               # Установит SGID на директорию
```

## 7. Лимиты, оптимизация и масштабирование

- **SUID не работает на скриптах:** Это ограничение безопасности, которое предотвращает эксплуатацию скриптов с повышенными правами.
- **Sticky Bit:** Применяется только к директориям. Не имеет смысла для файлов.
- **`umask`:** Действует только в рамках текущей сессии. Для постоянного изменения необходимо редактировать конфигурационные файлы.

## 8. Расширенный ИБ-контекст и инженерный FAQ

### 1. Векторы атак и уязвимости (Security Context)

- **SUID:** Неправильная установка SUID на исполняемый файл может привести к повышению привилегий для злоумышленника. Например, если SUID установлен на скрипт, который можно изменить, это создаёт уязвимость.
- **Sticky Bit:** Отсутствие Sticky Bit в общедоступных директориях (например, `/tmp`) позволяет другим пользователям удалять чужие файлы.
- **`umask`:** Слишком открытая маска (например, `000`) может привести к созданию файлов с правами `777`, что делает их доступными для всех.

### 2. Инженерный FAQ

- **Вопрос:** *Можно ли установить SUID на скрипт?*  
  **Ответ:** Нет, SUID не работает на скриптах (bash, python и т.д.). Это ограничение безопасности.

- **Вопрос:** *Как изменить `umask` для текущей сессии?*  
  **Ответ:** Просто выполните `umask 022` — маска изменится до закрытия терминала.

- **Вопрос:** *Что означает `umask -S`?*  
  **Ответ:** `umask -S` показывает маску в символьном виде. Например, `umask -S` может вывести `u=rwx,g=rwx,o=rx`.

### Ключевые понятия:

- **SUID** — позволяет выполнять файл с правами владельца.
- **SGID** — для файлов: выполнение с правами группы; для директорий: наследование группы.
- **Sticky Bit** — защита от удаления чужих файлов в общей директории.
- **umask** — маска, определяющая права для вновь создаваемых файлов.

## Заключение

В этой теме были рассмотрены специальные биты прав доступа (SUID, SGID, Sticky Bit) и маска прав по умолчанию `umask`. Понимание этих механизмов позволяет настраивать гибкую и безопасную систему прав доступа, а также правильно организовывать совместную работу пользователей в общих директориях. Маска `umask` является важным инструментом для контроля прав на новые файлы, а специальные биты — для решения задач, требующих повышенных привилегий.
